## What landed since the last handoff

- **T5.2 — single step block (2026-07-25, `bb64d88`).** The five-move
  step pipeline exists once: `blocks/step.py`'s
  `run_step_attempts(spec, host)` with the pure three-row `MODE_POLICIES`
  table (assemble activity / worktree ownership
  fresh-keep·borrowed·fresh-dispose / commit policy task·step·never)
  replaced the three diverged copies in `workflows.py` (net −290 lines).
  Worktree-ownership cleanup wraps close the leak class — a mid-step
  exception removes the worktree **and** its `forge/<task_id>` branch in
  all three modes (the block wraps the fresh modes; `_run_planned` wraps
  the borrowed worktree it creates; batch-wait shapes stay with `run()`'s
  T1.6b handler). The git seams are idempotent under activity retry:
  `create_worktree` recreates over crashed leftovers (prune →
  force-remove stale registration → `worktree add -B`), `commit_changes`
  returns HEAD's SHA on a retry after a landed commit (message-keyed),
  `remove_worktree` no-ops when already gone. Exploration is a
  per-attempt hook inside the retry loop, ordering pinned by a
  full-sequence test. The committed replay histories pass unregenerated —
  each mode's activity sequence is unchanged.
- **Worker version identity stamp (`9c67b4f`).**
  `sax_platform.temporal.identity` (lazy PEP 562 export —
  `subprocess`/`socket` are sandbox-restricted) captures
  `git rev-parse --short HEAD` once at worker startup, appends `-dirty`
  when the launch tree is modified, and stamps it into every worker's
  Temporal identity. `temporal task-queue describe --task-queue <q>
  [--namespace forge-dev]` is now the authoritative "which code is this

- **Lane-based identity bases (`fb7111e`).** The vestigial `desktop-`

  prod launchd `prod-forge-worker-1/2` / `prod-ocr-worker` /

  gained forge's `--worker-identity` option (envvar
  `FORGE_WORKER_IDENTITY`); every poller identity reads lane + role +
  version and agrees with `FORGE_ENV`, the namespace split, and

- **D103 — pinned prod checkout + clean-code guard (`001247c`, amends
  D99).** Production no longer runs the live working tree: it runs a
  detached git worktree at `~/repos-sax/forge-prod`, deployed only by
  `make prod-deploy REF=<ref>` (`deploy/prod-deploy.sh`), and all three
  workers refuse to start when `FORGE_ENV=prod` and the checkout is
  dirty or unverifiable (`require_clean_prod_code`, stderr + exit 78).
  Motivated by a realized incident the same morning: an installer run
  against a dirty tree put uncommitted code into production, caught only

  `forge-prod` pinned at `001247c` (detached, clean), plists bound to
  `forge-prod` paths, all four prod pollers stamped clean.
- **`deploy/prod-ocr` (`c543d22`).** One-command production ocr CLI
  access: embeds the D102 ceremony (`FORGE_ENV=prod` + ack + profile via
  the parse-don't-eval `load-env.sh` loader) and execs
  `uv run --package ocr ocr <args>` **from the pinned prod checkout**, so
  the CLI client runs the same commit as the workers serving it — the
  live tree plays no part. stderr banner names namespace + checkout sha +
  command; refuses (exit 78) when `forge-prod` is missing rather than
  falling back. Embedding the ack is sanctioned by the plist precedent:
  the ceremony prevents *accidental* prod use, and invoking a script
  named `prod-ocr` is the explicit act. zsh, deliberately outside the
  launchd bash family (interactive operator tooling). Also that day: the
  README command audit (`f712dc4`) — every documented example now carries

## What to know before touching anything

1. **The prod deploy model changed (D103).** `make workers-restart` no
   longer ships code — it relaunches whatever commit `forge-prod` is
   pinned to. Shipping to prod is `make prod-deploy REF=<ref>` (commit
   first; a worktree can only check out commits). Plist-affecting
   changes additionally need the one-time
   `~/repos-sax/forge-prod/deploy/launchd/install.sh --with-pbook
   --with-ocr --with-backup` (bootout/bootstrap — cuts the graceful
   drain; prefer a quiet queue). The dev tmux lane still runs the live
   working tree — that is the lane's purpose; its mid-edit relaunch
   hazards remain. Production ocr CLI commands go through
   `deploy/prod-ocr <cmd>` (the ceremony + pinned checkout in one
   command); the four-line manual ceremony remains valid for the forge
   CLI.
2. **Prod pollers must never show `-dirty`.** If
   `temporal task-queue describe` ever shows a dirty prod identity,
   something bypassed `prod-deploy` — that is an incident, per D103.
   Note `describe` lists recently-seen pollers for a few minutes with
   their `LastAccessTime`; after a restart, old identities linger and
   age out (twice this looked like a failed rename before it was ghosts).
3. **Step-pipeline conventions (T5.2).** The pipeline body lives in
   `blocks/step.py`; mode differences are `MODE_POLICIES` rows, not
   branches. Do not reintroduce inline pipeline logic in `workflows.py`;
   new pure decision logic still goes to `step_logic.py` (T5.1 rule
   unchanged). `StepSpec.__post_init__` enforces the borrowed/fresh
   worktree-handle pairing — respect it; `create_worktree` now resets
   branches (`add -B`), so a borrowed mode must never fall through to
   creation.
4. **Replay histories are valid UNREGENERATED** (T5.2's proof). Caveat:
   no committed history exercises `assemble_step_context` — planned-step
   mode's sequence is pinned by workflow tests alone. T5.3 (gather) will
   face the same preserve-or-regenerate choice; preservation is the
   stronger proof when the sequences allow it, and T5.5's harness
   rebuild is the natural place to add a planned-step history.
5. **Marked cleanups for T5.3/T5.4** (recorded in code comments and
   T5.2's Development Notes): the timeout/retry preset duplication
   between `workflows.py` and `blocks/step.py` (retired when the gather
   paths move); the near-duplicate
   `blocks.step.cleanup_worktree_after_exception` vs
   `workflow_blocks.cleanup_worktree_after_failure` (fold when
   `workflow_blocks.py` is in bounds).
6. **Workflow-test notes.** New workflow tests must pass
   `sync_mode=True` (the batch-first default otherwise routes to an
   unregistered `submit_batch_request` mock). The T5.5 rules stand: no
   new module-global scenario state, no new transition-token
   vocabularies in `tests/test_workflows.py`.
7. **Owner process preferences** (standing): planning in the main
   session; implementation dispatched to the `implementation-driver`
   agent (Opus) with small hard-bounded scopes; commits only on the
   owner's explicit word; mechanism-level explanations — separate
   act-now / act-later / no-action; challenge weak arguments, don't
   praise.
