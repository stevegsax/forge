## What landed since the last handoff

- **T5.1 — pure step logic (D95, 2026-07-24, `a1c32cf`).** The
  `evaluate_transition` activity is deleted; `determine_transition` is a
  pure function in the new `forge/step_logic.py` (zero `temporalio`
  imports), inlined at all five step sites. The module owns the failure
  summaries, the terminal-result builders stamping the nine-value
  `failure_kind` Literal, `merge_resolution → MergedFiles |
  MissingResolutions`, the output slimming, `llm_totals`, and the
  child-id/timeout helpers. `TransitionInput` is gone; the 12 by-name
  transition mocks are gone — workflow tests drive the signal through the
  `validate_output` mock (pass → SUCCESS; fail → RETRYABLE until
  `max_attempts`, then TERMINAL). Six replay histories regenerated
  (deliberate workflow-logic change); Replayer 7/7.
- **Contents travel at most once.** Embedded Step/SubTaskResults carry
  sha256 `output_digests` instead of contents (a model validator rejects
  both-populated); the fan-out builders slim children **and** conflict
  resolution before a result crosses the child→parent workflow boundary;
  `TaskResult.output_files` is the single content-carrying place for
  folded successful steps. A failed step's contents are dropped from the
  result and survive only in its worktree — that is the documented
  invariant, not an accident. `TestPayloadCap` pins a 24×25KB fan-out at
  ~0.6MB serialized.
- **A four-angle `/simplify` pass is folded into T5.1** (same commit):
  logic-only builder set (the four pass-through success builders deleted;
  success results constructed inline), one generic
  `slim_result[R: (StepResult, SubTaskResult)]` with an already-slim
  fast path (slim subtrees returned by reference), invariants moved onto
  the models (`file_count` property, `LLMRunTotals.from_stats`,
  `MissingResolutions.message`), batch-wait builders own their error
  wording. Skips recorded in the task file's Development Notes (notably:
  test token-vocabulary cleanup → T5.5; gather message dedup → T5.3).
- **Lane-scoped worker restarts (`fe6469a`).** `make workers-restart` now
  restarts **production only**: it resolves each launchd label to its pid
  and SIGTERMs that pid — never a pkill command-line pattern. Root cause:
  dev tmux workers run byte-identical command lines (the env split lives
  in environment variables), so the old pattern restart took the staging
  lane down with production (observed live 2026-07-24, then repaired).
  New `make dev-worker-restart WORKER=<name>` restarts one dev worker;
  `make workers-status` shows both lanes with crashed dev panes called
  out. SIGTERM (not `kickstart -k`) is deliberate — it preserves the
  graceful drain.
- **pbook runs in prod** (owner-directed): `deploy/launchd/install.sh
  --with-pbook` installed `com.saxcapital.pbook-worker` (KeepAlive,
  `env=prod`), after a prod `pbook migrate`. `pbook-task-queue` has
  pollers for the first time, so forge's cross-queue ingestion calls are
  served instead of hanging. Doc drift corrected along the way: the pbook
  worker **does** auto-migrate at startup (verified from its log; the
  launchd README's "never auto-migrates" claim predated the T3.4
  scaffold), and `deploy/README.md`'s quick start referenced the retired
  `forge.env.example` (now the per-env `envs/prod.env.example`, T0.9).

## What to know before touching anything

1. **All seven workers are running the committed code** (prod: forge ×2,
   ocr, pbook via launchd; dev: forge/ocr/pbook in tmux). The T5.1
   restart precondition (no in-flight forge workflows, because old
   histories carry `evaluate_transition` events the new code cannot
   replay) was checked and satisfied before the prod restart — it is
   spent; no residual concern.
2. **Restart the right lane.** `make workers-restart` = prod only;
   `make dev-worker-restart WORKER=<name>` = one dev worker;
   `make workers-status` shows both. Restart prod only on a committed,
   gates-green tree (launchd runs the live working tree — that hazard is
   unchanged).
3. **Do not add logic to workflow result construction inline.** Terminal
   results route through the `step_logic` builders (which stamp
   `failure_kind` and wording); success results are plain model
   constructions. New pure decision logic belongs in `step_logic.py`
   with direct unit tests in `tests/test_step_logic.py`.
4. **Replay histories are regeneration-fresh** (2026-07-24). Any further
   deliberate workflow-logic change in Phase 5 needs another
   `make replay-histories` + Replayer re-verify; T5.2's step-block
   consolidation will need exactly that.
5. **The workflow-test transition vocabulary is transitional.** Scripted
   `transitions=[...]` sequences now drive the `validate_output` mock
   (sticky terminal token); the token names no longer match their effect
   at every attempt count. Deliberately left for T5.5's harness rebuild —
   do not add new `global` state or new token vocabularies in
   `tests/test_workflows.py`.
6. **Owner process preferences** (standing): planning in the main
   session; implementation dispatched to the `implementation-driver`
   agent (Opus) with small hard-bounded scopes; commits only on the
   owner's explicit word; mechanism-level explanations — separate
   act-now / act-later / no-action; challenge weak arguments, don't
   praise.
