## What to know before touching anything

1. **Prod is behind main.** Production runs `001247c` (pre-T5.3);
   deploying T5.3 is `make prod-deploy REF=006e599` followed by the
   restart that command drives. Until then the prod workers execute the
   pre-consolidation gather/dispatch — fine, the behavior is preserved
   by construction, but diagnosis of a prod incident must read the
   pinned checkout's code, not main's.
2. **Blocks conventions, extended (T5.2 → T5.3).** The pipeline body is
   `blocks/step.py`, the gather is `blocks/gather.py`, the typed
   dispatch is `blocks/dispatch.py`, the persisting host is
   `blocks/host.py`. Do not reintroduce inline copies in
   `workflows.py`. All activity timeout/retry presets come from
   `forge/presets.py` only — never mint a module-local timeout
   constant, and never change a preset value casually: they are
   recorded in ScheduleActivityTask command attributes, so a value
   change is a replay-breaking change.
3. **Child workflows are started by name.** The gather starts
   `"ForgeSubTaskWorkflow"` as a string (import-cycle avoidance). A
   rename must update the constant; `test_gather_block.py` pins the
   string against `__name__` so a silent drift fails fast.
4. **`failure_kind` is ten values.** `child_crashed` means the child
   *raised* instead of returning — its diagnosis lives in the child's
   own workflow history, not in the result. The parent-level gather
   failure still uses `sub_task_failed`.
5. **Replay posture.** Histories valid unregenerated through all of
   T5.3. `fan_out_batch` (+ two children) pins the parent gather and
   batch-planner sequences; the nested gather, exploration, and sanity
   arms are pinned by workflow tests only. T5.5's harness rebuild
   remains the natural place to add histories.
6. **Known flake, attributed, do not chase (~1 in 8):**
   `TestRecursiveFanOutNestedFailure::test_failure_propagates` scripts
   child outcomes by popping a module-global transitions list from the
   `validate_output` mock, but the two children run in parallel, so
   which child draws `FAILURE_TERMINAL` is a race while the assertion
   demands `gc2`. Reproduced at `83a2e07`'s parent — T5.3 did not
   introduce it. The fix is T5.5's `ScenarioState` closures; a rerun is
   the correct response to a one-off failure there, not a patch to the
   old harness.
7. **Owner process preferences** (standing): planning in the main
   session; implementation dispatched to the `implementation-driver`
   agent (Opus) with small hard-bounded scopes; commits only on the
   owner's explicit word; mechanism-level explanations — separate
   act-now / act-later / no-action; challenge weak arguments, don't
   praise.
