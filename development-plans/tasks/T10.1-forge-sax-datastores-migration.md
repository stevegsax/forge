## Problem

Forge's data layer predates the fleet datastore consolidation and
carries five defects the sax-datastores design retires:

1. **Accidental topology.** One PG16 instance
   (`pgvector/pgvector:pg16`, host port 5434 via a gitignored override;
   compose default 5433 because sibling projects squat 5432/5433)
   hosts production (`forge`, `pbook`), the dev lane (`forge_dev`), and
   Temporal's persistence (`temporal`, `temporal_visibility`) side by
   side — environments are separated by nothing but database name.
2. **The app role is the cluster superuser** (`POSTGRES_USER=forge`
   via the image entrypoint) — every worker connection could drop any
   database on the instance, including Temporal's.
3. **Dev is not topology-parity with prod.** pbook's dev store shares
   the `forge_dev` database (`deploy/local-stack/README.md:129`) while
   prod separates `forge` and `pbook` — so dev never rehearses the
   real two-database layout.
4. **Temporal's databases are never backed up.** The nightly leg
   (`backup-app-dbs.sh`, launchd `db-backup` agent) dumps forge+pbook
   only, and it is verified-once/unmonitored — plan-review finding A7,
   still open.
5. **Extension surface is repo-local** (initdb SQL) rather than
   parity-by-construction, the failure class that forced another
   product's search rewrite.

sax-datastores replaces this class fleet-wide: **environment =
instance** (dev postgres :5432 + MinIO; prod postgres :5442, no MinIO,
S3 only), **project = role + database** (`forge_dev`/`forge_test`/
`forge_prod` roles own same-named databases with PUBLIC connect
revoked, so a wrong-project or wrong-environment URL fails at auth),
one canonical PG17+rum+pgvector image everywhere, fail-closed
provisioning, and a nightly backup with a scheduled restore proof.

## Background and Detailed Explanation

sax-datastores is the shared datastore infrastructure repo for all SAX
projects: two podman compose stacks (dev and prod), an idempotent
provisioning script that creates per-project roles and databases with
the load-bearing `REVOKE CONNECT … FROM PUBLIC`, one canonical
postgres image, and backup/restore-check scripts. Forge is the largest
migrant: it brings four production databases, a running Temporal
server whose persistence lives in the instance being replaced, and
launchd-supervised workers that must find their databases up at boot.

What forge gets from the move, concretely: environment separation
that fails closed (a dev URL cannot reach prod — different port,
role absent); the superuser demotion (the forge role owns its own
databases and nothing else — extensions are pre-installed by
provisioning as superuser, so the Alembic chains'
`CREATE EXTENSION IF NOT EXISTS` lines become no-ops, which is the
compensation that makes demotion safe); dev/prod topology parity for
pbook for the first time; Temporal's databases inside the nightly
backup for the first time (databases are enumerated from the live
instance, so nothing rides on a manifest); and **A7's mechanism
closed** — `make prod-restore-check` proves the newest dumps restore
and fails loudly when they are older than 48h, which is the alarm for
a silently dead backup job that forge's current leg never had.

The three risky seams, named up front. **Temporal's persistence
moves**: the temporal server container stays in forge's deploy but
its databases relocate to the shared prod instance, which means a
planned downtime window (workers and temporal down, dump/restore,
repoint, up) and cross-compose networking — the temporal container
reaches the shared postgres through the rootless-podman gateway path,
which the stack's pg_hba RFC1918 rows already anticipate; the exact
mechanism is a Plan decision. **Boot ordering**: sax-datastores has no
boot wiring of its own, and forge's workers boot via launchd expecting
the database up — stack-boot ownership must be decided, not left to
`restart: unless-stopped`. **PG16 → PG17**: the move is dump/restore
per database plus `REINDEX` of pbook's vector indexes, rehearsed on
the dev stack before prod cutover.

What this task deliberately does not change: **zero workflow code**
(the committed replay histories must pass unregenerated — this is
infrastructure, and the one forge code change is the environment
guard's new coherence check); the D103 pinned-checkout deploy model;
and the loopback-only network posture — tailnet exposure of the dev
instance exists in the sax-datastores design but is deferred here, so
D99's no-remote-access stance is unchanged by this task. Retiring
forge's own backup leg amends shipped decisions (D102's backup design,
D99/D102's stack composition), so the change-set mints a new decision
record with banners per the Specification Changes policy.

## Scope

**Precondition (owner act, before the dev stack can bind :5432):**
stop the legacy annotation_manager containers currently holding
5432/5433/9000 (volumes kept; that product migrates later from its own
repo). The prod stack (:5442) conflicts with nothing and could go up
first, but the PG16→17 rehearsal wants the dev stack up before prod
cutover, so freeing the ports is step one. The alternative — dev stack
on a temporary port — is rejected: it forfeits the default-port-gravity
design and bakes a second port story into every consumer.

**sax-datastores side:**

- `pbook` and `forge_temporal` become first-class projects in
  `PROVISION_PROJECTS` with password lines in both stacks' `.env` and
  compose `environment:` blocks; `PROVISION_EXTRA_DBS` attaches the
  visibility database per env
  (`forge_temporal_<env>:forge_temporal_visibility_<env>`).
- Forge's dev bucket names join `MINIO_BUCKETS` (dev object data is
  re-derivable and is not migrated).

**forge side:**

- Profiles (`~/.config/forge/envs/{prod,dev}.env`) and the temporal
  server's environment repoint at the new roles/DBs/ports.
- `deploy/local-stack/` shrinks to Temporal(+UI) only: the postgres
  and minio services, the initdb SQL, and `FORGE_PG_PORT` are deleted;
  the temporal server points at the shared instance.
- Boot wiring: the shared stacks come up before the workers at boot
  (extend `start-stack.sh`/launchd or equivalent — Plan decision).
- The environment guard gains **URL-suffix coherence**: `FORGE_ENV`
  must match the connection URL's role/database suffix before any
  connect, exit 78 on mismatch — the database twin of
  `require_namespace_coherence`.
- Backup retirement: the launchd `db-backup` agent,
  `backup-app-dbs.sh`, and the `deploy/s3` lifecycle leg are retired
  in favor of the shared nightly + restore-check; new decision record
  - banners on D102 (and D99 as touched), same change-set.
- CI: the postgres-marker testcontainers image moves to the canonical
  `sax-postgres-rum:17` — a recorded deviation from the guide's
  shared-`_test`-database step (testcontainers is stronger isolation
  and matches the stack's own CI philosophy).
- Docs rewritten in the same change-set: DEPLOYMENT.md,
  deploy/local-stack/README.md, WORKERS.md, CLAUDE.md "Running the
  System".

**Prod cutover (runbook shape; detail in the Plan):** stacks up +
provisioned → pre-cutover backup of the old instance → in-flight
workflow check (the DEPLOYMENT.md pre-deploy procedure — prefer a
drained queue) → workers + temporal down → dump/restore ×4 (`forge`,
`pbook`, `temporal`, `temporal_visibility`) with exact row-count
verification (the D102 precedent) → `REINDEX` pbook's vector indexes →
repoint + up → verify pollers/tracker/dev-lane run → shared nightly +
restore-check proven → old instance's volume kept for a decided
retention window, then removed.

**Decisions to settle in the Plan (each recorded with rationale):**
temporal-to-shared-postgres networking mechanism; stack-boot
ownership; pbook first-class vs extra-DB-under-forge (lean:
first-class, per the guide — it is a product); dev-lane data (lean:
re-seed `forge_dev`/`pbook_dev` rather than dump/restore — dev data is
disposable); verify the deployed temporal server version supports
PG17 before cutover; the new decision record's scope (which decisions
it amends).

**Out of scope:** tailnet exposure of either instance; adopting
`product-ci.yml` (forge CI keeps its own workflow); splitting ocr into
its own database slug — **ocr rides the forge database by design**
(D102); this task documents that in the sax-datastores guide rather
than "fixing" it; the other products' migrations (their own repos).

## Acceptance Criteria

- [ ] `forge_prod`, `pbook_prod`, `forge_temporal_prod`,
  `forge_temporal_visibility_prod` live on the shared prod instance
  (:5442, canonical PG17 image), row counts verified exact against the
  source at cutover; pbook's vector indexes REINDEXed post-restore.
- [ ] Isolation proven at auth: `psql` as `forge_prod` reaches only
  its own databases; a non-forge role is refused at CONNECT by every
  forge database (and vice versa).
- [ ] Guard coherence enforced: a `FORGE_ENV` that contradicts the
  URL's role/database suffix exits 78 before any connect; unit-tested.
- [ ] All four prod pollers report `prod-<role>@<sha>` (no `-dirty`)
  after cutover; `ocr tracker-status` exits 0; one dev-lane document
  run completes end to end in `forge-dev`.
- [ ] Boot proof: after a host reboot, the shared stacks are up before
  the workers poll; no worker crash-loops on a down database.
- [ ] Backups: the shared nightly covers all four forge databases
  (enumerated live); `make prod-restore-check` passes once — the
  stack's own production-ready gate; forge's `db-backup` agent,
  `backup-app-dbs.sh`, and the `deploy/s3` leg are retired in the same
  change-set as the new decision record + banners on D102/D99.
- [ ] The forge repo carries no postgres/minio machinery: local-stack
  compose is Temporal(+UI) only; initdb SQL and `FORGE_PG_PORT` gone;
  CI's testcontainers run the canonical image.
- [ ] Zero workflow-code changes: committed replay histories pass
  unregenerated; `make gates` green.
- [ ] Docs truth: DEPLOYMENT.md, deploy/local-stack/README.md,
  WORKERS.md, and CLAUDE.md "Running the System" describe the new
  layout in the same change-set.
