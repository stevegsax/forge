## Problem

OCR submission is peaky: mostly idle, but a 1,000-document burst is
ordinary, and submission is one Mistral batch per chunk — so a burst means
≥1,000 concurrent `OcrStoreWorkflow` waiters. The shipped T4.2 transport has
each waiter self-poll (`BackoffSchedule`: 300s for the first hour, doubling
to an 1800s cap). Correct, but: worst-case completion detection is ~30
minutes in the tail; every waiter burns ~11 history events per poll cycle
for hours; a burst produces thousands of no-op activity executions; and
provider request volume scales with waiter count.

Mistral's batch **list** endpoint changes the economics for the Mistral case
only: one request returns a page of job statuses (status-only by
construction — verified 2026-07-19: `output_file` is a file ID; no content
travels in status responses), with server-side `created_after` filtering and
`page_size` 100. One sweep covers N batches — amortization is real and grows
with burst size. This does **not** revisit D88/D100 for forge: Anthropic
polling is per-batch and forge's ~30-waiter worst case stands.

## Design (settled 2026-07-21, owner-adjudicated)

### Tracker

`OcrBatchTrackerWorkflow` — a **stateless** workflow on `ocr-task-queue`,
fired by a Temporal Schedule every **120s** with the T1.3 guard pattern
(overlap=SKIP + execution timeout; reintroduce the `_ensure_schedule` shape
in ocr's worker startup). Each firing is one short run:

1. **DB check (activity):** live jobs = non-terminal `ocr_job_status` rows
   (`submitted`/`processing`), LEFT JOINed to the read-only `batch_jobs`
   mirror on `request_id` for `batch_id` (rows with no ledger row are
   logged and skipped); exclude rows older than `BATCH_WAIT_CEILING` + 1h
   (they fail at their own ceiling). **No live jobs → write heartbeat and
   return — zero Mistral calls.** This implements "poll only when there are
   live jobs" as a cheap no-op, with no start/stop orchestration.
2. **List sweep (activity):** `MistralOcr.list_batch_statuses(created_after=now − ceiling − 1h)`
   (new platform method wrapping `batch.jobs.list_async`; pages until
   exhausted; maps provider statuses through the existing
   `_MISTRAL_JOB_STATUS` table; never downloads). Do **not** filter by
   remote status — a remotely-finished job is exactly what the sweep must
   report.
3. **Broadcast:** for each live job whose `batch_id` appears in the sweep,
   signal its store workflow (deterministic id `ocr-store-{document_id}`)
   with a status hint — a small frozen ocr-internal model
   (`batch_id`, normalized state). Send the **latest status
   unconditionally** (no change-detection, no per-job memory — the
   receivers' state machines absorb duplicates). A signal that bounces
   (workflow closed/not found) is logged and the cycle continues — expected
   for the one-cycle overlap after a job completes.
4. **Heartbeat (activity):** upsert the single-row `ocr_tracker_heartbeat`
   table (last_run_at + cycle counters; new table on ocr's own Alembic
   chain). A stale heartbeat is a **system** alert; tasks do not monitor
   their infrastructure.

Statelessness properties (these are the point — preserve them): the tracker
holds no memory between runs, so it is restart-safe mid-cycle, safe under
concurrent/duplicate runs (extra signals are absorbed downstream), and each
Schedule-fired run's history is discarded on completion — no
continue-as-new bookkeeping exists.

### Store child

`OcrStoreWorkflow` converts from the poll loop to a **signal-wait state
machine** with **one path** (owner-adjudicated: no per-task provider-poll
fallback — tracker failure is latency-only, bounded by the existing 25h
ceiling, and observable via the heartbeat):

- Signal handler (name must NOT resemble the retired `batch_result_received`)
  receives status hints and drives a state machine. Transition table:
  `pending → in_progress | any-terminal` ✓; `in_progress → any-terminal` ✓;
  same-state → no-op; any backward or terminal→different-terminal move →
  log warning, ignore. Terminal = ended/failed/expired/canceled.
- Wait: `workflow.wait_condition(state is terminal, timeout=BATCH_WAIT_CEILING)`.
  Ceiling expiry → today's MISSING path unchanged (upsert failed,
  `PersistBatchOutcome(MISSING)`, non-retryable ApplicationError — T1.6b
  symmetry intact). `ended` → the existing `fetch_and_store_ocr_result`
  (unchanged) → `PersistBatchOutcome(ENDED)`. `failed`/`expired`/`canceled`
  → today's terminal-failure paths (FAILED/EXPIRED).
- The hint is never authoritative: the fetch is keyed by the child's own
  `batch_id`/`request_id`, so a misrouted or stale hint at worst triggers a
  harmless early fetch attempt. This is the sanctioned signal pattern
  (hints not payloads, state-machine receivers, bounded waits); the
  payload-bearing, correlation-dependent, unbounded-wait pattern retired by
  T4.1/T4.2 stays retired.
- Timeout tree unchanged: child execution timeout stays ceiling + 1h;
  parent unchanged. No formula changes — do not re-derive.

  `MistralOcr.get_batch_status` **stays** (coherent single-batch primitive

## Acceptance Criteria

- [ ] Idle cycle: no live jobs → heartbeat written, **zero** provider calls
      (fake asserts list never invoked).
- [ ] Burst cycle: live jobs → one paged sweep → hints to exactly the live
      set; completed-row jobs not signaled; a bounced signal (closed
      workflow) is logged and the remaining broadcasts still deliver.
- [ ] State machine: duplicate hint → no-op; forbidden transition (e.g.
      failed→ended) → logged + ignored; double-SUCCESS delivery fetches
      exactly once; a hint arriving before the wait begins is still
      honored.
- [ ] Concurrent trackers: two overlapping tracker runs against the same
      state cause no double-fetch and no state damage.
- [ ] Store child: ended → fetch+store+ENDED; failed/expired → terminal
      paths; **no hint at all → 25h ceiling → MISSING** with run record and
      cleanup (T1.6b symmetry preserved; the converted ceiling test).
- [ ] `list_batch_statuses` pages a multi-page fake correctly, maps every
      provider status, performs no downloads.
- [ ] `BackoffSchedule` and `ocr_batch_status` deleted workspace-wide;
      `wait_batch_ended`/`FixedInterval` untouched (forge suite + replay
      histories green **unregenerated**).
- [ ] D101 + D100 banner + rule-8 addendum + signal-claims doc sweep land
      in this change-set; markdownlint clean.
- [ ] `make gates` EXIT=0 (all four suites; mypy ×4; import-linter).

## Plan

*Written 2026-07-22 (pre-implementation review), refining the suggested
staging. Every schema/code claim in the Design was verified against HEAD
(`1dcbdd1`); the resolutions below close the implementation choices the
spec left open. Verified as-specced: `ocr_job_status` has
`document_id` but no `batch_id` (the LEFT JOIN to the `batch_jobs` mirror —
which has nullable `batch_id` — is required, not optional);
`OcrSubmitWorkflow` persists the real `batch_id` in
`PersistBatchSubmission` before starting each child, so ledger rows for
live jobs normally carry it; store-child ids are `ocr-store-{document_id}`
(one per chunk document, 1:1 with `ocr_job_status` rows);
`OcrProcessingStatus` non-terminals are exactly `submitted`/`processing`;
`BackoffSchedule`'s only consumer is `workflow_store.py` (forge uses
`FixedInterval`); `FakeMistralOcr` mirrors the real surface and records
calls, so the "list never invoked" idle assertion is natural.*

### Resolutions

1. **Broadcast mechanism — workflow-side external signals.** The tracker
   signals each live child from workflow code:
   `workflow.get_external_workflow_handle(f"ocr-store-{document_id}").signal(...)`,
   each awaited inside its own try/except (bounce → `workflow.logger.warning`,
   continue). No Temporal client enters the activity layer; bounce
   absorption is per-handle. History bound: ~2–3 events per signal command,
   so a 1,000-job burst run is a few thousand events — discarded when the
   run completes (statelessness property preserved).
2. **Signal name and hint model.** Signal `ocr_status_hint`; payload
   `OcrStatusHint(batch_id: str, state: BatchPollStatus)`, frozen, in
   `ocr.models`. `BatchPollStatus` is exactly the transition-table
   vocabulary, and `sax_platform.ocr` is sandbox-importable by design (its
   SDK imports are lazy — module docstring).
3. **Store-child state machine.** Initial state `PENDING` (set before any
   `await` so a hint buffered at start is honored). Handler: validate
   `hint.batch_id == input.batch_id` (mismatch → warn + ignore), then apply
   the transition table onto `self._state`. Run body:
   `workflow.wait_condition(lambda: self._state in _TERMINAL, timeout=BATCH_WAIT_CEILING)`;
   `TimeoutError` → today's MISSING path verbatim; otherwise dispatch on
   `self._state` exactly where `wait_batch_ended`'s outcome is dispatched
   today (ended → fetch; failed/expired/canceled → terminal paths). `_fail`
   / `_mark_failed` / the fetch call are untouched.
4. **`_ensure_schedule` recovery.** The T1.3 shape (idempotent
   create-or-update, `overlap=SKIP`, `execution_timeout`) was deleted by
   T4.1; recover it from `git show 4470f97^:src/forge/worker.py` (and its
   test in that commit's `tests/test_worker.py`). Port into `ocr/worker.py`:
   schedule id `ocr-batch-tracker`, workflow `OcrBatchTrackerWorkflow`,
   `OCR_TASK_QUEUE`, interval **120s**, execution timeout 10 min (the SKIP
   policy owns cadence; the timeout only guards a wedged run).
5. **Tracker activities live on `OcrStoreActivities`** (it already holds
   the engine + Mistral capability; no new class): `list_live_ocr_jobs`
   (the join; exclusion window computed activity-side with real wall-clock
   `now`) returning a typed list of `(request_id, document_id, batch_id)`
   rows; `sweep_batch_statuses` (wraps the new
   `MistralOcr.list_batch_statuses`; `created_after` computed
   activity-side) returning `dict[batch_id, BatchPollStatus]`-shaped typed
   output; `write_tracker_heartbeat`. The workflow itself computes no
   times and reads no clocks beyond `workflow.logger`.
6. **Heartbeat table.** `ocr_tracker_heartbeat` — `id` TEXT PK (constant
   `"tracker"`), `last_run_at` UTCDateTime, `live_jobs` INT, `hints_sent`
   INT, `cycles` INT; migration `002_tracker_heartbeat` on the ocr Alembic
   chain; plain upsert in `ocr.store`.
7. **Deploy caveat (not in the spec text).** ST2 is a breaking
   workflow-logic change for **in-flight** `OcrStoreWorkflow` runs — the
   poll loop their histories recorded no longer exists, so they will fail
   replay on the new worker. Deploy with zero live ocr store workflows
   (drain, or terminate + resubmit). Single-operator local deployment
   (D99) makes this a drain step, not a migration.
8. **Unconditional-hint volume is bounded and acceptable.** Worst case
   (25h job, 120s cadence) ≈ 750 hints ≈ low-thousands of receiver
   history events — far under Temporal's limits and comparable to the
   poll loop it replaces. The wins are provider request volume (one paged
   sweep per 120s regardless of burst size) and ≤120s completion
   detection, per the Problem statement.
