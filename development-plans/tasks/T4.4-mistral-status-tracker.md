## Problem

OCR submission is peaky: mostly idle, but a 1,000-document burst is
ordinary, and submission is one Mistral batch per chunk — so a burst means
≥1,000 concurrent `OcrStoreWorkflow` waiters. The shipped T4.2 transport has
each waiter self-poll (`BackoffSchedule`: 300s for the first hour, doubling
to an 1800s cap). Correct, but: worst-case completion detection is ~30
minutes in the tail; every waiter burns ~11 history events per poll cycle
for hours; a burst produces thousands of no-op activity executions; and
provider request volume scales with waiter count.

Mistral's batch **list** endpoint changes the economics for the Mistral case
only: one request returns a page of job statuses (status-only by
construction — verified 2026-07-19: `output_file` is a file ID; no content
travels in status responses), with server-side `created_after` filtering and
`page_size` 100. One sweep covers N batches — amortization is real and grows
with burst size. This does **not** revisit D88/D100 for forge: Anthropic
polling is per-batch and forge's ~30-waiter worst case stands.

## Background and Detailed Explanation

Phase 4 spent two tasks deleting signals. T4.1 tore out forge's shared
poller and every signal handler; T4.2's headline acceptance criterion was
that `rg "@workflow.signal"` returns zero hits across the whole platform.
This task reintroduces one signal. Read as a diff, that looks like churn —
delete the thing, then add it back — so the first job of this explanation
is to show why it is principled: the signal that returns is a fundamentally
different, deliberately constrained shape, and the dangerous one Phase 4
retired stays retired.

The reason the answer differs for ocr comes down to economics specific to
the Mistral case. OCR submission is peaky: mostly idle, but a
1,000-document burst is ordinary, and because ocr submits one Mistral batch
per chunk, a burst means on the order of 1,000 concurrent
`OcrStoreWorkflow` waiters. Under T4.2's shipped design each of those
waiters polls Mistral for itself. That is correct but wasteful at burst
scale — thousands of no-op activity executions, ~11 Temporal history events
per waiter per poll cycle accumulating for hours, worst-case
completion-detection latency around 30 minutes in the tail, and provider
request volume that scales with the waiter count. Mistral's batch *list*
endpoint changes the arithmetic: a single status-only request (its
`output_file` is a pointer, so no result content travels in it) returns a
page covering every recent batch, so one sweep amortizes across N in-flight
jobs and the saving *grows* with burst size. This is the crucial scoping
point — Anthropic exposes no equivalent amortizing endpoint, forge's
polling stays per-batch, and its ~30-waiter worst case is unchanged. **T4.4
is emphatically not a reversal of D88; forge's transport is not touched at
all.**

The design is a stateless `OcrBatchTrackerWorkflow` on a 120-second
Temporal Schedule (overlap=SKIP, installed and reconciled at worker startup
by a reintroduced `_ensure_schedule` guard). Each firing is one short run:
check the DB for live jobs and — the cheap common case — if there are none,
write a heartbeat and return having made **zero** Mistral calls; otherwise
sweep the Mistral list endpoint once (paged), broadcast an
`ocr_status_hint` signal to each live job's store workflow, and upsert a
heartbeat. That idle short-circuit is quietly important: it implements
"poll only when there is work to do" as a plain no-op, with no start/stop
orchestration to get wrong. The store children, meanwhile, converted from
poll loops into signal-wait state machines that advance on the hints.

**Three properties are what make the returning signal safe rather than a
regression, and they map one-for-one onto the failures Phase 4 retired.**
First, hints are never payloads and never authoritative: the actual result
fetch stays keyed by the child's *own* `batch_id`/`request_id`, so a
misrouted, stale, or duplicated hint at worst triggers a harmless early
fetch attempt — whereas the retired signals *carried the result and its
correlation*, making a misrouted one silent data corruption. Second,
receivers are bounded state machines: a pure `next_state` table absorbs
duplicate and out-of-order hints and ignores forbidden transitions, and the
child waits on `wait_condition` under the unchanged 25-hour ceiling —
whereas the retired pattern waited unboundedly on a signal that might never
come. Third, the tracker holds no state between runs, so it is restart-safe
mid-cycle, harmless under concurrent or duplicate runs (extra hints are
absorbed downstream), and needs no continue-as-new bookkeeping because each
run's history is discarded on completion.

Those three properties collapse the blast radius of tracker failure to
*bounded latency*: if the tracker dies, waiters simply wait, capped by the
25-hour ceiling and visible through the heartbeat row (whose staleness is a
system alert, not task state). That is the reasoning behind the one design
choice most likely to look like an omission — there is deliberately **no**
per-task provider-poll fallback in the store child. The owner adjudicated
it directly: a fallback would reintroduce exactly the per-waiter polling
volume the tracker exists to remove, all to guard against a failure whose
worst case is only that results arrive slower. The retirements followed
from the same logic: `BackoffSchedule` and ocr's `ocr_batch_status`
activity lost their only consumers and were deleted, while
`MistralOcr.get_batch_status` (a coherent single-batch primitive with
diagnostic value) and forge's `FixedInterval` loop stayed — and forge's
committed replay histories passed unregenerated, the concrete proof forge's
transport was genuinely left alone.

The staged build surfaced several details worth keeping. The exception a
broadcast raises when its target workflow has already closed was pinned
empirically against the installed SDK — an `ApplicationError` of type
`ExternalWorkflowExecutionNotFound` — and is caught, logged, and excluded
from the heartbeat's `hints_sent` count, since a one-cycle overlap after a
job completes is expected, not an error. The heartbeat upsert increments
`cycles_total` in SQL on the conflict path rather than in Python, so two
overlapping tracker runs cannot lose a count. And the tracker signals the
`workflow_id` recorded in the `batch_jobs` ledger (obtained from a LEFT
JOIN) rather than reconstructing the deterministic `ocr-store-{document_id}`
string — the same value, taken from one source of truth instead of rebuilt.
The whole change landed against a new **D101** recording the amortization
argument, the sanctioned hint-signal pattern, the tracker's statelessness,
and the no-fallback adjudication, with an amendment banner on the D100
sentence it supersedes.

## Design (settled 2026-07-21, owner-adjudicated)

### Tracker

`OcrBatchTrackerWorkflow` — a **stateless** workflow on `ocr-task-queue`,
fired by a Temporal Schedule every **120s** with the T1.3 guard pattern
(overlap=SKIP + execution timeout; reintroduce the `_ensure_schedule` shape
in ocr's worker startup). Each firing is one short run:

1. **DB check (activity):** live jobs = non-terminal `ocr_job_status` rows
   (`submitted`/`processing`), LEFT JOINed to the read-only `batch_jobs`
   mirror on `request_id` for `batch_id` (rows with no ledger row are
   logged and skipped); exclude rows older than `BATCH_WAIT_CEILING` + 1h
   (they fail at their own ceiling). **No live jobs → write heartbeat and
   return — zero Mistral calls.** This implements "poll only when there are
   live jobs" as a cheap no-op, with no start/stop orchestration.
2. **List sweep (activity):** `MistralOcr.list_batch_statuses(created_after=now − ceiling − 1h)`
   (new platform method wrapping `batch.jobs.list_async`; pages until
   exhausted; maps provider statuses through the existing
   `_MISTRAL_JOB_STATUS` table; never downloads). Do **not** filter by
   remote status — a remotely-finished job is exactly what the sweep must
   report.
3. **Broadcast:** for each live job whose `batch_id` appears in the sweep,
   signal its store workflow (deterministic id `ocr-store-{document_id}`)
   with a status hint — a small frozen ocr-internal model
   (`batch_id`, normalized state). Send the **latest status
   unconditionally** (no change-detection, no per-job memory — the
   receivers' state machines absorb duplicates). A signal that bounces
   (workflow closed/not found) is logged and the cycle continues — expected
   for the one-cycle overlap after a job completes.
4. **Heartbeat (activity):** upsert the single-row `ocr_tracker_heartbeat`
   table (last_run_at + cycle counters; new table on ocr's own Alembic
   chain). A stale heartbeat is a **system** alert; tasks do not monitor
   their infrastructure.

Statelessness properties (these are the point — preserve them): the tracker
holds no memory between runs, so it is restart-safe mid-cycle, safe under
concurrent/duplicate runs (extra signals are absorbed downstream), and each
Schedule-fired run's history is discarded on completion — no
continue-as-new bookkeeping exists.

### Store child

`OcrStoreWorkflow` converts from the poll loop to a **signal-wait state
machine** with **one path** (owner-adjudicated: no per-task provider-poll
fallback — tracker failure is latency-only, bounded by the existing 25h
ceiling, and observable via the heartbeat):

- Signal handler (name must NOT resemble the retired `batch_result_received`)
  receives status hints and drives a state machine. Transition table:
  `pending → in_progress | any-terminal` ✓; `in_progress → any-terminal` ✓;
  same-state → no-op; any backward or terminal→different-terminal move →
  log warning, ignore. Terminal = ended/failed/expired/canceled.
- Wait: `workflow.wait_condition(state is terminal, timeout=BATCH_WAIT_CEILING)`.
  Ceiling expiry → today's MISSING path unchanged (upsert failed,
  `PersistBatchOutcome(MISSING)`, non-retryable ApplicationError — T1.6b
  symmetry intact). `ended` → the existing `fetch_and_store_ocr_result`
  (unchanged) → `PersistBatchOutcome(ENDED)`. `failed`/`expired`/`canceled`
  → today's terminal-failure paths (FAILED/EXPIRED).
- The hint is never authoritative: the fetch is keyed by the child's own
  `batch_id`/`request_id`, so a misrouted or stale hint at worst triggers a
  harmless early fetch attempt. This is the sanctioned signal pattern
  (hints not payloads, state-machine receivers, bounded waits); the
  payload-bearing, correlation-dependent, unbounded-wait pattern retired by
  T4.1/T4.2 stays retired.
- Timeout tree unchanged: child execution timeout stays ceiling + 1h;
  parent unchanged. No formula changes — do not re-derive.

### Retirements and record

  their only consumers — **delete both** (no-live-users rule).
  `wait_batch_ended` + `FixedInterval` stay (forge's loop).
  `MistralOcr.get_batch_status` **stays** (coherent single-batch primitive
  with tests; diagnostic value; one-line rationale in the D-entry).
- Same-change-set decision record (PROCESS.md "Specification Changes"):

## Acceptance Criteria

- [x] Idle cycle: no live jobs → heartbeat written, **zero** provider calls
      (fake asserts list never invoked).
- [x] Burst cycle: live jobs → one paged sweep → hints to exactly the live
      set; completed-row jobs not signaled; a bounced signal (closed
      workflow) is logged and the remaining broadcasts still deliver.
- [x] State machine: duplicate hint → no-op; forbidden transition (e.g.
      failed→ended) → logged + ignored; double-SUCCESS delivery fetches
      exactly once; a hint arriving before the wait begins is still
      honored.

- [x] Store child: ended → fetch+store+ENDED; failed/expired → terminal

### Design details fixed by this plan (spec-compatible choices)

- Signal name `ocr_status_hint`; hint model `OcrStatusHint` (frozen, in
  `ocr.models`): `batch_id: str`, `state: str` over the normalized
  `BatchPollStatus` vocabulary (`pending` / `in_progress` / `ended` /
  `failed` / `canceled` / `expired`). A hint whose `batch_id` differs from
  the child's own is logged and ignored.
- Store child: `@workflow.init` constructor takes `OcrStoreInput` so hints
  arriving before the wait begins are honored; internal state starts
  `pending`; transitions via a pure module-level `next_state` function
  implementing the spec table; terminal = {ended, failed, expired,
  canceled}; `canceled` keeps today's FAILED terminal handling.
- `MistralOcr.list_batch_statuses(*, created_after) -> dict[str, BatchPollStatus]`
  pages `batch.jobs.list_async` to exhaustion (page_size 100), maps through
  `_MISTRAL_JOB_STATUS` (unknown → IN_PROGRESS, matching
  `get_batch_status`), no remote-status filter, never downloads.
- The sweep activity computes `created_after = now − (BATCH_WAIT_CEILING + 1h)`
  itself (activities may read real time); the DB-check activity applies the
  same cutoff to `ocr_job_status.created_at`.
- Heartbeat table `ocr_tracker_heartbeat` (migration 002): single row
  (`id` int PK, constant 1), `last_run_at`, `live_jobs`, `hints_sent`,
  `cycles_total`; upserted every cycle, idle cycles included.
- Schedule: id `ocr-batch-tracker`, interval 120s, overlap=SKIP,
  execution_timeout 5 min (tracker activities are short; a wedged run skips
  ≤2 cycles), action on `OCR_TASK_QUEUE`, ensured at ocr worker startup by
  an ocr-local `_ensure_schedule` reintroduced from the T1.3 prior art.
