## Background and Detailed Explanation

This is the migration's closing gate, and it does two jobs. First, it
cleans up after Phases 5–6: those phases rewrote the internals behind
several CLI commands, leaving CLI tests that patch implementation paths
*by string*. A string patch like `patch("forge.cli._foo")` keeps passing
green even after `_foo` is moved or deleted — the test has quietly
stopped testing anything. Those are replaced with injected fakes, which
a refactor cannot silently defeat. Second, it is the single release gate:
every package proven green — 85% coverage, mypy strict, ruff,
import-linter — through one command from the workspace root, after which
the monorepo is tagged **v1.0**. That tag is the terminal act of the
migration, and a standing rule forbids applying it any earlier.

**The sweep inventory (2026-07-08).** This file is also the designated
home for every minor finding the review cycles deferred as "sweep
fodder." The point of writing the inventory *here* is that otherwise
these items live only in archived reports that nothing in Phase 8 would
surface — they would be dropped silently. So the acceptance rule is
explicit: each item is verified fixed, deleted, or waived with a reason
— no silent drops. Each is *verify-then-fix-or-waive*, never assumed
still live, since an earlier phase may already have resolved it. (The
line pointers reference pre-migration HEAD `927ac75`; after T2.1 the
paths move under `apps/forge/`, so items are found by symbol name, not
line.)

The phase-independent items were extracted into standalone Phase 0 tasks
(T0.1–T0.4) so they need not wait behind the whole migration; this task's
closing check just confirms they landed. What remains is phase-linked — a
duplicated `DEFAULT_TEMPORAL_ADDRESS` (should be absorbed by T3.4's
plumbing consolidation), the four-times-repeated providers.py subprocess
pattern (extract a helper only if the providers survive Phase 7 intact),
`planner.py`'s import of three private names from `activities/context.py`
(likely moot after T7.5), a mypy config that lists sub-flags `strict`
already implies and leaves the test suite untype-checked, and ingestion
workflow IDs minted from `int(time.time())` that collide at second
resolution (moot if T6.4 deleted the command) — plus stale docs
artifacts (`diataxis/`, `sample-flows/`, `docs/llm-examples/`) to
regenerate or archive. Each carries its own "verify" because the mooting
deletion may already have happened.

**The waivers** record items deliberately not fixed, each moot or low
interim risk — the playbook-subsystem items (moot at T6.7), the
extraction-subsystem error-class gaps (moot at T1.8), missing store
indexes, the test-strategy doc mismatch (T5.5 makes it true again), XDG
placement of the store, an undeclared `mistralai` whose only importer is
a stack T1.1 deletes, and a "coverage inflation" claim that measurement
*refuted*: the ~1,400 dead LOC sit at 0% and therefore deflate the
aggregate, and the gate clears despite them. One more docs casualty is
noted for disposition here: `batch_processing.feature` (and a line of
`cli.feature`) describes the deleted shared multi-provider signal poller
— dead since T4.1/T4.2 left zero `@workflow.signal` platform-wide — with
specific scenarios flagged verified-false and the still-true survivors
called out for any rewrite.

Done means `just check` green from the workspace root, every
sweep-inventory item resolved or waived on the record, T0.1–T0.4
confirmed complete, and `rg` confirming no dangling references to files
the sweep moved or deleted.
