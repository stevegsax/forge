## Problem

pbook is workflow-as-RPC: 16 one-activity wrapper workflows plus 4 other
RPC workflows mean every CLI command requires a running worker — `pbook
search` is uvx + a Temporal connect + 4 sequential activities for what is
one embed call, one SQL statement, and pure ranking. CRUD, retrieval, and
export should be plain sync library functions, with Temporal reserved for
the two workflows that actually need durable execution (Phase 6's
ingest/curation).

## Background and Detailed Explanation

T6.1 is about pbook no longer using a durable-workflow engine as a
phone line.

**The problem.** Temporal exists to run long, restartable,
failure-surviving processes — an ingestion that spans a 24-hour batch,
a weekly sweep. pbook currently uses it for everything: 20 of its
workflows are "workflow-as-RPC," where the workflow does nothing
durable — it makes one activity call and returns the answer. `pbook
search`, for example, spins up a `uvx` process, opens a Temporal
connection, and runs four activities in sequence just to compute one
embedding, run one SQL query, and rank the rows in memory — all pure,
fast, in-process work. The durability machinery buys nothing here and
taxes every command: nothing runs without a live worker.

**The fix.** Split the two concerns. A new `pbook/service.py` holds
plain synchronous library functions built over a frozen
`AppContext(settings, engine, embedder|None)` — CRUD, retrieval, and
export become ordinary function calls with no Temporal in the path. The
16 wrapper workflows and 4 other RPC workflows are deleted outright
(verified: nothing outside pbook references them), and the CLI calls
the service functions directly. Temporal is kept only for the two
workflows in this phase that genuinely need durable execution — ingest
and weekly curation (T6.4). Characterization tests come first: the
exact `--json` envelope every CLI command emits is recorded as a golden
before the refactor, so the rewrite is provably output-preserving.

**The buried gotcha:** with the store now optional, a missing
`PBOOK_DATABASE_URL` must degrade cleanly — it raises `ConfigError` and
surfaces as a `db_disabled` envelope, not a stack trace (the pbook
worker's store was silently disabled before T0.9 set that variable for
the first time).

**How you'll know it's done:** the golden envelopes stay green through
the refactor, `pbook search` runs with no worker at all, and p50
latency is under a second on the dev DB.

## Scope

- Record golden `--json` envelope characterization tests for every CLI
  command **first**.
- Build `pbook/service.py` sync functions over frozen
  `AppContext(settings, engine, embedder|None)`.
- Delete the 16 cli_ops wrapper workflows + 4 other RPC workflows
  (verified: nothing outside pbook references them).
- CLI rewired to direct service calls.
- Missing `PBOOK_DATABASE_URL` → `ConfigError` → `db_disabled` envelope.

## Acceptance Criteria

- [ ] Golden envelope tests stay green through the refactor.
- [ ] `pbook search` needs no worker.
- [ ] p50 < 1s on the dev DB.
