## Problem

1. **Defaults inversion.** `_submit_and_wait` defaults `sync_mode=True`
   (`cli.py:365`) while the CLI flag defaults to batch mode
   (`--sync/--no-sync` default False, `cli.py:614-619`). Any future
   caller relying on the helper's defaults silently gets sync mode,
   inverting the batch-first default the whole system is built on.
2. **Helper duplication.** `_submit_and_wait` (`cli.py:350-396`) and
   `_submit_no_wait` (`cli.py:399-446`) are ~45 identical lines differing
   only in `execute_workflow` vs `start_workflow`, and both re-declare 14
   keyword parameters mirroring `ForgeTaskInput` field-for-field —
   guaranteed drift.
3. **Double discovery.** `eval_planner` runs `discover_eval_cases` twice
   per invocation (`cli.py:1639` and again inside `_run_eval` at
   `cli.py:1553`) — duplicate directory I/O and a window for the case
   list to change between the count check and the run.

## Background and Detailed Explanation

Three hygiene problems in the CLI's submission helpers, the first a
genuine trap. `_submit_and_wait` defaulted its `sync_mode` parameter to
`True` while the CLI flag defaulted to batch mode — so any future
caller that leaned on the helper's default would silently get
synchronous execution, inverting the batch-first default the whole
system rests on. The other two were drift risks: `_submit_and_wait` and
`_submit_no_wait` were ~45 near-identical lines that each re-declared
fourteen keyword parameters mirroring `ForgeTaskInput` field-for-field,
and `eval_planner` ran `discover_eval_cases` twice per invocation
(duplicate directory I/O plus a window for the case list to change
between the count and the run).

The fix collapsed both helpers into one `_submit(task_input:
ForgeTaskInput, temporal_address, *, wait: bool)` — `execute_workflow`
versus `start_workflow` branches on `wait`, with two `@overload`s
pinning `wait=True → TaskResult` and `wait=False → str`. Passing the
whole `ForgeTaskInput` deleted the fourteen-field mirror and, with it,
the inversion: there is no longer a `sync_mode` parameter to default
wrongly — it rides inside `ForgeTaskInput`, whose own default is `False`
(batch), matching the flag. `eval_planner` now discovers cases once and
threads the list into `_run_eval`. The change rippled through ~24 CLI
tests that had patched the old helpers and read per-call kwargs; all
were repointed to read fields off the single positional
`ForgeTaskInput`.

## Scope

- Align the helper defaults with the CLI's batch-first default (or make
  `sync_mode` a required parameter so no default exists to invert).
- Merge the two submit helpers behind one function with a wait flag;
  pass `ForgeTaskInput` (or a single kwargs dict) instead of 14 mirrored
  parameters.
- Discover eval cases once; pass the list through.

Coordinate note: Phases 5–6 change which CLI commands exist
(ingest/playbooks leave), but `run`/`eval-planner` and the submit helpers
survive — these fixes are not throwaway work.

## Plan

Landed alongside T0.1 and T0.6 (shared `cli.py`).

1. **Merge the two submit helpers.** Replace `_submit_and_wait` /
   `_submit_no_wait` (each re-declaring the 14-field `ForgeTaskInput` mirror)
   with a single `_submit(task_input: ForgeTaskInput, temporal_address, *,
   wait: bool)`. Construct the `ForgeTaskInput` in `run` and pass it in;
   `execute_workflow` vs `start_workflow` branches on `wait`. Two `@overload`s
   give `wait=True → TaskResult`, `wait=False → str`. Update the two call
   sites in `run`.
2. **Defaults inversion — dissolved by the merge.** The merged helper has no
   `sync_mode` parameter (it rides inside `ForgeTaskInput`, default `False` =
   batch), so there is no helper-level default to invert. Satisfies the AC's
   "sync_mode has no default" branch.
3. **Double discovery.** Change `_run_eval` to take `cases: list[EvalCase]`
   instead of `corpus_dir`; `eval_planner` discovers once and passes the list.
4. **Tests.** Repoint every `@patch("forge.cli._submit_and_wait"/
   "_submit_no_wait")` to `_submit`; assertions that read the old per-call
   kwargs now read `task_input.<field>` (and `task_input.task` for the
   `TaskDefinition`).

## Development Notes

**2026-07-18 — landed (with T0.1, T0.6).**

- *Merged helper signature.*
  `async def _submit(task_input: ForgeTaskInput, temporal_address: str, *,
  wait: bool) -> TaskResult | str`, with two `@overload`s pinning
  `wait=True → TaskResult` and `wait=False → str`. `run` constructs the
  `ForgeTaskInput` (applying `model_routing or ModelConfig()`, exactly as the

  literals so the overloads resolve precisely. The 14-parameter mirror that
  duplicated `ForgeTaskInput` field-for-field is deleted.

  as one `ForgeTaskInput`, the helper has no `sync_mode` parameter at all — the
  `sync_mode=True` default that inverted the CLI's batch-first `--no-sync`
  default no longer exists. `ForgeTaskInput.sync_mode` itself defaults to
  `False` (batch), matching the flag.
- *Test blast radius.* ~24 `test_cli.py` tests patched `_submit_and_wait` /
  `_submit_no_wait` and read per-call kwargs. All repointed to `_submit`;
  assertions that were `call_kwargs[1]["plan"]` etc. now read the fields off
  the single positional `ForgeTaskInput` (`task_input.plan`,
  `task_input.task.validation…`).
