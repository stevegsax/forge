## Problem

`Plan` enforces only `steps: min_length=1` (`models.py:244-249`). Duplicate
step IDs, duplicate sub-task IDs, overlapping fan-out target files,
cyclic/forward step references, and absolute paths are all constructible
and flow straight into execution, where overlapping targets trigger
conflict-resolution LLM calls a free deterministic check would have
prevented. The checks already exist (`eval/deterministic.py:52-350`) but
run only in the eval harness; the sole acceptance gate on planner output is
`Plan.model_validate` (`planner.py:221`). The existing checks also iterate
exactly one nesting level, so nested-sub-task violations are invisible even
to eval.

## Background and Detailed Explanation

T5.6 made forge check a plan for structural defects *before* it executes,
using validation logic the codebase already had but never ran at the
moment it mattered.

**The problem.** The only gate on planner output was
`Plan.model_validate`, and the only structural rules it enforced were "at
least one step" and "at most 25". Everything else a bad plan can carry —
duplicate step IDs, duplicate sub-task IDs, two fan-out sub-tasks that
write the same file, an absolute path — was constructible and flowed
straight into execution. Overlapping target files were the expensive
case: they trigger the LLM conflict-resolution path at merge time, paying
for model calls to untangle a collision a free, deterministic check
rejects up front. This is Principle 2 — don't send the model to compute
what you can decide by inspection. The maddening part was that the checks
*already existed*, in `eval/deterministic.py`, but ran only inside the
eval harness; nothing ran them on real planner output.

**What shipped.** The check logic moved into a new pure module,
`forge/plan_checks.py`, as *finders* — functions returning the offending
items, empty when the plan is clean. `eval/deterministic.py` kept its
nine public checks, its result models, and its wording, each body now a
call to a finder; the live gate runs the five *structural* finders from
`blocks/dispatch.py::dispatch_planner`, the one seam every planner call
on both lanes passes through since T5.3. A rejected plan is re-planned
with the specific violations appended to the planner's prompt — pure
string work, so a retry costs one more planner call and no extra activity
— for three attempts total, no backoff, thinking escalated on the last.
After the third, the run halts cleanly with
`failure_kind="plan_preflight"` (Principle 5) rather than executing a
plan known to be malformed.

**The gate is a subset, and that is the task's main judgment call.** Four
of the nine eval checks are not gates. Two of them (`context_files
plausible`, `no_forward_references`) need the repo file set, which a
workflow can only obtain by scheduling an activity — a command-sequence
change that would invalidate the committed replay histories, and the
whole design of this gate is that it emits nothing on a clean plan. The
consequence is explicit and was accepted: **cyclic/forward references are
caught by eval, not by the live gate.** The other two
(`fanout_steps_have_min_subtasks`, `all_task_targets_covered`) are
quality judgments rather than defects — a one-child fan-out executes
correctly, and an uncovered declared target is a call about intent whose
false positive costs a whole run.

**The three buried gems, as they turned out.** *Nested violations* are
now caught: every finder recurses, ids are checked among siblings (a
child's identity is the compound `<parent>.sub.<child>` path), and target
overlap compares each child's *effective* target set — its own targets
plus every descendant's — because a grandchild's file surfaces in its
parent's merged output. Recursive fan-out was kept; nothing was deleted.
*The REVISE splice* turned out to be worse than "unbounded history": with
`Plan.steps` capped at 25 since T4.1, an over-cap splice raises a pydantic
`ValidationError` inside workflow code, which Temporal retries as a
workflow task forever — a hung run, not a failed one. `splice_revision`
therefore *catches*: it rejects before constructing the `Plan`, and also
enforces a revision-count cap and re-runs the gate checks on the spliced
result, producing `failure_kind="plan_revision"`. *The empty-response
hole* closed with a `model_validator` on `LLMResponse`: both lanes turn a
pydantic `ValidationError` into the typed mismatch outcome, and
`LLMSchemaMismatch` is deliberately retryable in `LLM_RETRY`, so a
do-nothing response is now re-sampled instead of parsing into a silent
no-op success (nothing written, zero files validated, SUCCESS reported).

**One shape had to change to make room for the gate.** Three test
fixtures reached the conflict-resolution arm by having two sub-tasks
*declare* the same file — exactly what the overlap rule now rejects. They
were rewritten to declare distinct targets while both children still
*write* the shared file, which is what a conflict looks like in
production now: conflict detection has always read what children
produced, never what the plan promised. One committed replay history
(`conflict_resolution_sync`) recorded the old plan in its own payload and
had to be regenerated; the other twelve replay untouched, which is the
proof that a clean plan costs no commands.

## Scope

- Run the deterministic plan checks at plan acceptance in the planner path;
  violations feed back into the planner retry context, the same way
  validation errors feed generation retries.
- One shared, pure implementation used by both the preflight gate and
  `eval/deterministic.py` (cross-reference, don't duplicate).
- Recurse into nested `sub_tasks` — or record the Phase 5 decision to drop
  recursive fan-out and delete the depth machinery instead.
- *(2026-07-08 sweep)* Gate REVISE-spliced plans too: run the same
  deterministic checks on `revised_steps` at the splice site
  (`workflows.py:931-944`) and enforce a max-revision/max-total-steps cap
  (exceeded → terminal result) — the REVISE loop is the one structurally
  unbounded history path and no `continue_as_new` escape exists.
- *(2026-07-08 sweep)* The June "cheap validators" residue: a
  `model_validator` on `LLMResponse` rejecting `files=[]` + `edits=[]`
  (`models.py:365-373`) so a do-nothing response fails parse and enters
  the error-aware retry path — distinct from T3.5's refusal/truncation
  outcomes (an empty response is a contract violation, not a refusal).

### Amendments (2026-07-27 — owner rulings + reconciliation, per the plan review)

Source: [../../forge-plan-review-2026-07-27.md](../../forge-plan-review-2026-07-27.md)
§4, and the owner walkthrough of 2026-07-27.

- **Retry policy (owner-ruled): three planner attempts total, no
  backoff, escalating context.** Preflight failures are semantic, not
  transient — the transport layer already owns transient retry, and a
  timer between attempts adds nothing on the sync lane and hours on the
  batch lane. Each retry appends the specific deterministic violations
  to the planner's context (the prior-errors pattern step retries
  already use); optionally escalate thinking on the final attempt.
  After the third failed attempt: halt cleanly (Principle 5).
- **Ordering (owner-ruled): runs after T5.5** — the preflight retry arm
  and the REVISE cap are new behavioral scenarios, written once in the
  rebuilt harness.
- **The REVISE hazard changed shape (worse-behaved than specced).** The
  splice reconstructs `Plan(steps=…)` and `Plan` now carries
  `max_length=25` (T4.1), so an over-cap splice raises a pydantic
  `ValidationError` **inside workflow code** — an infinitely retrying
  workflow task (hung workflow), not the spec's "unbounded history."
  The revision cap must therefore *catch* the over-cap case and produce
  a clean terminal result, not merely count.
- **Stale refs:** the gate premise now reads `models.py:299-307`
  (`min_length=1, max_length=MAX_PLAN_STEPS` — the max was added by
  T4.1 and partially consumes the "only min_length" claim; everything
  else listed remains unconstrained); the splice is at
  `src/forge/workflows/task.py:435-443`; the batch-lane acceptance gate
  is `Plan.model_validate_json` in `blocks/dispatch.py` (`plan_result`).
- **Cheaper than specced:** since T5.3 all planner dispatch flows
  through the single `dispatch_planner` seam in `blocks/dispatch.py`,
  so the gate hangs in exactly one place and covers both lanes.

## Plan

Written 2026-07-27 before coding, per [PROCESS.md](../PROCESS.md), after
reading the amendments above, the plan review's §4 T5.6 entry, and the
current code at `blocks/dispatch.py`, `workflows/task.py`,
`eval/deterministic.py`, and `models.py`.

**1. One pure home for plan structure: `src/forge/plan_checks.py`.** The
nine check bodies move out of `eval/deterministic.py` into a new pure
module (zero `temporalio` imports, the `step_logic.py` pattern) as
*finder* functions returning a tuple of offending descriptors — empty
tuple means clean. `eval/deterministic.py` keeps its nine public
`check_*` functions, its `DeterministicCheckResult` wording, and
`ALL_CHECKS`/`run_deterministic_checks` verbatim; each body becomes a
call to its finder. That is the shared implementation both consumers
require: one algorithm, two presentations.

Every finder recurses into nested `sub_tasks` (AC 2). Sibling-scope
rules stay sibling-scoped (sub-task ids unique among siblings, matching
the compound `<parent>.sub.<child>` id space); the target-overlap rule
compares each child's *effective* target set — its own targets plus every
descendant's — because a grandchild's file surfaces in its parent's
merged output, so a grandchild/uncle collision is a real collision.

**2. The gate is a subset of the checks, and the subset is a decision.**
`PREFLIGHT_CHECKS` names the structural checks the gate enforces:
duplicate step ids, duplicate sub-task ids, overlapping sub-task targets,
absolute/`..` target paths, and leaf nodes with no target files. The
other four stay eval-only, for stated reasons recorded in the module and
in Development Notes: `check_context_files_plausible` and
`check_no_forward_references` require the repo file set, which is I/O the
workflow cannot do without adding an activity (a command-sequence change
this task rules out); `check_fanout_steps_have_min_subtasks` and
`check_all_task_targets_covered` are quality judgments, not defects — a
one-child fan-out executes correctly, and an uncovered declared target is
an intent call whose false positive costs the whole run.

**3. The gate hangs at `dispatch_planner` (one place, both lanes).**
`dispatch_planner` becomes the three-attempt loop: `typed_dispatch` →
`preflight(plan)` → clean returns `PlanCallResult`; violations append a
specific violation list to the planner's `user_prompt` (the prior-errors
pattern, pure string work, no extra command) and go again; the final
attempt also escalates thinking. After the third failure it returns
`PlanPreflightHalt`, so the signature becomes
`PlanCallResult | PlanPreflightHalt`. A raise is deliberately not used:
`run()` catches `ApplicationError` as a batch-wait failure and would
mislabel the halt.

**4. The REVISE splice catches instead of counting.**
`plan_checks.splice_revision` is pure and returns
`RevisedPlan | RevisionRejected`. It rejects before constructing `Plan`
when the spliced length would exceed `MAX_PLAN_STEPS` (the pydantic
`ValidationError`-inside-workflow hang the amendment describes), when the
revision count would exceed `MAX_PLAN_REVISIONS`, and when the spliced
plan fails the same gate checks. `workflows/task.py` turns a rejection
into a clean terminal `TaskResult`.

**5. Two new `failure_kind` values**, because both failures are
mis-described by every existing kind: `plan_preflight` (the planner could
not produce a structurally valid plan in three attempts) and
`plan_revision` (a sanity-check revision is over the cap or structurally
invalid). The `Literal` grows 10 → 12.

**6. `LLMResponse` rejects the do-nothing response** with a
`model_validator` (`files=[]` and `edits=[]`). Both lanes already convert
a pydantic `ValidationError` into the typed mismatch outcome
(`client.py:254`, `batch.py:234`), and `LLMSchemaMismatch` is
deliberately retryable in `LLM_RETRY` — so on the sync lane the empty
response is re-sampled by the activity retry, which is the error-aware
path the scope asks for. On the batch lane the parse activity raises it
non-retryable (re-parsing identical stored bytes cannot change the
outcome), unchanged from every other mismatch.

**7. `derive_execution_timeout` learns about the retries.** Its
`planner_waits` term is `max_exploration_rounds + 1`; three planner
attempts on the batch lane make it
`max_exploration_rounds + MAX_PLANNER_ATTEMPTS`. Pure, CLI-side, no
replay impact.

**Replay.** The gate emits no commands on a clean plan, so the committed
histories are expected to replay unregenerated — with one known
exception found while reading the fixtures: `conflict_resolution_sync`
records a plan whose two sub-tasks both declare `shared.py`, which the
overlap gate rejects. That fixture is changed to declare distinct targets
while both children still *write* `shared.py` (conflict detection reads
what children produced, not what they declared), preserving exactly what
the scenario proves, and that one history is regenerated. See Development
Notes.

## Development Notes

**2026-07-27 — the gate is a subset of the nine checks, and that is a
decision.** Running all nine at plan acceptance is not possible and not
desirable. Two of them (`check_context_files_plausible`,
`check_no_forward_references`) take a `known_repo_files` set; obtaining it
inside a workflow means scheduling an activity, which changes the command
sequence of every planned run and invalidates the committed replay
histories — the one thing this task's design avoids by staying pure inline
logic. They keep their existing SKIP behavior. The consequence for the
acceptance criteria is explicit: **"cyclic references" are *not* caught by
the live gate** — only by eval, where the corpus supplies the file set. A
repo-set-free forward-reference rule was considered and rejected because
"step 1 reads `config.py`, step 3 rewrites `config.py`" — an everyday plan
— is indistinguishable from a genuine forward reference without it, so the
rule would false-positive constantly and halt real runs.

The other two omissions are judgment, not mechanism.
`check_fanout_steps_have_min_subtasks` fails a one-child fan-out, which
executes correctly and merely wastes a child workflow — a quality signal,
not a defect worth burning three REASONING calls and then halting.
`check_all_task_targets_covered` needs the `TaskDefinition` (which the
`dispatch_planner` seam does not carry) and is a call about *intent*: the
user's declared target list versus the planner's file layout. Its false
positive costs the whole run. Both remain scored by eval. This split is
recorded here rather than buried in code because it narrows the task's
stated scope; it is the reviewable decision of this task.

**2026-07-27 — the overlap gate collides with how conflict resolution was
being tested.** `check_sub_task_targets_non_overlapping` is the headline
gate rule (the Problem's cost argument), and it rejects exactly the fixture
shape three tests used to *reach* the conflict-resolution arm: two
sub-tasks declaring the same `shared.py`. The fixtures were changed to
declare distinct targets while both children still *write* `shared.py`.
Nothing about the proof weakens — conflict detection has always classified
what children produced (`classify_file_conflicts` over
`SubTaskResult.output_files`), never what the plan declared — and the new
fixture is now the *only* live shape a conflict can take: an undeclared
write. Sites: `tests/support/block_mocks.py::five_arm_activities`,
`tests/replay/regenerate.py::_scenario_conflict_resolution_sync`.

**2026-07-27 — replay: 12 of 13 histories unregenerated, 1 regenerated
deliberately.** `conflict_resolution_sync` fails as
`NondeterminismError: Activity machine does not handle this event:
HistoryEvent(id: 29, StartChildWorkflowExecutionInitiated)`. The mechanism
is not subtle and was not a mystery: the recorded history's planner result
carries the old overlapping-target plan, so replaying it through the new
code rejects that plan at preflight and schedules a *second planner call*
where the history has a child-workflow start. No amount of fixture editing
can save a history whose recorded payload is the rejected artifact, so this
one history was regenerated after the fixture fix, and only this one
(`uv run python -m tests.replay.regenerate conflict_resolution_sync`). The
other twelve — including `nested_fan_out_sync`, whose single-sub-task
fan-out is exactly why `undersized_fan_outs` is eval-only — replay
untouched, which is the behavior-preservation proof that the gate emits no
commands on a clean plan.

**2026-07-27 — the duplicate-id gather test moved to the sub-task path.**
`TestGatherDuplicateSubTaskIds` drove duplicates through a *planner* plan,
which the gate now intercepts three attempts earlier. The gather's runtime
guard is still live and still worth an end-to-end test, so the test now
starts `ForgeSubTaskWorkflow` directly with duplicated nested sub-tasks —
the one path no planner output passes through. Same assertions, with the
nested mode's wording (`"Duplicate nested sub-task IDs detected"`). The
plan-path proof did not disappear; it moved to
`tests/workflows/test_preflight.py` as a preflight halt.

**2026-07-27 — the empty-response validator makes an old payload shape
undeserializable.** `LLMResponse` with `files=[]` and `edits=[]` no longer
validates, which is the point (both lanes turn the pydantic
`ValidationError` into the typed mismatch outcome, and `LLMSchemaMismatch`
is deliberately retryable in `LLM_RETRY`, so the sync lane re-samples). The
side effect worth stating: a *recorded* payload of that shape — an
in-flight workflow whose history holds an empty generation result — now
fails to deserialize on replay. No committed history carries one and the
shape was a silent no-op success, so nothing is lost, but a production
worker upgrade while such a run is in flight would fail that run's workflow
task. `tests/test_models.py`'s cache-field backward-compat payload was
updated for the same reason.

**2026-07-27 — `derive_execution_timeout` had to learn about the retries.**
Its planner term was `max_exploration_rounds + 1`; on the batch lane each
planner attempt is a full 25h-ceilinged batch wait, so three attempts is
`max_exploration_rounds + MAX_PLANNER_ATTEMPTS`. Missing this would have
left a batch-lane planned run able to exhaust its own execution timeout
inside the retry arm. The function is pure and CLI-side, so this is not a
replay-affecting change.
