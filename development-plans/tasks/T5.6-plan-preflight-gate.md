## Problem

`Plan` enforces only `steps: min_length=1` (`models.py:244-249`). Duplicate
step IDs, duplicate sub-task IDs, overlapping fan-out target files,
cyclic/forward step references, and absolute paths are all constructible
and flow straight into execution, where overlapping targets trigger
conflict-resolution LLM calls a free deterministic check would have
prevented. The checks already exist (`eval/deterministic.py:52-350`) but
run only in the eval harness; the sole acceptance gate on planner output is
`Plan.model_validate` (`planner.py:221`). The existing checks also iterate
exactly one nesting level, so nested-sub-task violations are invisible even
to eval.

## Background and Detailed Explanation

T5.6 makes forge check a plan for structural defects *before* it
executes, using validation logic the codebase already has but never
runs at the moment it matters.

**The problem.** The only gate on planner output today is
`Plan.model_validate`, and the only rule it enforces is "at least one
step." Everything else a bad plan can carry — duplicate step IDs,
duplicate sub-task IDs, two fan-out sub-tasks that write the same
file, a step referencing a later or cyclic step, an absolute path — is
constructible and flows straight into execution. Overlapping target
files are the expensive case: they trigger the LLM
conflict-resolution path at merge time, paying for model calls to
untangle a collision a free, deterministic check would have rejected
up front. This is Principle 2 again — don't send the model to compute
what you can decide by inspection. The maddening part is that the
checks *already exist*, in `eval/deterministic.py`, but they run only
inside the eval harness; nothing runs them on real planner output on
the live path.

**The fix.** Run those deterministic checks at plan acceptance in the
planner path, and feed any violations back into the planner's retry
context exactly the way validation errors already feed generation
retries — so the planner gets a chance to fix its own malformed plan.
Crucially, the check is *one shared, pure implementation* used by both
the preflight gate and `eval/deterministic.py`, cross-referenced
rather than copied, so the two can never diverge.

**The buried gems (the 2026-07-08 amendments).** Three sharp edges the
dense scope hides. *Nested violations are currently invisible:* the
existing checks iterate exactly one nesting level, so a duplicate ID
or overlapping target inside a nested sub-task escapes even the eval
harness — T5.6 either recurses into `sub_tasks` or records a Phase-5
decision to drop recursive fan-out and delete the depth machinery
outright. *The REVISE loop is unbounded:* when a sanity check splices
revised steps back into a running plan, that splice is the one
workflow path whose history can grow without a structural ceiling and
with no `continue_as_new` escape — so the gate must also run on
`revised_steps` at the splice site and enforce a max-revision /
max-total-steps cap, terminating cleanly when exceeded. *The
empty-response hole:* a do-nothing `LLMResponse` (`files=[]` and
`edits=[]`) currently parses fine; a `model_validator` should reject
it so it fails parse and enters the error-aware retry path. This is a
contract violation — the model returned nothing usable — which is
distinct from T3.5's typed refusal and truncation outcomes, where the
model deliberately declined or was cut off.

**How you'll know it's done:** a plan with duplicate step IDs,
overlapping fan-out targets, or cyclic references is rejected before
any step runs and triggers a planner retry carrying the violation
list; nested violations are caught (or nesting is removed and the
decision recorded); eval and preflight share one implementation; and a
REVISE splice past the cap terminates cleanly while an empty
`LLMResponse` fails validation and retries with feedback.

## Scope

- Run the deterministic plan checks at plan acceptance in the planner path;
  violations feed back into the planner retry context, the same way
  validation errors feed generation retries.
- One shared, pure implementation used by both the preflight gate and
  `eval/deterministic.py` (cross-reference, don't duplicate).
- Recurse into nested `sub_tasks` — or record the Phase 5 decision to drop
  recursive fan-out and delete the depth machinery instead.
- *(2026-07-08 sweep)* Gate REVISE-spliced plans too: run the same
  deterministic checks on `revised_steps` at the splice site
  (`workflows.py:931-944`) and enforce a max-revision/max-total-steps cap
  (exceeded → terminal result) — the REVISE loop is the one structurally
  unbounded history path and no `continue_as_new` escape exists.
- *(2026-07-08 sweep)* The June "cheap validators" residue: a
  `model_validator` on `LLMResponse` rejecting `files=[]` + `edits=[]`
  (`models.py:365-373`) so a do-nothing response fails parse and enters
  the error-aware retry path — distinct from T3.5's refusal/truncation
  outcomes (an empty response is a contract violation, not a refusal).

## Acceptance Criteria

- [ ] A plan with duplicate step IDs, overlapping fan-out targets, or
      cyclic references is rejected before any step executes and triggers a
      planner retry carrying the violation list.
- [ ] Nested sub-task violations are detected (or nesting is removed and
      the decision recorded).
- [ ] Eval and preflight share one implementation.
- [ ] *(2026-07-08)* A REVISE splice exceeding the revision/step cap
      terminates cleanly; an empty LLMResponse fails validation and
      triggers a retry with feedback.
