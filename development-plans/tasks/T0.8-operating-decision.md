## Problem

Whether forge runs unattended anywhere before Phase 4 lands is undecided
and unrecorded. The answer determines the status of the "stop the
bleeding" tasks:

- **If yes:** T1.2, T1.3, and T1.7 (plus T0.7's fail-open secrets fix)
  are urgent — the system is operating with two known silent-data-loss
  criticals, a wedgeable poller, and root-privileged model-influenced
  subprocesses.
- **If no:** the interim tasks T1.2/T1.3 are deletable waste — drop them
  with a dated note, remove their T2.1 dependency edge, and reorder to
  shorten the path to Phase 4, which makes both criticals unconstructible.

Every idle week without this decision transfers value from the interims
to the accusation that Phase 1 front-loaded urgency it didn't feel
(review §5).

## Background and Detailed Explanation

This was a decision to be recorded, not code to be written — but it had
been open since the review, and it gated the urgency of several other
tasks. The open question: does forge run unattended anywhere before
Phase 4 lands? If *yes*, the "stop the bleeding" interims (T1.2, T1.3,
T1.7) were genuinely urgent — the system would be operating with known
silent-data-loss criticals and a wedgeable poller. If *no*, T1.2/T1.3
were deletable waste that should be dropped to shorten the path to Phase
4, which makes those criticals unconstructible anyway. Every idle week
without the answer transferred value from the interims toward the
accusation that Phase 1 had front-loaded urgency it didn't actually
feel.

By the time the task closed it had been **mooted by events**, so it was
recorded as a retrospective. The question was answered *yes* by D99
(launchd workers on an always-on desktop), and the branch the answer
would have gated was already dead: T1.2/T1.3 had shipped, so the "drop
the interims" disposition was no longer available, and their eventual
deletion is owned by T4.1. All that remained was the specified artifact
— a dated paragraph in the TASKS.md Phase 1 preamble recording that
forge does operate unattended, that the interims were justified and
served, and that no reorder was needed. The deployment-shape decision
itself already lived in DECISIONS.md as D99, so this note stayed in
TASKS.md per the task's own scope.
