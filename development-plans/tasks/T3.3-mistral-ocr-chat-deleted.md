## Problem

All Mistral API interaction currently runs on forge's worker via sax-llm,
even though only ocr consumes it. With the shared poller dying in Phase 4,
ocr needs its own Mistral OCR capability from the platform library
(injected, not imported as a global). The review verified that **no
production code path uses Mistral chat** — all forge tier defaults are
Anthropic — so chat support is deleted rather than ported.

## Background and Detailed Explanation

Mistral is used in exactly one place — ocr's document OCR — yet every
Mistral API call historically ran on **forge's** worker through the
shared sax-llm library. With the cross-queue signal poller scheduled to
die in Phase 4, ocr needed its own OCR capability, owned by the platform
library and handed to ocr by dependency injection rather than reached as
a module global. T3.3 built `sax_platform.ocr.MistralOcr` for that, and
made a second, sharper cut: the June review had verified that **no
production code path uses Mistral chat** — every forge tier default is
Anthropic — so the ~450-line Mistral chat lane was deleted outright
rather than ported. Only the OCR half (batch submit via file upload,
polling with error-file merging, image extraction) moved across.

The reason this could not be a tidy standalone port is a hidden coupling
the scout uncovered: forge's production OCR flow ran *through* forge's
own batch SPI, resolving `MistralProvider` from sax-llm's registry at
submit and poll time. Deleting sax-llm's Mistral support therefore had
to happen in the *same* change that switched forge's mistral branch onto
the new `MistralOcr` — otherwise production would break in the window
before Phase 4 rewired polling into ocr. So the delete and the switch
were one coupled edit, with a narrow `_BlobSubmitProvider` Protocol
standing in for the fact that `MistralOcr` deliberately never implemented
the full chat-bearing provider interface.

Two honest findings shaped the as-shipped code. The June scope's "OCR
sync call" turned out never to have existed in sax-llm — its `call()`
was chat-only — so `MistralOcr.process` is a thin *new* wrapper over the
SDK's async OCR endpoint, not a port of anything. And the Mistral SDK
does not read `MISTRAL_API_KEY` on its own, so `make_mistral_client` kept
the explicit env fallback sax-llm had carried. A post-merge review then
fixed four real defects: the error-file parser crashed on lines with an
explicit `"response": null` (a present-but-null key defeats a `.get`
default), and the same latent bug hid in the success path; the client
silently accepted a missing API key instead of failing at construction
as its docstring promised; a dropped empty-string endpoint normalization
was restored; and forge's two hand-rolled dispatch sites were collapsed
onto one lazily-cached resolver, ending a fresh SDK client per poll and a
needless base64-image round-trip through `model_dump`/`model_validate`.

## Scope

Port from sax-llm: OCR sync call + OCR batch (file-based upload for
`/v1/ocr`, poll with error-file merging,
`_extract_images_from_response`). **Delete Mistral chat support** —
verified zero production users (all forge tier defaults are Anthropic; ocr
never imports mistralai/sax_llm directly; only mocked unit tests exercise
it). ocr receives `MistralOcr` via DI.

## Plan

*Written 2026-07-16. Scouted reality: ocr's production flow runs
through forge's SPI today — `submit_provider_batch`
(activities/batch_submit.py) and `poll_batch_results`
(activities/batch_poll.py) resolve `MistralProvider` from sax_llm's
registry. Deleting sax_llm's Mistral support therefore requires
forge's mistral branch to switch to the ported capability in the same
change, or production breaks before Phase 4 rewires polling into ocr.*

### Design

1. **`sax_platform.ocr`** (new module): `MistralOcr` class owning the
   ported capability — sync OCR call, batch submit via file upload to
   `/v1/ocr`, poll with error-file merging, image extraction
   (`_extract_images_from_response` port) — plus the OCR-relevant
   result models (shapes structurally identical to sax_llm's
   `BatchPollResult`/`BatchResultEntry`/`ExtractedImage` so forge's
   poll path adapts trivially; sax_platform must not import sax_llm).
   The Mistral SDK client is **injected** (constructor arg), not a
   module global. sax-platform gains `mistralai>=1.0.0,<2`; the
   SDK-importing module is lazily exported like client/batch (the
   sandbox-light rule from T3.2).
2. **forge's mistral branch switches**: `submit_provider_batch` and
   `poll_batch_results` use `sax_platform.ocr.MistralOcr` when
   provider == "mistral"; sax_llm's registry no longer knows mistral.
3. **sax_llm deletion**: `mistral.py` deleted whole (chat support was
   verified zero-users in June; the OCR half is ported), registry
   mistral entries gone, `mistralai` dependency dropped from sax-llm,
   mistral mock tests deleted (the AC's "only deleted-code references
   are the removed mock tests").
4. **ocr DI seam**: ocr's worker constructs `MistralOcr` at startup
   (MISTRAL_API_KEY env) and installs it via an explicit
   `ocr/deps.py` set/get seam (mirroring its `_init_store` pattern);
   Phase 4's self-polling activities consume it. ocr's pyproject gains
   `sax-platform`. (CLAUDE.md's "ocr imports forge_contracts only"
   line updates at closeout.)
5. **e2e AC**: ocr's env-gated e2e suite runs live at the end
   (MISTRAL_API_KEY available on this machine) if its cost profile is
   a tiny document; otherwise recorded as env-gated-not-run with
   reason.

### Steps

1. S1 (agent): `sax_platform.ocr` + mocked-SDK tests (shapes ported
   verbatim from sax_llm/mistral.py).
2. S2 (agent, after S1): forge branch switch + sax_llm deletion +
   test updates (both sides in one change — they are coupled).
3. S3 (agent, parallel with S2): ocr DI seam + pyproject + tests.
4. Gates; e2e check; PR; CI; closeout.
