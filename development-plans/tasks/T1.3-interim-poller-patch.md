## Problem

**Critical, live:** transient signal-delivery failure permanently marks the
`batch_jobs` row FAILED while the provider still holds the paid result
(batch_poll.py:178-197); rows >24h go MISSING with **no signal**, so the
waiter burns the full 25h timeout (`_BATCH_WAIT_TIMEOUT`,
workflow_blocks.py:59).

## Scope

Minimal — the subsystem dies in Phase 4:

- On signal-delivery failure, leave the row SUBMITTED (next cycle retries;
  safe under [T1.2](T1.2-interim-batch-result-correlation.md) dedup).
- MISSING sends the waiter an error-payload signal so it fails fast.
- Do **not** build the attempts-cap/two-column machinery.
- **Amendment (2026-07-08, capture sweep):** also fix the wedge —
  `poll_batch_results` raises `RuntimeError` when ANY job errored
  (`batch_poll.py:205-207`) and the poller workflow sets no retry policy
  (`batch_poller_workflow.py:26-32`, unlimited default attempts), so one
  bad batch turns the poller into a retry loop while the overlap=SKIP
  schedule skips every subsequent run. Stop raising on partial per-job
  errors (report `errors_found` in the result; the next scheduled run is
  the retry) or set a finite `retry_policy` on the activity call, and give
  the scheduled action an explicit execution timeout + overlap policy in
  `_ensure_schedule`.

## Plan

All three fixes live in `execute_poll_batch_results`
(`src/forge/activities/batch_poll.py`) and `_ensure_schedule`
(`src/forge/worker.py`). No workflow or model file changes.

1. **Signal-delivery failure leaves the row SUBMITTED (bug 1).** In the ENDED
   branch, track a `delivery_failed` flag. If any entry's signal delivery
   raised, `continue` without calling `update_status_fn` — the row stays
   SUBMITTED and the next poll cycle re-polls and re-delivers. Safe under
   [T1.2](T1.2-interim-batch-result-correlation.md): waiters key by
   `request_id` and `setdefault`, so re-delivered signals are no-ops. Only
   advance to PROCESSING (or terminal FAILED when there are no entries) when
   every entry was delivered.

2. **MISSING wakes the waiter (bug 2).** In the >24h branch, send the waiter a
   `BatchResult(error=..., result_type="errored")` signal before marking the
   row MISSING. The waiter (`batch_submit_and_wait`, ingestion) raises on
   `result.error`, so it fails fast instead of burning the 25h
   `_BATCH_WAIT_TIMEOUT`. No new forge-contracts enum member is needed — the
   existing `BatchResult.error` + `"errored"` convention (already used by the
   terminal-failure path, and the fail-fast half already covered by
   `test_batch_error_in_signal_raises`) fully represents the payload.

3. **Un-wedge the poller (bug 3).** Delete the `raise RuntimeError` on
   `errors_found > 0` — report `errors_found` in the returned result (log a
   warning for observability) and let the next scheduled run be the retry.
   Give the scheduled action an explicit `execution_timeout` and set
   `SchedulePolicy(overlap=ScheduleOverlapPolicy.SKIP)` in `_ensure_schedule`
   (and apply them on the update path too, so an already-running schedule
   picks up the backstop), so a wedged run is terminated and the next run can
   fire.

Factor a small `_deliver_signal` helper (get handle, signal, log-and-return
False on failure) to de-duplicate the three signal sites.
