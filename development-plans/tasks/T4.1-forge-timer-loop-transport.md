## Problem

Two confirmed criticals live in the signal-based batch transport: batch
results are consumed without correlation (a duplicate/stale signal becomes
the wrong call's result), and the poller abandons paid results (transient
delivery failure → terminal FAILED; >24h → MISSING with no signal, so the
waiter burns the full 25h timeout). The merged plan's adjudication: under
D79 (1 request = 1 batch = 1 waiter) the shared poller amortizes zero
provider calls, and timer-loop polling makes both criticals
unconstructible because the requester is the recipient. Today's
`request_id` is also minted inside the retried submit activity, which can
orphan paid batches on retry.

## Scope

Replace the signal wait: `submit` activity (platform builder;
`output_config.format`; **request_id/custom_id minted in the workflow via
`workflow.uuid4()`** — closes the submit-retry orphan window) →
`workflow.sleep(poll_interval)` + thin `batch_status(batch_id)` activity
loop (**default 300–600s, configurable; never below 300s** — verified
history math: ~11 events/poll; 25h at 600s ≈ 1,650 events; 30-wait worst
case ≈ 24k of 51.2k) → `fetch_results` activity (download; validate with
the call site's output class; provider threaded through — no more
`"anthropic"` default; claim-check return: inline ≤256KB else S3 pointer).
Keep the 25h ceiling + T1.6b failure symmetry. Delete:
BatchPollerWorkflow + its Schedule, `BATCH_RESULT_SIGNAL` consumption in
forge, all signal
handlers + the [T1.2](T1.2-interim-batch-result-correlation.md)/
[T1.3](T1.3-interim-poller-patch.md) interims, the BatchResult
cross-workflow envelope. `batch_jobs` reduced to forge-internal
audit/spend ledger (written at submit + final fetch; provider-lifecycle
statuses only).

### Accepted tradeoff (documented)

A dead waiter orphans its paid batch — there is no longer a shared poller
to notice a completed batch whose requesting workflow has died.
Reconciliation (a sweep that detects orphaned completed batches) is
deferred; the symptom is a slightly higher invoice, not data corruption.

### Amendment (2026-07-08): the timeout tree must close

The timer-loop keeps the batch wait *inside* the waiting workflow, so this
task inherits a defect the June review missed: execution timeouts are not
derived from the wait budget. Under shipped defaults, fan-out children get
15–20-minute execution timeouts (`_child_timeout`, `workflows.py:137`,
applied at `:1201`/`:1692`) while their batch-mode generation call may
legally wait ≤24h — any batch slower than ~15 minutes kills the child and
orphans the paid batch. The 48h workflow execution timeout (`cli.py:66`)
likewise admits fewer waits than the defaults allow (exploration rounds ×
attempts × 25h). This task must derive child and workflow execution
timeouts from the number of permitted batch waits and their ceiling, or the
migration faithfully preserves the bug.
