## Problem

Two confirmed criticals live in the signal-based batch transport: batch
results are consumed without correlation (a duplicate/stale signal becomes
the wrong call's result), and the poller abandons paid results (transient
delivery failure → terminal FAILED; >24h → MISSING with no signal, so the
waiter burns the full 25h timeout). The merged plan's adjudication: under
D79 (1 request = 1 batch = 1 waiter) the shared poller amortizes zero
provider calls, and timer-loop polling makes both criticals
unconstructible because the requester is the recipient. Today's
`request_id` is also minted inside the retried submit activity, which can
orphan paid batches on retry.

## Background and Detailed Explanation

Forge sends most of its LLM work in *batch mode* — an asynchronous lane
that costs half as much as a live call but can take up to 24 hours to
return an answer. That creates a hard question: a workflow that submits a
batch may have to wait a day for the result, so how does the answer get
back to the workflow waiting for it? The design this task replaced answered
with a separate, shared `BatchPollerWorkflow` that polled every outstanding
batch on a Schedule and, when one finished, delivered its result back to
the waiting workflow by Temporal *signal* — an asynchronous message pushed
into a running workflow.

That indirection carried two confirmed critical bugs. First, results were
consumed with no correlation: a duplicate or stale signal could be picked
up as some other call's result — silent data corruption, the worst failure
a task orchestrator can have. Second, the poller abandoned results the
operator had already paid for — a transient delivery failure was recorded
as a terminal FAILED, and a batch that ran past 24h was marked MISSING with
no signal ever sent, so the waiting workflow sat burning its full 25-hour
timeout for an answer that had, in fact, already arrived.

**The fix inverts the arrangement: every workflow polls for its own
batch.** The wait became submit → a loop of `workflow.sleep(interval)` plus
a thin `batch_status` activity → a `fetch_batch_result` activity, all
living in the one choke point (`batch_submit_and_wait`) that every forge
batch wait already funnels through. What makes this *simpler* rather than
merely different is D79's "one request = one batch = one waiter": with a
single waiter per batch, a shared poller amortizes zero provider calls — it
was pure coordination machinery buying nothing. And both criticals become
structurally unconstructible, because the requester is now its own
recipient — there is no separate party who could misroute a result or drop
a signal. The whole signal path went with the poller: the Schedule, every
`@workflow.signal` handler, the correlation dictionaries, and the Phase 1
interims (T1.2/T1.3) that had patched it.

One subtle correctness point drove a specific choice — the
`request_id`/`custom_id` is now minted *inside the workflow* via
`workflow.uuid4()` (deterministic under Temporal replay), not inside the
submit activity as before. A submit activity that minted its own id could,
on retry, submit a second paid batch under a fresh id — an orphan. Minting
in the workflow means a retried submit reuses the same id, closing that
window.

**The buried gem is the timeout tree — a latent defect the June review
missed, and one this migration would have faithfully preserved if left
alone.** Keeping the wait *inside* the waiting workflow means the
workflow's own execution timeout now has to cover a batch that may legally
run for a day. Under the shipped defaults it did not: fan-out children were
given 15–20-minute execution timeouts while their batch-mode generation
call could wait up to 24 hours, so any batch slower than ~15 minutes would
kill the child mid-wait and orphan the paid batch. The task therefore
derived both child and workflow execution timeouts from the *number of
permitted batch waits* times the 25-hour ceiling (mode-aware
`_child_timeout` and `derive_execution_timeout`), and added a
`MAX_PLAN_STEPS = 25` validator so an oversized LLM plan fails as a
retryable parse error rather than blowing an unbounded timeout. The defect
was not theoretical — it surfaced live during the cutover, when a
three-level recursive fan-out test failed because a mid-tree node runs two
sequential batch phases that together outran its still-sync-sized timeout.

A few smaller as-shipped truths are worth carrying. The `batch_jobs` table
was reduced to a forge-internal audit ledger *behaviorally*, with no schema
migration — `ENDED` is simply a new string value on an existing column, and
`update_batch_status` gained a monotonic WHERE-guard so a delayed retry
cannot regress a terminal row. The transport landed with committed replay
histories under `tests/replay/`, so a future workflow edit that changes the
command sequence is caught. And one tradeoff is accepted and documented:
with no shared poller, a workflow that dies mid-wait orphans its paid batch
— reconciliation (a sweep for completed-but-abandoned batches) is deferred,
and the symptom is a slightly larger invoice, never lost or corrupted data.

## Scope

Replace the signal wait: `submit` activity (platform builder;
`output_config.format`; **request_id/custom_id minted in the workflow via
`workflow.uuid4()`** — closes the submit-retry orphan window) →
`workflow.sleep(poll_interval)` + thin `batch_status(batch_id)` activity
loop (**default 300–600s, configurable; never below 300s** — verified
history math: ~11 events/poll; 25h at 600s ≈ 1,650 events; 30-wait worst
case ≈ 24k of 51.2k) → `fetch_results` activity (download; validate with
the call site's output class; provider threaded through — no more
`"anthropic"` default; claim-check return: inline ≤256KB else S3 pointer).
Keep the 25h ceiling + T1.6b failure symmetry. Delete:
BatchPollerWorkflow + its Schedule, `BATCH_RESULT_SIGNAL` consumption in
forge, all signal
handlers + the [T1.2](T1.2-interim-batch-result-correlation.md)/
[T1.3](T1.3-interim-poller-patch.md) interims, the BatchResult
cross-workflow envelope. `batch_jobs` reduced to forge-internal
audit/spend ledger (written at submit + final fetch; provider-lifecycle
statuses only).

### Accepted tradeoff (documented)

A dead waiter orphans its paid batch — there is no longer a shared poller
to notice a completed batch whose requesting workflow has died.
Reconciliation (a sweep that detects orphaned completed batches) is
deferred; the symptom is a slightly higher invoice, not data corruption.

### Amendment (2026-07-08): the timeout tree must close

The timer-loop keeps the batch wait *inside* the waiting workflow, so this
task inherits a defect the June review missed: execution timeouts are not
derived from the wait budget. Under shipped defaults, fan-out children get
15–20-minute execution timeouts (`_child_timeout`, `workflows.py:137`,
applied at `:1201`/`:1692`) while their batch-mode generation call may
legally wait ≤24h — any batch slower than ~15 minutes kills the child and
orphans the paid batch. The 48h workflow execution timeout (`cli.py:66`)
likewise admits fewer waits than the defaults allow (exploration rounds ×
attempts × 25h). This task must derive child and workflow execution
timeouts from the number of permitted batch waits and their ceiling, or the
migration faithfully preserves the bug.

## Plan

### Design (settled up front)

**The timer loop lives in `workflow_blocks.batch_submit_and_wait`** — already
the single choke point for every forge batch wait (generation, planner,
exploration, sanity check, conflict resolution, ingestion extraction). New
shape:

1. Mint `request_id = str(workflow.uuid4())` **in the workflow**; pass it in
   `BatchSubmitInput` (new required field). `execute_batch_submit` stops
   minting its own uuid — a retried submit reuses the same custom_id.
2. Submit via the existing `submit_batch_request` activity; persist
   `PersistBatchSubmission` exactly as today (survivable submit-time ledger
   write, unchanged).
3. Timer loop: `batch_status` activity (thin; `BatchStatusInput(batch_id,
   provider)` → normalized `BatchStatusResult.state` in
   `in_progress | ended | failed | expired | canceled`) + `workflow.sleep()`.
   Poll interval: default 600s, **floor 300s enforced twice** (pydantic
   `ge=300` on the input field and a defensive clamp in the loop). Deadline:
   the existing 25h `wait_timeout`, checked in workflow code via
   `workflow.now()`.
   - `ended` → break to fetch.
   - `failed`/`expired`/`canceled` → persist terminal outcome
     (`FAILED`/`EXPIRED`), raise `ApplicationError` (non-retryable).
   - deadline passed → persist `MISSING` ("gave up waiting after 25h"), raise
     `ApplicationError`. `BATCH_WAIT_FAILURES` semantics and the T1.6b
     failure symmetry (worktree cleanup + terminal run row) are preserved.
4. Fetch: new `fetch_batch_result` activity — `FetchBatchResultInput(batch_id,
   request_id, provider)` (provider **required**, threaded from
   `BatchSubmitResult.provider`; no `"anthropic"` default anywhere in the new
   path) → `BatchFetchResult(raw_response_json | s3_key | error)`. Downloads
   the batch's result lines, selects this waiter's line by custom_id,
   claim-checks the body: inline ≤256KB, else S3 pointer via the existing
   envelope (`dump_batch_result_payload`). A failed line or a missing
   custom_id returns `error`. This is a forge-internal **activity return**,
   not a cross-workflow envelope — the contracts `BatchResult` signal payload
   is what forge stops using.
5. Persist terminal `ENDED` outcome (new `PersistBatchOutcome` persist kind →
   monotonic `update_batch_status`), then classify via the **existing**
   `parse_llm_response` activity (unchanged: resolves the s3 pointer,
   validates with the call site's output class). Fetch + parse together are
   D88's "fetch_results".

**Provider dispatch** for `batch_status`/`fetch_batch_result` reuses the
poller's per-provider machinery (anthropic → `sax_platform.llm.batch`
`get_batch_status`/`fetch_batch_result_lines`; mistral → the injected
`MistralOcr`), moved from `batch_poll.py` into the new activity module. The
platform's `fetch_batch_result_lines`/`classify_result_json` **stay** — their
docstrings are updated (they now serve the timer-loop transport, not the
"pre-T4.1" path).

**`batch_jobs` reduction is behavioral, not structural.** Write points become
submit + terminal outcome; statuses become provider-lifecycle only:
`SUBMITTED` → `ENDED` (new member; fetched successfully) | `FAILED` |
`EXPIRED` | `MISSING` (waiter gave up at the ceiling). `PROCESSING` becomes a
legacy, read-only member (old poller rows) — never written. No column
changes, therefore **no Alembic migration** (the anticipated ALTER turned out
unnecessary — see Dev Notes). `update_batch_status` gains the monotonic
state-machine predicate (`WHERE status = 'submitted'` — the only non-terminal
state) and stops clobbering a recorded `error_message` with `None`. The
schema-×2 drift finding is closed with a forge-side sync test comparing the
contracts read-only mirror to `forge.store.BatchJob` column-by-column.

**Timeout tree closes.** `_child_timeout` becomes mode-aware: sync keeps
today's 15min + 5min/level; batch derives from the permitted-wait budget —
leaf waits = `max_attempts` (one generation wait per attempt; sub-tasks do
not explore), each nesting level adds one conflict-resolution wait:
`(max_attempts + remaining_levels) × 25h + (15 + 5×remaining) min`. The CLI's
flat 48h `_WORKFLOW_EXECUTION_TIMEOUT` likewise becomes mode-aware, derived
from the enumerated batch-wait sites (single-step: `max_attempts ×
(max_exploration_rounds + 1)` waits; planned mode needs a plan-steps bound to
close the tree — add a documented `MAX_PLAN_STEPS` cap validated on `Plan`).
The implementing stage enumerates every wait site and records the exact
formula here.

**Stays until T4.2 (do not delete):** `submit_batch_blob` + the contracts SPI
wire models (`BatchSubmitSpiInput`, `BatchResult`, `BatchSubmitResult`),
`BATCH_RESULT_SIGNAL` constant, the contracts `batch_jobs` read-only mirror,
`resolve_batch_result`, and all of ocr. Between T4.1 and T4.2 ocr can submit
but nothing polls its batches — accepted phase-ordering gap.

**Deleted:** `BatchPollerWorkflow` + the `forge-batch-poller` Schedule +
`_ensure_schedule` poller wiring + `_POLLER_EXECUTION_TIMEOUT` (T1.3),
`poll_batch_results` activity + `batch_poll.py`, the T1.2 correlation dicts +
`batch_result_received` signal handlers (ForgeTaskWorkflow,
ForgeSubTaskWorkflow, ingestion workflows), `BatchPollerInput`/
`BatchPollerResult`/forge's `BatchResult` re-export, the worker
`batch_poll_interval` flag, `tests/test_batch_poll.py`,
`tests/test_batch_poller_workflow.py`.

**Config:** `batch_poll_interval_seconds: int = 600` (`ge=300`) on
`ForgeTaskInput`/`SubTaskInput`, CLI `--batch-poll-interval`; ingestion uses
the default.

- 2026-07-19 (ST3c) — **Timeout tree closed.** Enumerated every batch-wait
  site and derived child + workflow execution timeouts from the
  permitted-wait budget. Each wait is bounded by the shared 25h
  `BATCH_WAIT_CEILING` (now in `forge.models`, one source of truth —
  `workflow_blocks._BATCH_WAIT_TIMEOUT` references it). Sequential 25h waits
  per path (worst case, `remaining = max_depth − depth`):

  | Execution path | Max sequential 25h waits | Basis |
  | --- | --- | --- |
  | Leaf sub-task | `max_attempts` | one generation wait per retry; leaves don't explore |
  | Nested sub-task (depth `d`) | `W(d) = W(d+1) + 1` = `max_attempts + remaining` | awaits slowest child, then one conflict-resolution wait |
  | Root single-step (`plan=False`) | `max_attempts × (max_exploration_rounds + 1)` | per attempt: exploration loop + one generation wait |
  | Root planned — planner | `max_exploration_rounds + 1` | exploration loop + one planner wait |
  | Root planned — regular step | `max_step_attempts` | one generation wait per step retry |
  | Root planned — fan-out step | `(max_sub_task_attempts + max_fan_out_depth) + 1` | awaits depth-0 child budget, then one conflict-resolution wait |
  | Root planned — sanity check | `1` per `sanity_check_interval` steps | one reasoning wait |

  **`_child_timeout` (batch mode)** — `remaining = max_depth − depth`; sync
  mode keeps `(15 + 5×remaining) min` only:

  ```text
  (max_attempts + remaining) × 25h  +  (15 + 5×remaining) min
  ```

  **`derive_execution_timeout`** (pure, `forge.models`; sync = flat 48h). With
  `budget(w) = w×25h + w×10min + 1h`:

  ```text
  single-step:  w = max_attempts × (max_exploration_rounds + 1)
  planned:      w = (max_exploration_rounds + 1)
                  + MAX_PLAN_STEPS × max(max_step_attempts,
                                          max_sub_task_attempts + max_fan_out_depth + 1)
                  + (MAX_PLAN_STEPS ÷ sanity_check_interval  if interval > 0 else 0)
  ```

  Caveats: (a) `MAX_PLAN_STEPS = 25` bounds planned mode; it is a `max_length`
  validator on `Plan.steps`, so an oversized LLM plan is a retryable parse
  failure, not an unbounded timeout. (b) The parent's execution timeout must
  cover *awaiting* its fan-out children (each runs inside its own
