# T5.5 — Harness rebuild + replay tests

**Status:** NOT STARTED
**Phase:** 5 — Workflow consolidation (forge)
**Repos:** forge
**Depends on:** [T5.4](T5.4-split-the-monolith.md)
**Last updated:** 2026-07-08

## Problem

The workflow-test harness rests on 30 module-level `global` statements, 11
`_reset_*` functions, and roughly 1.5k LOC of quadruplicated activity
stubs inside a single 4,134-LOC `test_workflows.py`. The shared mutable
globals make `pytest-xdist` impossible and every new scenario expensive to
write. There is also no replay-test coverage guarding workflow
determinism across refactors.

## Background and Detailed Explanation

T5.5 rebuilds the workflow-test harness so tests can run in parallel
and stop leaking state into each other, and completes the replay-test
net that guards workflow determinism across all the Phase-5 rewrites.

**The problem.** The workflow tests are wired through shared mutable
state: 30 module-level `global` statements, 11 `_reset_*` functions
that each test must remember to call, and roughly 1,500 lines of
near-identical activity stubs copied four times over — all inside a
single 4,134-line `test_workflows.py`. Shared globals mean two tests
can never run at once, so `pytest-xdist` parallelism is impossible,
and every new scenario is expensive to add because it has to thread
through the global-and-reset machinery. The test file is a monolith
mirroring the code monolith T5.4 just dismantled.

**The fix.** Replace the globals with per-test state captured in
closures: a mutable `ScenarioState` object that
`build_stub_activities(scenario)` closes over to produce the named
`@activity.defn` stubs, and a `run_task(env, input, scenario)` helper
returning a frozen `HarnessResult`. With state local to each test, the
30 globals and 11 reset functions are deleted, the quadruplicated
stubs collapse, and the file splits into per-mode files. The
behavioral Temporal coverage that matters — retry, sanity
abort/revise, fan-out merge/conflict/child-failure, the S3-pointer
fetch path, the depth-2 regression — is preserved, not thinned.

**The buried gem (replay tests, per the 2026-07-08 amendment).** A
replay test re-runs a committed workflow history against the current
workflow code and fails if the code would now make a different
decision — the guard that a refactor did not accidentally change
workflow behavior in a way Temporal's durability cannot tolerate. The
scaffold is *introduced* by T4.1 alongside the new transport (the
riskiest rewrite must not land without a replay net), and each Phase-5
rewrite regenerates and replays its histories as it lands; T5.5
maintains and *completes* that scaffold rather than starting it. It
also adds two coverage categories the dense spec folds in: a
crash-recovery scenario (kill the worker mid-task, restart it, and
show it resumes and completes on the post-migration transport) that
substantiates the README's durability claim, and property-based
(hypothesis) tests over the edit engine's pure matching and
application functions (which may instead land with T0.5's edit-engine
work — whichever comes first).

**How you'll know it's done:** `pytest-xdist` parallelism is possible
because no shared globals remain, and the behavioral scenario count is
preserved or the reduction is justified.

## Scope

`tests/support/workflow_harness.py`:

- Per-test mutable `ScenarioState` captured by closures producing the
  named `@activity.defn` stubs (`build_stub_activities(scenario)`).
- `run_task(env, input, scenario) -> HarnessResult` (frozen).
- Split the 4,134-LOC test_workflows.py into per-mode files; delete 30
  `global` statements, 11 `_reset_*` functions, ~1.5k LOC of
  quadruplicated stubs.
- Keep behavioral Temporal coverage (retry, sanity abort/revise, fan-out
  merge/conflict/child-failure, S3-pointer fetch path, depth-2
  regression).
- Add the platform replay-test scaffold: committed histories under
  `tests/replay/` + one-command regeneration.
  *(Amended 2026-07-08: T4.1 now introduces the scaffold with the new
  transport — the riskiest rewrite must not land without a replay net —
  and each Phase 5 rewrite (T5.1–T5.4) regenerates and replays histories
  as it lands. This task maintains and completes the scaffold, not
  introduces it.)*
- *(2026-07-08 sweep)* Two additional test categories: property-based
  (hypothesis) tests over the edit engine's pure matching/application
  functions (per test-strategy.md:67; may live in T0.5 instead — whichever
  lands first), and one crash-recovery scenario (worker killed mid-task,
  restarted worker resumes and completes on the post-migration transport)
  substantiating README's durability claim.
