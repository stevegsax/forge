# T5.5 — Harness rebuild + replay tests

**Status:** DONE

**Repos:** forge
**Depends on:** [T5.4](T5.4-split-the-monolith.md)
**Last updated:** 2026-07-27

## Problem

The workflow-test harness rests on 30 module-level `global` statements, 11
`_reset_*` functions, and roughly 1.5k LOC of quadruplicated activity
stubs inside a single 4,134-LOC `test_workflows.py`. The shared mutable
globals make `pytest-xdist` impossible and every new scenario expensive to
write. There is also no replay-test coverage guarding workflow
determinism across refactors.

## Background and Detailed Explanation

T5.5 rebuilt the workflow-test harness so tests can run in parallel and
stop leaking state into each other, and completed the replay-test net
that guards workflow determinism across all the Phase-5 rewrites.

**The problem.** The workflow tests were wired through shared mutable
state: 55 module-level scenario bindings (lists, dicts, counters, and a
swapped function pointer), 19 `global` statements, 12 `_reset_*`
functions that each test had to remember to call, and 184
`@activity.defn` stubs over 26 distinct activity names — all inside a
single 6,179-line `test_workflows.py`. Shared state meant two tests
could never run at once, so `pytest-xdist` parallelism was impossible.
Worse than the parallelism cost, scenarios were scripted by *consumption
order*: `list.pop(0)` handed the next scripted outcome to whichever
activity call arrived first. With parallel fan-out children, arrival
order is a coin flip — the mechanism behind the known ~1/8
`TestRecursiveFanOutNestedFailure::test_failure_propagates` flake, and a
latent defect in several tests that stayed green only because their
outputs happened not to collide.

**The fix.** The globals were replaced with per-test state captured in
closures: a `ScenarioState` instance constructed inside each test, and
one canonical `build_activities(state)` factory producing all 26 named
`@activity.defn` mocks as closures over it. Scripting is keyed by
*identity* — a child's compound sub-task id, a step's id, a task id —
never by arrival order, and the scripts a test hands in are read-only
(sequential consumption uses an internal cursor). The batch lane
recovers a call's identity from its `request_id`, the same way the real
transport selects a waiter's result line. The monolith split into
per-mode files under `tests/workflows/`, and all 100 behavioral
scenarios were preserved class for class; the flake was fixed at its
mechanism and proven by a 20/20 repeated run.

**The buried gem (replay tests, per the 2026-07-08 amendment).** A
replay test re-runs a committed workflow history against the current
workflow code and fails if the code would now make a different decision
— the guard that a refactor did not accidentally change workflow
behavior in a way Temporal's durability cannot tolerate. The scaffold
was *introduced* by T4.1 alongside the new transport (the riskiest
rewrite must not land without a replay net), and each Phase-5 rewrite
regenerated and replayed its histories as it landed; T5.5 completed it,
taking the committed set from 6 histories to 13 — the four it owed
(planned step, depth-2 nested gather, exploration, sanity check) plus
all three stretch items (conflict resolution, sync-lane planner,
worktree-reset retry). Every new history is a new file; the six that
existed passed unregenerated throughout, which is the proof the rebuild
touched no workflow code. The task also shipped the crash-recovery
scenario the dense spec folded in — a worker killed mid-task, a second
worker started, the run finishing on it — which substantiates the
README's durability claim for the first time. The property-based
(hypothesis) category the spec also named was consumed by T0.5, which
landed `tests/test_output_properties.py` first.

**How you know it's done:** `pytest-xdist` runs the workflow suites on
14 workers (demonstrated, with the dependency added), no module-level
mutable containers remain, the behavioral scenario count is unchanged at
100 (plus the new crash-recovery scenario), and `test_workflows.py` no
longer exists.

### Key design decisions

1. **One key space per activity, keyed by workflow identity (D3).**
   `transitions` / `validations` are keyed by the *validate identity* —
   `ValidateOutputInput.task_id`, which is the task id for a root/planned
   step and the compound `parent.sub.child` id for a sub-task or nested
   node. `llm_responses` are keyed by the *call identity* —
   `compound(task_id, sub_task_id)`, else `step_id`, else `task_id`, read
   off the `AssembledContext`. Conflict/sanity responses are keyed by
   their input's `task_id`. Unlisted keys fall back to a default.
2. **Scripts are immutable; cursors are separate.** A test hands the
   harness `Mapping[str, Sequence[...]]` and the harness never mutates
   it: consumption is an internal per-key cursor. No `pop(`, no
   `.clear()`, no shared queue. Within one key, calls come from a single
   sequential workflow, so cursor order is the workflow's own
   deterministic activity order — never a scheduler race. The
   sticky-terminal semantics of `_validation_for_transition` are
   preserved per key.
3. **Batch-lane identity via `request_id`.** `parse_llm_response` receives
   only `task_id`, which cannot distinguish two fan-out children. The
   submit mock records `request_id -> BatchSubmitInput`, the fetch mock
   returns a body naming the `request_id`, and the parse mock recovers
   the originating context — exactly how the real transport selects a
   waiter's line. This is what lets the legacy counter-based parse
   handlers (`% 2`, `% 3`, `% 4`) become keyed lookups.
4. **The lane is never changed by migration.** Every legacy section runs
   in **batch** mode (`sync_mode` defaults to `False`, and their activity
   sets register the batch trio) — the sync `call_llm` mocks in those
   sections are dead code. Flipping them to `sync_mode=True` would change
   what each test proves, so D6 is applied to *new* tests only; migrated
   tests keep their transport exactly.
5. **Uniform call-log vocabulary.** The canonical mocks log
   `name` or `name:detail` with one format per activity
   (`create_worktree:<task_id>`, `commit:<message or status>`,
   `parse_llm_response:<output_type>`, …). `ScenarioState` exposes
   `called()`/`count()`/`entries()` so relocated assertions keep their
   exact meaning. One deliberate deviation, driver-owned and noted in
   Development Notes: the recursive section's parse handler logged
   `"call_llm"` for a *batch* parse, which collides with the batch
   section's `assert "call_llm" not in log` ("the sync path was not
   used"); the migrated assertion names the batch-lane entry instead and
   proves the same thing.

**Design decisions taken during implementation** (beyond the Plan):

1. **Two key spaces, not one.** `validate_output` sees only
   `ValidateOutputInput.task_id`, so transitions are keyed by that (task
   id, or compound sub-task id); generation responses are keyed by the
   *call* identity read off the assembled context. A planned run's steps
   therefore share one transition key and different response keys. Both
   are documented in the harness module docstring's table.
2. **Scripts are immutable; cursors are separate.** Tests hand in
   `Mapping`/`Sequence` values the harness never mutates; sequential
   consumption uses an internal `_cursors` dict. There is no `pop(`, no
   `.clear()`, and no handler-pointer reassignment anywhere in the new
   files. The four per-file response tables are `MappingProxyType`, so
   read-only is structural rather than promised.
3. **Batch-lane identity via `request_id`.** `ParseResponseInput` carries
   only a `task_id`, which cannot tell two fan-out children apart. The
   submit mock records `request_id → BatchSubmitInput`, the fetch mock
   returns a body naming that `request_id`, and the parse mock recovers
   the originating context — the same selection the real transport does
   with a custom_id. This is what let every counter-based parse handler
   become a keyed lookup.
4. **Discovery: every legacy scenario ran on the batch lane.**
   `sync_mode` defaults to `False` and the old activity lists all
   registered the batch trio, so the sync `call_llm` mocks in those
   sections were dead code — the "call_llm" entries in their call logs
   were written by the *parse* handler. Migration therefore did not
   change any test's lane (guide D6 is applied to new tests only, which
   use `sync_mode=True`). Consequence: three assertion families had to be
   renamed to the batch-lane entry they actually observed — `"call_llm"`
   → `"parse_llm_response:LLMResponse"` (recursive depth-limit),
   `"call_conflict_resolution"` →
   `"parse_llm_response:ConflictResolutionResponse"` (fan-out and nested
   conflict), `"call_sanity_check"` →
   `"parse_llm_response:SanityCheckResponse"` (three sanity tests). Each
   carries an inline comment; each proves exactly what it proved before.
   This is the only assertion-text change class in the migration.
5. **The four T5.2/T5.3 factory sections moved verbatim** into
   `tests/support/block_mocks.py` + three test files. They already used
   the target pattern and their tests assert on exact call *sequences*;
   folding them into the canonical set would have changed those
   assertions (D5). The rename to public names (`step_block_activities`
   …) is the whole diff, plus `_PASS_VALIDATION`/`_LLM_RESPONSE` now
   coming from the harness.

**Payload deviations (all verified unobserved before accepting).** The
old counter-based handlers interpolated the call count into
`explanation` strings (`f"LLM call #{n}"`); keyed responses use fixed
strings. The sanity-check scenarios no longer script per-step file names
(`file{n}.py`) because nothing asserted on them, so they use the harness
default. The recursive depth-limit leaf now returns `leaf.py` rather than
the `gc1.py` the `% 3` counter happened to produce. File paths and
contents that *are* asserted on are byte-identical throughout.

**Finding — a test comment that overstated its proof.** The old
`TestBatchPlanned` called `_PLANNER_THINKING = ThinkingPolicy(enabled=True,
effort="high")` a "distinctive planner thinking policy — proves
passthrough rather than coincidentally matching some other default." It is
neither distinctive (it is exactly `ThinkingPolicy()`'s default) nor
threaded from the assemble activity: `_plan_task` overwrites the assembled
`PlannerInput.thinking` with `ForgeTaskInput.thinking` before dispatch. The
assertion is kept as-is — it does prove the task-level policy reaches the
submit — with the comment corrected to say so.

**Crash recovery.** `tests/workflows/test_crash_recovery.py` starts a
run, blocks `assemble_context` forever, shuts the worker down (cancelling
that activity out from under the workflow), then starts a second worker
against the same task queue and awaits the same handle: the run completes
SUCCESS, the stranded activity is re-executed exactly once, and the
worktree created by the first worker is not re-created. It asserts the
workflow was still `RUNNING` at the kill, so it cannot pass vacuously.
Both workers set `max_cached_workflows=0`: with sticky execution on,
Temporal routes the run's later workflow tasks back to the dead worker's
private sticky queue, and that queue only drains after its
schedule-to-start timeout — a delay the time-skipping server does not
fast-forward, so the test sat in real time (diagnosed by probe: the
history's last event was a `WORKFLOW_TASK_SCHEDULED` nobody polled).
Disabling the cache puts every workflow task on the shared queue, which is
where a real restarted worker picks the run up once that timeout passes.

**Replay histories: 6 → 13.** All four hard ACs plus all three stretch
items landed, as *new files*; `git diff` over `tests/replay/histories/`
is empty for the pre-existing six, which passed unregenerated at every
