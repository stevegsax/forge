## Problem

Output shaping today uses forced tool use via sax-llm's provider stack and
a string-keyed registry. The review verified that structured outputs are
GA, work in the Message Batches API, and compose with prompt caching — so
forced tool use can retire. `messages.parse` is sync-only, which means the
platform library must own **both** lanes: a sync client and the batch
request-body builder + helpers that Plan B's design forgot (forge is
batch-first).

## Background and Detailed Explanation

"Structured outputs" is the modern way to make the model return a
validated object instead of free text: you hand the provider a JSON
schema and it constrains its own generation to match, returning data
that already parses into your Pydantic type. It replaces "forced tool
use" — the older trick of defining a throwaway "tool" purely so the
model's arguments arrived as shaped JSON — which cost a tool-definition
detour on every call and needed a string-keyed registry to recover the
output class at parse time. T3.1 built the one place the whole platform
gets structured outputs from: `sax_platform.llm`.

The load-bearing word in the scope is **both**. The SDK's ergonomic
`messages.parse` helper is sync-only, but forge is batch-first (the
Batch API returns results up to 24h later at half price). So a sync
client alone was useless here; the library had to also own the batch
lane the original design omitted — a pure request-body builder that
turns model/system/messages/schema into a request dict, plus the
submit/status/fetch helpers. Both lanes share one classifier core so
they agree on what a result means.

The real depth of this task is the **failure surface**. Before it, a
refusal, a `max_tokens` truncation (the model ran out of output budget
mid-object), and a plain text-only reply all collapsed into the same
misleading Pydantic `ValidationError` — indistinguishable from a
genuine schema mismatch. On the batch lane that was expensive: after a
paid up-to-24h round-trip, the parse would then retry deterministically
on the identical stored bytes, forever. The fix was to check
`stop_reason` **before** parsing, turning those into typed outcomes —
`LLMRefused`, `LLMTruncated` (carrying the partial text and the cap it
hit), and `LLMSchemaMismatch` — so the misleading-error collapse became
unrepresentable. Clients were also constructed with `max_retries=0`,
because retries belong to Temporal's activity RetryPolicy, not stacked
underneath it by the SDK; and `max_tokens` became required per call,
since generation prompts routinely exceed the old hard
4096-output-token default.

Two findings from the as-shipped work are worth keeping. First, the
cache pre-work went nowhere useful because the production `interactions`
table was **empty** — zero rows ever recorded — so the "is our prompt
caching net-negative?" question was unmeasurable from data; the decision
locked to emitting no cache breakpoints by default, with caching an
explicit per-call opt-in. Second, the sync lane shipped as
`messages.create` + `output_config.format` rather than the literal
`messages.parse` the scope named: `parse` couples transport and parsing,
so a refusal or truncation could surface as a parse failure *before*
`stop_reason` was classified — defeating the whole point. A genuine bug
also surfaced only because the two lanes were built independently: the
`anthropic` SDK did not model `stop_details` on `Message`, so real wire
refusals carried the refusal category as a plain dict, and the first
implementation's attribute-only read silently dropped it.

## Scope

`sax_platform.llm`: `AnthropicLLM(client)` with
`complete[T: BaseModel](..., output_type: type[T]) -> Completion[T]` on
`client.messages.parse`, `complete_schema(...)` (JSON-schema dict path),
`complete_text(...)`; frozen `Completion[T]` with token/cache telemetry;
**plus the batch lane Plan B forgot**: pure batch request-body builder
(model, system, messages, `output_config.format` schema → request dict),
batch submit/status/results helpers. Verified: structured outputs are GA,
work in the Batch API, compose with caching (use 1h-TTL cache_control in
batches; hits are best-effort 30–98%).

### Amendments (2026-07-08)

The client must own the failure surface, not just the happy path:

- Construct provider clients with `max_retries=0` — retries belong to
  Temporal's activity RetryPolicy (port the rationale from the dead
  `forge/llm_client.py:258-264`; see T1.1's amendment).
- Surface `stop_reason` on both lanes as typed outcomes: refusal,
  `max_tokens` truncation, and text-only responses must be distinguishable
  from schema-validation failures. Today all three collapse into misleading
  ValidationErrors; on the batch lane the parse then retries
  deterministically on identical stored bytes after a paid up-to-24h
  round-trip.
- Per-call output-token budget: no hard 4096 default. Call sites must be
  able to size `max_tokens`; generation prompts demand complete file
  contents that routinely exceed 4096 output tokens.

**Capture-sweep additions (2026-07-08):**

- **Cache breakpoints must earn their premium.** Today's cache_control
  placement is plausibly net-negative: breakpoints on a sub-1024-token
  tool schema (never cacheable) and one monolithic system block whose
  volatile tail busts reuse; under D79 single-request batches nothing
  shares a prefix within the TTL — near-every call pays the 1.25× write
  premium for entries nothing reads. The new client places breakpoints
  only where the cumulative prefix meets the model's minimum cacheable
  length and reuse is expected. Pre-work: query the interactions store
  for `cache_read_input_tokens` vs `cache_creation_input_tokens` now
  (review rec 7); if reads ≈ 0, disabling cache_control at forge call
  sites is a conflict-free interim mitigation.
- **Re-verify the API facts at execution time.** The "Verified:
  structured outputs are GA, work in the Batch API, compose with caching"
  claims above are the one-time 2026-06-10 verification whose external
  evidence is lost. Mirror T2.1's wheel-matrix pattern: re-verify
  `output_config.format` batch behavior and `messages.parse` semantics
  against the live API before building on them.

### Pre-work results (details in Development Notes)

- **Rec 7 (cache telemetry):** the production `interactions` table is
  **empty** — zero rows ever recorded in the externalized store. The
  net-negative-caching hypothesis is unresolvable from data, and there
  is zero evidence of cache reads. Decision: the new client emits **no
  cache breakpoints by default**; caching is explicit per-call opt-in.
- **Live API re-verification:** run at execution time against the real
  API (sync `messages.parse` semantics incl. truncation shape;
  `output_config.format` in a real batch incl. a truncated item and a
  shared ≥4096-token cached system prefix).
- **Cache minimums moved:** current models' minimum cacheable prefix
  is 2048–4096 tokens depending on model (not the 1024 the June scope
  assumed); 1h-TTL writes cost 2× (not 1.25×). Both harden the
  "breakpoints must earn their premium" rule.

### Design

**Package** `libs/sax-platform`, import name `sax_platform`, py.typed,
mypy strict + 85% coverage gate + ruff from day one (the T2.2/T2.3
recipe applied at birth); workspace member (not yet a dependency of
anything, like ocr); added to import-linter `root_packages` with
contracts: never imports forge/pbook/ocr, independent of sax_llm and
forge_contracts. Depends on `anthropic` + `pydantic` only.

**Modules** (FCIS: pure core, I/O at the edges):

- `llm/models.py` — frozen generic `Completion[T]` (`output: T`,
  `model`, `stop_reason`, `input_tokens`, `output_tokens`,
  `cache_creation_input_tokens`, `cache_read_input_tokens`,
  `request_id`); outcome classification as a **pure function**
  `classify(message) -> Classified` shared by both lanes; typed
  failures carrying the same telemetry: `LLMRefused` (never worth a
  Temporal retry), `LLMTruncated` (carries the partial text and the
  `max_tokens` that was hit), `LLMSchemaMismatch` (validation failed
  on complete output; carries raw text). stop_reason checked **before**
  parsing — the June review's misleading-ValidationError collapse
  becomes unrepresentable.
- `llm/cache.py` — pure: `CacheSpec(ttl)` opt-in, per-model minimum
  prefix table (4096 opus/haiku-4-5, 2048 fable/sonnet-4-6, 1024
  sonnet-4-5; unknown → 4096), chars/4 heuristic; placement only when
  the cumulative prefix clears the model minimum, else the breakpoint
  is silently omitted (tested).
- `llm/client.py` — `AnthropicLLM(client: AsyncAnthropic)`; factory
  `make_client()` constructs with `max_retries=0` (Temporal owns
  retries; asserted by test). `async complete[T: BaseModel](...,
  output_type, model, max_tokens, system=None, cache=None) ->
  Completion[T]` on `messages.parse`; `complete_schema(...)` (JSON
  schema dict → `Completion[dict[str, Any]]`); `complete_text(...)
  -> Completion[str]`. `max_tokens` is **required** everywhere — no
  default (generation output routinely exceeds the old 4096 cap).
  Failures raise the typed exceptions (activities map them onto
  Temporal RetryPolicy non-retryable types).
- `llm/batch.py` — pure `build_batch_request(custom_id, *, model,
  max_tokens, messages, system=None, output_type|output_schema=None,
  cache=None) -> dict` (request-body builder, D90); thin I/O helpers
  `submit_batch`, `get_batch_status`, `fetch_batch_results(...,
  output_types: Mapping[custom_id, type]) -> list[BatchItemResult]`
  where each item is `Completion[T]` or a typed failure **value**
  (same classifier core; failures-as-values because a batch fetch
  processes N independent items — the sync lane's exceptions don't
  compose across items).

**Testing:** mocked transport at the httpx layer (`http_client=
DefaultAsyncHttpxClient` with `httpx.MockTransport` returning canned
wire JSON) so the SDK's real serialization runs — not SDK-object
mocks. Both lanes: success, refusal, truncation, schema mismatch,
cache-fields recorded (repeated-prefix scenario asserts
`cache_read_input_tokens > 0` lands in `Completion`), no-breakpoint-
under-minimum, `max_retries==0` assertion.
