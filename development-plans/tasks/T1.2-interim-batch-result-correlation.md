## Problem

**Critical, live:** `batch_result_received` appends to `list[BatchResult]`
and consumers take by count (`wait_condition(len>0)` + `pop(0)` —
workflow_blocks.py:119-123, ocr workflow_store.py:62). At-least-once signal
delivery means a duplicate/stale signal becomes the *wrong call's* result.

## Scope

- Replace the list with `dict[str, BatchResult]`.
- Handler = `setdefault(result.request_id, result)`.
- `batch_submit_and_wait` waits on **its own** `request_id`; never pop.
- Apply in ForgeTaskWorkflow, ForgeSubTaskWorkflow,
  TranscriptIngestionWorkflow, ocr OcrStoreWorkflow (~20 lines each).

## Plan

Correlate batch results by `request_id` instead of by arrival count. A batch
result is delivered by an at-least-once Temporal signal, so a duplicate or a
stale signal from a *different* call currently satisfies `len(list) > 0` and is
popped as the wrong call's result. Key the buffer by `request_id` and have each
waiter read its own id.

Production changes (buffer `list[BatchResult]` → `dict[str, BatchResult]`):

- `workflow_blocks.batch_submit_and_wait` — take `dict[str, BatchResult]`, wait
  on `submit_result.request_id in batch_results`, read by that key, never pop.
  `generation_dispatch` / `conflict_resolution_dispatch` signatures follow.
- `ForgeTaskWorkflow`, `ForgeSubTaskWorkflow` (workflows.py) — `dict` buffer +
  `setdefault(result.request_id, result)` handler (first delivery wins).
- `TranscriptIngestionWorkflow` (ingestion_workflow.py) — same buffer + handler.
- `OcrStoreWorkflow` (ocr) — same buffer + handler; it already knows its own
  `input.request_id`, so it waits on that key and reads it.

Test changes: the two self-signaling submit mocks (test_workflows.py,
test_e2e.py) and the planned-batch submit mock hard-coded a *constant*
`request_id`. That was harmless under FIFO-by-count but produces stale reads
under id-keying whenever a workflow makes ≥2 batch calls (planner+generation,
retries, fan-out). The real `submit_batch_request` mints a fresh `uuid4` per
call — update the mocks to mint per-call ids so they mirror production.

- **Buffer swap, per repo.** forge `workflow_blocks.batch_submit_and_wait` now
  keys on `submit_result.request_id` (wait on `request_id in batch_results`,
  read by key, no pop); `generation_dispatch` / `conflict_resolution_dispatch`

  (workflows.py), `TranscriptIngestionWorkflow` (ingestion_workflow.py), and

  `setdefault(result.request_id, result)`. `OcrStoreWorkflow` already carries
  its own `input.request_id`, so it waits on and reads that exact key.
- **Verified request_id is on the wire model.** `BatchResult.request_id` already
  exists in forge-contracts; no contracts change needed (T1.3 owns contracts).
  The poller sets `request_id = entry.custom_id` on success and `job["id"]` on
  failure (batch_poll.py), and the real `submit_batch_request` mints
  `str(uuid.uuid4())` per call (batch_submit.py:73), so signal and submit ids
  match in production.
- **Unnamed instance of the pattern — the test mocks.** The task named four
  workflows, but the same count-based assumption lived in the test *mocks*: the
  two self-signaling submit mocks (test_workflows.py, test_e2e.py) and the
  planned-batch submit mock hard-coded a single constant `request_id`. Harmless
  under FIFO-by-count, but under id-keying (which never pops) the second batch
  call in a workflow re-reads the first call's result. Since `sync_mode`
  defaults to **False** (batch is the default path), the planned and fan-out
  e2e scenarios exercise this with ≥2 batch calls and would have broken. Fixed
  by minting a per-call id in each mock (uuid4 for the self-signaling ones;
  `f"req-bp-{output_type_name}"` for the planned mock, whose two signals were
  updated to match) — mirroring the real activity. This is not scope creep: the
  mocks were coupled to the old broken semantics.
- **Checked but clean:** ocr `OcrGatherWorkflow` uses a `set[str]` keyed by
  `chunk_document_id` with `issubset` — already idempotent under at-least-once
  delivery, not the count-based bug, left untouched.
- **Regression tests.** forge
  `TestBatchSingleStep::test_batch_result_correlated_by_request_id`: a wrong
  request's error result + a duplicate of it arrive before the correct result,
  and a stale duplicate of the correct id arrives after — workflow still
  succeeds (old code would pop the wrong error and fail). ocr
  `TestOcrStoreWorkflow::test_result_correlated_by_request_id`: same shape,
  asserting the store ran for `r1` and no failure status was written.

  coverage 87.84% (gate 85%). ocr `uv run pytest -q`: 48 passed, 3 deselected
  (ocr has no coverage gate). Ruff clean on all changed files; the only repo
