## Problem

**Critical, live:** `batch_result_received` appends to `list[BatchResult]`
and consumers take by count (`wait_condition(len>0)` + `pop(0)` —
workflow_blocks.py:119-123, ocr workflow_store.py:62). At-least-once signal
delivery means a duplicate/stale signal becomes the *wrong call's* result.

## Background and Detailed Explanation

This was a deliberate stopgap, and it is worth understanding why a fix
known to be temporary was still worth building. The bug was live and it
corrupted results: a completed batch was delivered back to its waiting
workflow by a Temporal **signal**, and the waiter took the next result
off a list by arrival count (`wait_condition(len>0)` then `pop(0)`).
Temporal signals are *at-least-once* — the same signal can arrive twice,
and a stale signal from a different batch call can arrive at all — so a
duplicate or misordered delivery would be popped as some other call's
answer. In batch mode, which is the default path, any workflow that
makes two or more batch calls (planner plus generation, a retry, a
fan-out) was exposed to silently attributing the wrong LLM output to a
step.

The fix was small and surgical: replace the count-keyed list with a
`dict[str, BatchResult]` keyed by `request_id`, have the handler
`setdefault` (first delivery wins, duplicates are no-ops), and have each
waiter read *its own* id rather than whatever arrived. It applied
identically across the two forge workflows, the ingestion workflow, and
ocr's store workflow. The unnamed instance of the same bug lived in the
test mocks, which had hard-coded a single constant `request_id` —
harmless under FIFO-by-count but a stale read under id-keying — so they
were updated to mint a fresh id per call, mirroring the real activity.

Why build it knowing it would die? Because the correctness hole was live
and Phase 4 was still several phases out; leaving results misattributed
for that whole window was not acceptable. The entire signal path this
task hardened was later deleted by T4.1 (2026-07-19), which replaced
signal delivery with per-workflow timer-loop polling — the requester
polls for and reads its own result, so there is no routing to
misattribute and no at-least-once hazard at all. The stopgap did its job
for the interim and is now gone.

## Plan

Correlate batch results by `request_id` instead of by arrival count. A batch
result is delivered by an at-least-once Temporal signal, so a duplicate or a
stale signal from a *different* call currently satisfies `len(list) > 0` and is
popped as the wrong call's result. Key the buffer by `request_id` and have each
waiter read its own id.

Production changes (buffer `list[BatchResult]` → `dict[str, BatchResult]`):

- `workflow_blocks.batch_submit_and_wait` — take `dict[str, BatchResult]`, wait
  on `submit_result.request_id in batch_results`, read by that key, never pop.
  `generation_dispatch` / `conflict_resolution_dispatch` signatures follow.
- `ForgeTaskWorkflow`, `ForgeSubTaskWorkflow` (workflows.py) — `dict` buffer +
  `setdefault(result.request_id, result)` handler (first delivery wins).
- `TranscriptIngestionWorkflow` (ingestion_workflow.py) — same buffer + handler.
- `OcrStoreWorkflow` (ocr) — same buffer + handler; it already knows its own
  `input.request_id`, so it waits on that key and reads it.

Test changes: the two self-signaling submit mocks (test_workflows.py,
test_e2e.py) and the planned-batch submit mock hard-coded a *constant*
`request_id`. That was harmless under FIFO-by-count but produces stale reads
under id-keying whenever a workflow makes ≥2 batch calls (planner+generation,
retries, fan-out). The real `submit_batch_request` mints a fresh `uuid4` per
call — update the mocks to mint per-call ids so they mirror production.
