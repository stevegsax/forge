# T5.5 harness migration guide — directions, examples, rationale

**Audience.** Three readers: the `implementation-driver` (writes the
harness core, the flake-class fix, and everything on the driver-only
list; reviews all delegated work against this guide), `code-writer`
(executes the bulk migration batches following the patterns here — when
a case doesn't match a pattern in this guide, stop and hand it back
rather than improvising), and reviewers (the checklist in §7 is the
review). Written 2026-07-27 in the planning session at owner direction:
every decision is explicit, with rationale, so authors and reviewers
work from the same context instead of reverse-engineering intent.

**Scope boundary (hard).** This migration is **test-side only**. Zero
changes to `src/forge/**` or to `tests/replay/**`. The committed replay
histories must pass UNREGENERATED at every step — the harness rebuild
cannot change a workflow command sequence because it never touches
workflow code. If a scenario appears to require a source change to be
testable, that is a finding for the driver, not a change.

## §1 The two patterns

### Current (what you are migrating away from)

Scenario scripting lives in module-level mutable containers, mutated by
`_reset_*` functions and read by mock activities at call time
(`tests/test_workflows.py:114-125, 228-229, 2549-2555`):

```python
_parse_handler: Callable[[ParseResponseInput], ParsedLLMResponse] | None = None
_CAPTURED_SUBMIT_INPUTS: dict[str, BatchSubmitInput] = {}
_call_log: list[str] = []
_transition_sequence: list[str] = []          # popped by _validation_for_transition
_RECURSIVE_LLM_RESPONSES: list[LLMResponse] = []   # .pop(0) per call


@activity.defn(name="parse_llm_response")
async def mock_parse_response(input: ParseResponseInput) -> ParsedLLMResponse:
    assert _parse_handler is not None, "No parse handler set — call _reset_*() first"
    return _parse_handler(input)
```

Three structural defects, all visible in that excerpt:

1. **Consumption-order scripting.** `list.pop(0)` hands the next
   scripted outcome to *whichever call arrives first*. With parallel
   child workflows, arrival order is scheduler-dependent — this is the
   entire mechanism of the ~1/8
   `TestRecursiveFanOutNestedFailure::test_failure_propagates` flake
   (the terminal token is meant for `gc2`; sometimes `gc1` draws it).
   The defect is broader than the one flaky test: the recursive
   fallback handler assigns outputs by a modulo call counter
   (`_RECURSIVE_PARSE_LLM_COUNT % 3`, `test_workflows.py:2592-2607`),
   so even *passing* tests depend on child scheduling order and stay
   green only because their outputs happen to be conflict-free.
2. **Inter-test coupling.** A test that forgets its `_reset_*` inherits
   the previous test's scenario. The
   `assert _parse_handler is not None … call _reset_*() first` message
   is the fossil record of this failure mode being hit and papered
   over.
3. **Stub multiplication.** 184 `@activity.defn` decorators over 26
   distinct activity names (worst case: 16 copies of one activity),
   because each section re-stubs the world to bind it to that section's
   globals. Divergence between copies is the same disease Phase 5
   removed from the source tree.

### Target (what you are migrating to)

One `ScenarioState` instance per test, constructed in the test
function; mock activities are **closures over that instance**, built by
one canonical factory in `tests/support/workflow_harness.py`. Skeleton
(the driver owns the real one; field names here are illustrative, the
*shapes* are normative):

```python
@dataclass
class ScenarioState:
    """Per-test scripting + capture. Constructed in the test, never shared."""

    # Scripting: keyed by scope, never by consumption order.
    # Key = the compound task id carried on the activity input
    # (ValidateOutputInput.task_id, e.g. "parent.sub.st1"); "" = default.
    transitions: dict[str, list[str]] = field(default_factory=dict)
    llm_responses: dict[str, list[LLMResponse]] = field(default_factory=dict)
    conflict_responses: list[ConflictResolutionCallResult] = field(default_factory=list)

    # Capture: assertion surfaces, replacing _CAPTURED_* / _call_log.
    call_log: list[str] = field(default_factory=list)
    submit_inputs: dict[str, BatchSubmitInput] = field(default_factory=dict)

    def next_transition(self, task_id: str) -> list[ValidationResult]:
        """Keyed successor of _validation_for_transition — same sticky-terminal
        semantics, per key: a trailing failure_terminal token stays in the
        sequence so every remaining attempt for THAT task id keeps failing."""
        ...


def build_activities(state: ScenarioState) -> list[Callable]:
    """The one canonical mock set: every activity name the workflows call,
    each a closure over `state`. Tests register this list on their Worker,
    plus per-test extras/overrides appended AFTER (later registration wins
    is NOT a Temporal semantic — overrides replace entries in the list)."""
    @activity.defn(name="validate_output")
    async def mock_validate_output(input: ValidateOutputInput) -> list[ValidationResult]:
        return state.next_transition(input.task_id)
    ...
    return [mock_validate_output, ...]
```

Usage shape in a migrated test:

```python
async def test_failure_propagates(env: WorkflowEnvironment) -> None:
    state = ScenarioState(
        transitions={"parent.sub.st1.sub.gc2": ["failure_terminal"]},  # keyed: gc2, not "second pop"
    )
    async with Worker(env.client, task_queue=FORGE_TASK_QUEUE,
                      workflows=[ForgeSubTaskWorkflow],
                      activities=build_activities(state)):
        result = await env.client.execute_workflow(...)
    assert ...  # same assertions as before, now against state.call_log etc.
```

## §2 Decisions and rationale

Each decision is binding for this migration. "Because the driver said
so" is not a rationale — these are the actual reasons, so reviewers can
detect violations *and* recognize legitimate exceptions.

- **D1 — State lives on a per-test instance; closures bind it.**
  Rationale: module state is what makes scenario assignment global and
  order-dependent; an instance created inside the test function is
  unreachable from any other test by construction. Mock activities run
  worker-side (outside the workflow sandbox), so closures are legal —
  the sandbox restriction applies to workflow code reading module
  state, not to activities holding references.
- **D2 — Mocks stay by-name: `@activity.defn(name="…")`.** Rationale:
  workflow code calls activities by string name; the committed replay
  histories and the real worker registration match on those names. A
  rename, or a switch to direct function references, silently unbinds
  the mock — the workflow then schedules an unregistered activity and
  the test hangs to its timeout instead of failing at the point of
  error. Every activity name in the canonical set must be byte-equal to
  the name the workflow uses.
- **D3 — Scripting is keyed by identity, never by arrival order.** Key
  = the compound task id (or batch id for the poll counter, mirroring
  `tests/replay/regenerate.py:102`'s already-safe pattern). Rationale:
  parallel children make arrival order a coin flip; identity is stable
  under any scheduling. This is the *mechanism* fix for the flake, not
  a rerun band-aid. The sticky-terminal semantics of
  `_validation_for_transition` (`test_workflows.py:197-207`) must be
  preserved per key: a terminal token keeps that child failing through
  `max_attempts`.
- **D4 — One canonical activity set, parameterized by state.**
  Rationale: 184 stubs → ~26. Per-test behavior differences are data
  (fields on `ScenarioState`) or explicit overrides appended to the
  list — never a fourth copy of the stub. The T5.2/T5.3 lesson applies
  to test code verbatim: hand-synchronized copies drift.
- **D5 — Migration is 1:1: same scenarios, same assertions.**
  Rationale: the rebuild's correctness proof is that it changes *how*
  scenarios are expressed, not *what* is proven. Scenario count is an
  AC. If an existing assertion looks wrong, weak, or redundant during
  migration: flag it in the hand-back note; do not fix, strengthen, or
  delete it in the same change. (One planned exception, driver-owned:
  the flake test's scripting changes from ordered to keyed — that IS
  the fix, and its assertion stays identical.)
- **D6 — `sync_mode=True` stays the default for migrated and new
  tests**; the batch trio (`submit_batch_request` echoing the minted
  request_id, `batch_status`, `fetch_batch_result` —
  `test_workflows.py:128-149`) is registered only in scenarios that
  exercise the batch transport. Rationale: the batch-first production
  default otherwise routes every test through mocks it didn't set up
  (CLAUDE.md Test Patterns; live examples at `test_workflows.py:5171`).
- **D7 — The file splits by workflow mode; the harness is a support
  module.** Target layout: `tests/support/workflow_harness.py`
  (ScenarioState + `build_activities` + shared builders like
  `_make_parsed`), and `tests/workflows/test_single_step.py`,
  `test_planned.py`, `test_fan_out.py`, `test_batch_transport.py`,
  `test_interactions.py` (driver may adjust the partition; one mode's
  tests never import another test module — shared needs go to the
  support module). Rationale: 6,180 lines in one file is itself a
  maintenance defect, and the rebuild is the only cheap moment to fix
  it. `rg` confirms no other test file imports from `test_workflows`
  today, so the split has no external blast radius. `conftest.py`
  keeps the session-scoped `env = temporal_env` re-export — request
  only `env`, never both names (the fixture cache is per-name; two
  names = two time-skipping servers).
- **D8 — Frozen test *data* may stay at module level; mutable state may
  not.** `_TASK_INPUT`, `_LLM_RESPONSE` (`test_workflows.py:104-107`)
  and friends are read-only fixtures — migrating them to instances is
  churn without benefit. The test for "is this state?": is it ever
  mutated, cleared, popped, or reassigned? If yes → ScenarioState. If a
  test needs a variant of a constant, it uses
  `model_copy(update={...})` — never in-place mutation of the shared
  constant.
- **D9 — Capture surfaces move onto the instance.** `_call_log`,
  `_CAPTURED_SUBMIT_INPUTS`, `_SUBMIT_OUTPUT_TYPES` become
  `state.call_log` / `state.submit_inputs` / etc. Rationale: same
  isolation argument as D1, and it makes "what did this test observe"
  local to the test that asserts on it.
- **D10 — `pytest-xdist` lands with the rebuild (dev dependency), and
  the parallel-run AC is demonstrated, not asserted.** Rationale: the
  spec's headline AC ("xdist now possible") is unfalsifiable while the
  dep is absent, and `docs/operations/test-strategy.md:67` already
  claims it's available. Demonstration = one green
  `uv run pytest -n auto --no-cov tests/workflows/` run recorded in the
  task file. (Coverage under xdist can misbehave; the gate run stays
  serial.)

## §3 Good / bad examples

**Example 1 — ordered scripting (the flake's family).**

```python
# BAD (current): whichever child's validate_output runs first draws the token
_reset_recursive_mock_state(transitions=["success", "failure_terminal"])

# BAD (superficial migration): same race, now wearing a dataclass
state = ScenarioState(transition_queue=["success", "failure_terminal"])  # still popped in arrival order

# GOOD: the outcome is bound to the child it's about
state = ScenarioState(transitions={
    "fanout-parent.sub.st1.sub.gc2": ["failure_terminal"],
})  # gc1 and leaf fall through to the default (pass)
```

The middle form is the one to watch for in review: moving a list onto
the instance without re-keying it migrates the *storage* and keeps the
*bug*.

**Example 2 — the handler-pointer dispatch.**

```python
# BAD (current): a module-global function pointer swapped per section
_parse_handler = _single_step_parse_handler

# BAD: keeping the pointer but storing it on the instance — still one
# opaque callable per test doing hidden multi-way dispatch on output_type
state.parse_handler = _single_step_parse_handler

# GOOD: the canonical parse mock dispatches on input.output_type_name
# itself and reads canned responses from keyed state; sections stop
# owning private handlers at all
async def mock_parse_response(input: ParseResponseInput) -> ParsedLLMResponse:
    return state.parsed_for(input.output_type_name, input.task_id)
```

**Example 3 — counter-based poll scripting (keep the good pattern).**
`tests/replay/regenerate.py:102-110` already keys its
in-progress-before-ended counters by `batch_id`. That pattern is
correct — reproduce it on the instance (`state.status_polls:
dict[str, int]`). Do not "simplify" it to a single shared counter; two
concurrent batch waits in one scenario would then interleave.

**Example 4 — stub payload fidelity.**

```python
# BAD: "tidying" a canned result while migrating
return BatchSubmitResult(request_id=input.request_id, batch_id="b1")  # dropped provider

# GOOD: byte-for-byte the same payload the old stub returned
return BatchSubmitResult(request_id=input.request_id,
                         batch_id="msgbatch_mock123", provider="anthropic")
```

Rationale: canned payloads are load-bearing — result models validate
them, workflow code branches on them (`provider` is threaded
explicitly since T4.1), and assertions read them. Migration changes
where a payload lives, never what it says.

**Example 5 — over-consolidation.**

```python
# BAD: merging two tests "because they're almost the same" during migration
@pytest.mark.parametrize("resolve_conflicts", [True, False])
async def test_conflicts(...):  # was two tests with different worker sets
```

Two tests that differ in registered activities, worker composition, or
scenario shape prove different things; parameterizing them changes the
proof. Consolidation proposals go in the hand-back note for the driver
to adjudicate *after* the 1:1 migration is green (D5).

**Example 6 — what NOT to migrate.** `_PASS_VALIDATION` /
`_FAIL_VALIDATION` (`test_workflows.py:191-194`) are immutable
module-level constants used read-only. Leave them (or move them to the
support module verbatim). Migrating constants wastes diff budget and
buries the real changes in noise (D8).

## §4 Watch-out list (hazards that will not announce themselves)

1. **An unregistered activity does not fail fast.** If a migrated
   worker's activity list is missing a name the workflow calls, the
   test hangs until its timeout, which reads as "mysterious slow test,"
   not "missing mock." First diagnostic: diff the activity list against
   the workflow's calls. This is the failure shape of most migration
   mistakes under D2/D4.
2. **The time-skipping environment makes sleeps free, not ordering
   deterministic.** Fast-forwarded timers still interleave parallel
   children nondeterministically — do not conclude from ten green local
   runs that an ordered script is safe (the flake passes 7 of 8 runs).
   Review for order-dependence structurally (any `pop`, any call
   counter deciding identity), not empirically.
3. **`asyncio_mode = "auto"`** — no `@pytest.mark.asyncio` decorators;
   adding them is harmless noise, copying them into new files is
   convention drift.
4. **One `env` name only** (conftest re-export). A file that imports
   `temporal_env` directly alongside `env` starts a second time-skipping
   server for the session — slow, and a source of cross-server
   confusion.
5. **Run migrated files with `--no-cov` while iterating**
   (`uv run pytest tests/workflows/test_planned.py --no-cov`); the 85%
   aggregate gate fails any partial run. Full serial suite + replay
   suite before every hand-back.
6. **Do not touch `tests/replay/`** — `regenerate.py`'s module-level
   knobs are deliberate and documented (worker-side, keyed by unique
   batch_id, single sequential process) and its histories are the
   behavior-preservation proof. It is also the reference implementation
   for keyed counter scripting (Example 3).
7. **The old file dies at the end, not the start.** Migration proceeds
   class-by-class: a batch moves classes into the new files, the old
   copies are deleted in the same change, and the suite count is
   conserved (D5's AC). Never leave a test existing in both places — it
   double-runs, and coverage/count assertions lie.
8. **`rg -n`, never `rg -rn`** (`-rn` parses as `--replace n` and
   fabricates output). For any `.md` edits: never begin a wrapped prose
   line with `+` (the repo's formatter hook re-parses it as a list
   marker).
9. **Flake discipline during the rebuild:** until the recursive class
   is migrated (driver-owned), `TestRecursiveFanOutNestedFailure::
   test_failure_propagates` can still fail ~1/8 on unrelated batches —
   a one-off failure there gets one rerun and a note, never a "fix" in
   a bulk batch.

## §5 Delegation boundary

**Driver-only (never delegated):** `tests/support/workflow_harness.py`
(ScenarioState + `build_activities` + keyed-transition semantics); the
recursive/fan-out test classes (the flake fix and every scenario with
parallel children); every batch-transport scenario (the trio + poll
counters); the file-split skeleton and conftest wiring; anything that
looks like it needs a `src/forge/**` change (stop-and-report); the
four new replay histories and any `tests/replay/` work; final gates.

**Code-writer batches (mechanical, after the driver has landed the
harness and one fully-migrated exemplar class):** single-step and
planned-mode test classes with no parallel children — port each class
onto ScenarioState following the exemplar, 1:1 per D5, one bounded
batch of classes per hand-off, each batch green (`--no-cov` file run)
before hand-back. Every batch's hand-back note lists: classes moved,
scenario count before/after (must match), assertions changed (must be
"none"), and anything flagged for the driver (D5 candidates, suspected
dead tests, unmatched patterns).

## §6 Sequencing inside T5.5

1. Driver: support module + exemplar class + xdist dep (D10).
2. Driver: recursive/fan-out classes — the flake fix, proven by a
   repeated run (`uv run pytest tests/workflows/test_fan_out.py
   --no-cov -q` ×20 green, recorded in the task file).
3. Code-writer batches: remaining classes per §5.
4. Driver: batch-transport classes + the four missing replay histories
   (planned-step, nested gather, exploration, sanity; stretch:
   conflict resolution, sync planner, worktree-reset retry) — history
   additions are new files, never regenerations of committed ones.
5. Gates: full serial suite, replay suite, one demonstrated
   `-n auto` run, `make gates`, task close-out per PROCESS.md.

## §7 Reviewer checklist (per code-writer batch)

- [ ] Activity names in every migrated stub byte-equal to the old ones
  (D2); no direct-reference registrations.
- [ ] Zero module-level mutable containers introduced or surviving in
  migrated files — check for `pop(`, `.clear()`, call-counting globals,
  and handler-pointer reassignment, not just `global` statements.
- [ ] All scripting keyed (D3); no consumption-order lists — including
  ones that moved onto the instance (Example 1's middle form).
- [ ] Scenario count conserved; assertions diff-identical (D5); no
  parameterization merges (Example 5).
- [ ] Canned payloads field-for-field identical (Example 4).
- [ ] Frozen constants left alone (D8); no `model_copy`-less mutation
  of shared data.
- [ ] `sync_mode=True` present on migrated scenarios that had it; batch
  trio registered only where the old test registered it (D6).
- [ ] Old copies deleted in the same change; no double-existence (§4-7).
- [ ] File-scoped run green with `--no-cov`; full serial suite + replay
  suite green at hand-back.
