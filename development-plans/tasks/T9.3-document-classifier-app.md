**Last updated:** 2026-07-27

## Problem

The audit product needs machine tagging along three multi-valued
facets — Investment (SPV), Company, and document type — so the gap
report can show, per investment, which expected documents (Private
Placement Memorandum, Subscription Agreement, Purchase Agreement,
Valuation Support, Series Appendix) are present, missing, or pending
review. The classifier is a forge workspace app: a scanner polls the
documents store for documents whose current text lacks current machine
tags, a two-layer rule engine evaluates them, and tag applications are
written to the WADM manager under a service account. Both upstream
services are separate, not-yet-designed projects; this task file
exists now so the reviewed design survives as an actionable spec, and
its premises must be re-derived hard at pickup reconciliation.

## Background and Detailed Explanation

The classifier never pushes and is never pushed to. It polls the
documents store read-only for work (the same tracker-style pattern ocr
uses), and no upstream service is modified for tagging — the design's
standing principle is that pipeline stages vary independently. Its
input contract is deliberately narrow: a document identity, a text
version, and the text, regardless of whether the text came from OCR
(PDF) or native extraction (EPUB). Its output is tag applications
written through the WADM manager's API, attributed to the classifier's
service account.

Rules are two layers because the parts change at different speeds and
need different evidence. Layer 1 is matchers: span-capturing
primitives that run named patterns (per-tag alias strings from the
tag registry) against zones of the document — title area, first fifty
words, first page, and the source filename. Layer 2 is boolean
expressions over matcher results, evaluated by the `rule-engine`
library (a safe, purpose-built expression grammar; it returns booleans
only, which is exactly why span capture lives in Layer 1 — evidence
needs positions, and the library does not expose them). Rules and
alias strings are registry data the admin edits without a deploy; the
matcher engine, zone definitions, prompts, and thresholds are
repo-side code. Every deterministic content match applies its tag as
an annotation targeting the matched span, so an auditor can click a
tag and see why it exists; filename matches carry no span and apply as
a document-level annotation reading "Tag assigned from file name".

Disagreement always goes to a human — the design's review-bias
principle. If no document-type rule fires, the AI fallback evaluates
(batch, full OCR text, structured output constrained to the
registry's document-type set plus none-of-the-above, model tier from
T9.2's baselines). If multiple document-type rules fire, or the AI
disagrees with a deterministic match, the applications are written in
the WADM manager's proposed state — withheld from search and from the
gap report's "present", which instead shows pending review. Facets
are multi-valued (combined DocuSign envelopes legitimately carry two
document types); there is no Limited Partner facet — document type
plus SPV tags cover LP needs.

Re-classification is sweep-based and conservative. Every machine
application is stamped with the registry rule revision and the text
version it was computed from; sweeps re-evaluate stale stamps only,
select their own applications by attribution (human and manually
applied tags are untouchable by construction), never re-apply a
(document, tag) pair carrying a human tombstone — tombstones survive
rule revisions — and never silently remove a reviewer-approved
application: when a new rule revision disagrees with one, the
disagreement is flagged for review like any other.

The external dependencies are the reason this task is queued last.
The documents store and WADM manager are being designed as their own
projects, with the classifier's requirements exported to them from
the design record (enumeration feed, stable text versions, tag
registry with stable IDs, application lifecycle, tombstone
visibility, service-account auth, among others). Pickup
reconciliation for this task means checking the landed contracts
against those exports before writing the Plan — where they diverge,
the divergence is recorded as a dated amendment here first.

## Scope

- `apps/document_classifier` workspace member: own worker and task
  queue, `sax_platform` dependency only, never `forge`.
- Scanner workflow (poll the documents-store enumeration feed; select
  documents with text but no current machine tags; orphan/stale
  cleanup per the sweep rules).
- Layer-1 matcher engine (zones: title, first-N-words, first page,
  filename; normalization tolerant of OCR noise; span capture) fed by
  registry alias/pattern data.
- Layer-2 `rule-engine` integration (expressions as registry data;
  safe evaluation; per-tag composition of matcher results).
- WADM-manager client (service-account auth; applications with
  evidence spans or filename-evidence metadata; proposed-state writes
  on disagreement; attribution-scoped queries).
- Sweep workflows (rule-revision and text-version stamps; tombstone
  respect; reviewer-approved protection).
- AI fallback via `sax_platform.llm` batch with `ModelConfig`-driven
  tier and thresholds from T9.2.
- Out of scope: document intake and text extraction (documents
  store), tag registry and application storage (WADM manager), all
  UI, splitting combined PDFs (v1 relies on multi-tagging plus
  evidence anchors), any Limited Partner facet.

## Acceptance Criteria

Contract-level; re-derive against the landed platform contracts at
pickup.

- [ ] The scanner consumes only the documents-store enumeration feed;
  no reads of ocr tables or any other service's schema.
- [ ] Layer-1 matchers return (fired, spans) per zone; the filename
  zone yields metadata evidence rather than spans; content-match
  applications carry span-targeted evidence annotations.
- [ ] Layer-2 expressions are evaluated by `rule-engine` from registry
  data; alias and rule edits take effect without a deploy.
- [ ] The conflict policy is encoded exactly: zero document-type fire
  → AI fallback; multiple fires → proposed state; AI disagreement with
  a deterministic match → proposed state; nothing auto-applies on
  disagreement.
- [ ] All machine writes are attributed to the service account;
  sweeps select by own attribution and stale stamps only; a
  tombstoned (document, tag) pair is never re-applied; a
  reviewer-approved application is never removed by a sweep.
- [ ] The AI fallback runs batch, full text, structured output
  constrained to the registry document-type enum plus
  none-of-the-above.
- [ ] `make gates` green.
