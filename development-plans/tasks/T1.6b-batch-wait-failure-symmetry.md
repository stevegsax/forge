# T1.6b — Batch-wait failure symmetry

**Repos:** forge

## Problem

When the 25h batch wait times out or errors, forge leaves no run record and
an orphaned worktree (ocr handles the same condition correctly via
`_mark_failed`).

## Scope

- Wrap the wait in `try/except TimeoutError|ApplicationError` → persist a
  FAILURE_TERMINAL run row + clean the worktree in `finally`.
- Share the shape via workflow_blocks.

## Plan

The batch wait lives in `batch_submit_and_wait` (workflow_blocks.py). It can fail
two ways, and today both crash straight out of the workflow — no run row, orphaned
worktree:

1. **25h timeout** — `workflow.wait_condition(timeout=...)` calls
   `asyncio.wait_for` and raises **`asyncio.TimeoutError`**, which on Python 3.11+
   *is* the builtin `TimeoutError` (confirmed in the installed temporalio source:
   `_workflow_instance.workflow_wait_condition`). Note `temporalio.exceptions.TimeoutError`
   is a *different* class (activity timeouts) — must NOT import it or it would shadow
   the builtin and catch the wrong thing.
2. **Fast failure (T1.3)** — a MISSING/errored batch delivers an error-payload
   `BatchResult`; `batch_submit_and_wait` turns `result.error` (and the no-body
   case) into a raised **`ApplicationError`** in workflow context.

Both are raised *in workflow code* (not wrapped in `ActivityError`), so they reach
the workflow's `run()` directly.

**Approach — wrap at the `run()` seam, reuse the success-path persist:**

- Add a shared handler to workflow_blocks: `BATCH_WAIT_FAILURES = (TimeoutError,
  ApplicationError)` and `cleanup_worktree_after_failure(repo_root, task_id, exc)`
  — survivable worktree removal (swallows `ActivityError`; never raises, so a
  cleanup blip can't mask the terminal record).
- `ForgeTaskWorkflow.run`: wrap the plan/single-step dispatch in
  `try/except BATCH_WAIT_FAILURES` → clean worktree (`task.task_id`), build a
  FAILURE_TERMINAL `TaskResult`, then fall through to the *existing*
  `_persist_block(PersistRun(...))` — the same survivable helper and the same
  `(workflow_id, run_id)` key (T1.6a) the success path uses.
- `ForgeSubTaskWorkflow.run`: wrap dispatch the same way → clean worktree
  (`compound_id`), return a FAILURE_TERMINAL `SubTaskResult`. Sub-tasks don't write
  run rows; returning a normal failure lets the parent's existing failure handling
  record the run row. Same handler, no duplication.

Worktree cleanup is correct here because a batch-wait failure means the current
step's LLM call never produced output — nothing to preserve for that step.

## Development Notes

**2026-07-15**

- **Exception types (verified against installed temporalio, not the task shorthand):**
  the 25h wait raises the **builtin** `TimeoutError` (`asyncio.wait_for` →
  `asyncio.TimeoutError`, aliased to builtin on 3.11+). The T1.3 fast-failure path
  raises `temporalio.exceptions.ApplicationError`. Caught tuple is
  `(TimeoutError, ApplicationError)` — builtin `TimeoutError`, deliberately *not*
  `temporalio.exceptions.TimeoutError` (that class is for activity timeouts and
  would shadow the builtin). Neither is wrapped in `ActivityError`; both are raised
  in-workflow, so `run()` catches them directly. Regular activity failures still
  surface as `ActivityError` and are untouched.
- **FAILURE_TERMINAL run row keying:** unchanged from the success path — the row
  goes through the existing `_persist_block(PersistRun(workflow_id=..., run_id=...,
  task_result=result))` at the end of `ForgeTaskWorkflow.run`, keyed on
  `(workflow_id, run_id)` (T1.6a). The except branch only sets `result`; the persist
  is shared, so survivable-write semantics and the key shape are identical.
- **Sub-task path:** `ForgeSubTaskWorkflow.run` has no PersistRun of its own; on a
  batch failure it cleans its `compound_id` worktree and returns a FAILURE_TERMINAL
  `SubTaskResult`. The parent's normal failure handling then writes the parent run
  row — so a sub-task batch failure also ends with a run row + no orphan.
- **Behavior change to an existing test:** `test_batch_error_in_signal_raises`
  previously asserted the error-payload path raises `WorkflowFailureError`. That was
  exactly the bug (crash, no row, orphan). It now asserts a graceful
  FAILURE_TERMINAL result — this is the intended acceptance behavior ("ANY
  batch-wait failure leaves a run row and no orphaned worktree").
- **Cleanup survivability:** `cleanup_worktree_after_failure` swallows
  `ActivityError` only (not `CancelledError`, which must propagate), so a failed
  worktree removal is logged but never blocks the terminal run row.
- **Planned-mode trade-off:** if a batch wait fails mid-plan after earlier steps
  committed, cleaning the parent worktree discards those commits. Accepted: a 25h
  timeout / missing batch is catastrophic, the specified behavior is "no orphaned
  worktree," and the failure row records the outcome. Not hit by any existing test
  (they all deliver a batch result).
