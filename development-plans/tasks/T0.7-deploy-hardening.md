## Problem

The EC2 deployment (Terraform, SSM secret bootstrap, mTLS gateway,
systemd worker units) served two jobs that no longer exist for a
single-operator system: hosting Temporal near Supabase, and exposing
Temporal to remote CLIs. The owner's desktop is always on; remote
invocation went unused while the surface accumulated defects (G31–G35).
Meanwhile Temporal persisting to Supabase means every workflow tick
crosses the internet once Temporal runs locally.

## Background and Detailed Explanation

This task began life as "deploy hardening" — fixing five defects
(G31–G35) in the EC2 bootstrap and Terraform surface — and was rewritten
mid-flight when the owner retired EC2 entirely (D99). The EC2 host had
existed to do two jobs that no longer applied to a single-operator
system: run Temporal near the Supabase database, and expose Temporal to
remote CLIs over an mTLS gateway. The operator's desktop is always on,
and remote invocation went unused while its gateway, cert chain, SSM
secret plumbing, and Terraform surface only accumulated defects. Keeping
Temporal remote carried a second cost: once Temporal ran locally, every
workflow tick would otherwise cross the internet to persist.

So the shape became **local-first**. The EC2/mTLS surface was deleted
outright (`deploy/terraform/`, `deploy/scripts/`, `deploy/systemd/`, the
cert and client tooling, `SECURE-REMOTE-ACCESS.md`). The renamed
`deploy/local-stack/` grew Temporal and a Temporal UI as loopback-only
podman services, persisting to the stack's own Postgres beside
`forge_dev`. Workers stay host `uv run` processes, now supervised by
**launchd** instead of systemd, with secrets in one chmod-600 env file
read by a wrapper that parses `KEY=VALUE` lines *without*
shell-evaluating them. That last detail is the one original finding that
survived structurally rather than by deletion: G35 (unquoted env
sourcing) is fixed because the line-by-line parser replaces the unsafe
`source`. G34 (no S3 lifecycle rule) also survived — blobs stay on real
S3 — and shipped as `deploy/s3/lifecycle.json` with a documented apply
command. The other three findings were *mooted*: the scripts, SSM path,
and Terraform that carried them no longer exist.

Two verification findings shaped the local setup and are load-bearing
for anyone running it. This machine already publishes Postgres on 5433
(another project maps it), so the stack runs on **5434** via a
gitignored `deploy/local-stack/.env` override — local `FORGE_DB_URL` on
this machine must use 5434. And the task deliberately closed with an
owner-gated remainder rather than fully live: filling in the env file,
running the launchd installer, applying the S3 lifecycle policy, and
`pmset` for always-on were the owner's moves. This "stores stay managed
on Supabase" shape was itself later superseded by D102/T0.9, which
rehomed the application store onto the same local Postgres.

## Scope (D99)

- **Delete the EC2/mTLS surface:** `deploy/terraform/`,
  `deploy/scripts/` (bootstrap-instance.sh, fetch-secrets.sh,
  smoke-test.sh), `deploy/systemd/`, `deploy/certs/`, `deploy/client/`,
  `deploy/temporal/`, `docs/operations/SECURE-REMOTE-ACCESS.md`.
- **Local stack grows Temporal:** rename `deploy/local-database/` →
  `deploy/local-stack/`; add `temporal` (auto-setup, persistence in the
  stack's Postgres: `temporal` + `temporal_visibility` databases beside
  `forge_dev`) and `temporal-ui` services, both loopback-only; Makefile
  and README follow.
- **Workers stay host processes** (`uv run … worker` from the forge
  checkout), supervised by **launchd**: templates + installer under
  `deploy/launchd/`, secrets in one chmod-600
  `$XDG_CONFIG_HOME/forge/forge.env` read by a wrapper that parses
  KEY=VALUE lines without shell-evaluating them (keeps G35 fixed).
  Containerizing the workers is deferred to the sax-llm absorption
  increment (image builds can't COPY `../` sibling sources).
- **Stores stay managed:** Supabase Postgres (forge/pbook state), S3
  (blobs). S3 lifecycle policy committed at `deploy/s3/lifecycle.json`
  with the apply command documented — application is owner-gated.
- **Docs truth pass:** DEPLOYMENT.md rewritten for the local topology
  (including pmset always-on guidance); deploy/README.md rewritten;
  TOC.md, OVERVIEW.md, ARCHITECTURE.md mTLS/EC2 mentions updated.
  Client-side TLS env handling in forge-contracts stays (dormant, not
  worth a contracts change now).

### Dispositions of the original findings (2026-07-16, D99)

- **G31 fetch-secrets fails open** — mooted: the script and the SSM
  path are deleted; secrets live in one chmod-600 env file.
- **G32 auto-setup re-runs DDL against Supabase; unpinned installers**
  — mostly mooted: Temporal persistence is the local stack's Postgres,
  and bootstrap (with its curl|sh installs) is deleted. auto-setup
  remains locally, where re-running setup against our own Postgres on
  restart is tolerable; `SKIP_SCHEMA_SETUP` guidance documented in the
  compose file.
- **G33 Terraform can replace the instance** — mooted: Terraform is
  deleted.
- **G34 no S3 lifecycle rule** — survives EC2 removal (blobs stay on
  real S3): addressed by `deploy/s3/lifecycle.json` + documented
  `aws s3api put-bucket-lifecycle-configuration` command. Once applied,
  the June review §8's cited "bucket TTL" becomes true rather than
  needing a doc correction.
- **G35 unquoted env sourcing** — the offending `source` dies with
  bootstrap; the launchd wrapper that replaces it parses the env file
  line-by-line instead of shell-evaluating it, so the fix is
  structural, not deleted-by-accident.
