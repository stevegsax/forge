# T5.3 — Single gather + dispatch

**Status:** DONE
**Phase:** 5 — Workflow consolidation (forge)
**Repos:** forge
**Depends on:** [T5.2](T5.2-single-step-block.md)
**Last updated:** 2026-07-26

## Problem

The fan-out gather code exists twice in `workflows.py` (parent and
nested), and the duplicated nested copy is where the T1.5 propagation bug
(`resolve_conflicts`/`thinking`/`model_routing` dropped) was bred. The
four batch LLM-dispatch arms (planner, sanity, exploration, conflict) each
carry their own copy of the call/submit/parse plumbing rather than sharing
one implementation on the Phase-4 transport.

## Background and Detailed Explanation

T5.3 was the fan-out counterpart to T5.2: it collapsed two copies of the
gather logic into one and unified five copies of the typed LLM-dispatch
layer, then used the single surviving gather to fix a failure mode where
one crashed child destroyed the whole run and killed its siblings
mid-batch.

**The problem.** Two duplications lived here. First, the fan-out
*gather* — start N child workflows, wait for them, merge their outputs
— was written twice in `workflows.py`, once for the top-level fan-out
and once for a fan-out nested inside a sub-task. The nested copy is
where the T1.5 propagation bug was bred: `resolve_conflicts`,
`thinking`, and `model_routing` were honored by the parent path and
silently dropped by the nested one. Second, the *typed dispatch layer*
above the batch transport existed five times — planner and sanity check
inline in `workflows.py`, generation and conflict resolution as
hand-rolled twins in `workflow_blocks.py`, and exploration inline,
divergent, and persisting nothing. (The task's original "four arms carry
their own submit/poll/parse plumbing" predates T4.1, which had already
reduced the transport itself to one implementation.)

**The fix.** `blocks/gather.py` owns one `run_fan_out_gather(spec, host)`
used by both callers, with the two differences — who owns the worktree,
whether the gather commits — expressed as the two rows of a pure
`GATHER_POLICIES` table (the top-level step borrows the plan's worktree
and commits; a nested node creates its own, removes it on every exit, and
never commits, per D16). It returns a neutral `GatherSuccess |
GatherFailure`, which each caller stamps onto its own result type through
the T5.1 `step_logic` builders, and it builds every child's input in one
pure function — so the T1.5 fix lives in exactly one place and cannot
drift again. `blocks/dispatch.py` owns `typed_dispatch`, one
implementation of lane fork → typed result → interaction persist over a
pure five-row `ARMS` table, on the Phase-4 timer-loop transport (which
stays in `workflow_blocks.py` and is imported, not moved). The per-run
state both blocks need — sync lane, poll cadence, per-role persist
counters — became `DispatchHostBase`, a plain non-`@workflow.defn` base
class that both workflow classes inherit, retiring the four dispatch
members each had carried verbatim.

**The buried gems (the 2026-07-08 amendments).** Two defects the
consolidated gather was the right place to fix once. *Per-child failure
isolation:* both gathers used to bare-await their children, so a child
that *raised* — an execution timeout, an escaping activity failure —
propagated a `ChildWorkflowError` straight out of `run()`. The
consequences cascaded: no `TaskResult`, no run record, no worktree
cleanup, and — because the default ParentClosePolicy is TERMINATE —
every in-flight sibling was killed, orphaning the paid batches they were
waiting on. The gather now wraps each child await, so a raising child
becomes a failed `SubTaskResult` (a new `child_crashed` `failure_kind`,
the tenth value, meaning "the diagnosis is in the child's own history,
not in this result") while its siblings run to completion; the pattern
source was `ingestion_workflow.py`. ParentClosePolicy is now stamped
explicitly as TERMINATE — the same value the SDK defaulted to, so the
committed histories replay unchanged, but chosen rather than inherited.
*Uniform interaction records:* exploration was the one dispatch path of
the five that wrote nothing to the interactions store — up to 20 LLM
calls per task with no token or cost record, leaving T7.4's future budget
enforcement nothing to enforce against. Fixing it needed more than a
persist call: the sync activity returned a bare `ExplorationResponse`
whose token counts died in a trace span, so it now returns an
`ExplorationCallResult` envelope carrying the spend *and* the prompts it
assembled internally. Building that envelope also exposed a latent crash
in `build_persist_interaction`, which assumed every result's `response`
had an `explanation` field.

**How it shipped:** the depth-2 nested-fan-out regression stayed green
throughout; all five arms share one implementation; a raising child
yields a failed `SubTaskResult` while its siblings finish and the parent
still returns a `TaskResult` and writes a run record; every dispatch arm
produces an interaction record with token counts; and the committed
replay histories — the batch planner sequence and both generation lanes —
passed **unregenerated** at every step, which is the behavior-preservation
proof that the consolidation changed no command sequence. `workflows.py`
went from 1,632 lines to 917.

## Scope

- `blocks/gather.py` — `run_fan_out_gather(children, fan_out, settings, *,
  commit)` for parent (commit=True) and nested (commit=False, D16) — the
  T1.5 fix now lives in exactly one place.
- `blocks/dispatch.py` — `typed_batch_dispatch` consolidating the
  planner/sanity/exploration/conflict arms onto the Phase-4 transport.

### Amendments (2026-07-08)

- `run_fan_out_gather` must isolate per-child failure: wrap each child
  await in try/except so a *raising* child (execution timeout, batch error,
  wait expiry) yields a failed SubTaskResult instead of a
  `ChildWorkflowError` escaping `run()`. Today the gathers bare-await
  (`workflows.py:1230-1233`, `:1720-1724`): no TaskResult, no run record,
  no worktree cleanup, and the implicit default ParentClosePolicy
  (TERMINATE) kills in-flight siblings, orphaning their paid batches. The
  correct pattern already exists in `ingestion_workflow.py:264-299`.
- Choose and document an explicit ParentClosePolicy for fan-out children.
- *(2026-07-08 sweep)* `typed_batch_dispatch` persists an interaction
  record for every arm uniformly — exploration is currently the only one
  of the five dispatch paths that writes nothing to the interactions
  store (`workflows.py:380-400`; up to 20 calls/task with no token/cost
  record), which also makes T7.4's budget enforcement unverifiable.

### Design decisions (settled)

1. **What "four arms of plumbing" means post-T4.1.** The
   submit/poll/fetch/parse transport already exists exactly once
   (`workflow_blocks.batch_submit_and_wait`, T4.1). The surviving
   duplication is the *typed dispatch layer* above it — per arm: a
   sync/batch fork, an `AssembledContext` build, a typed parse of the
   batch body, and the interaction persist. Five arms share that shape:
   planner (`workflows.py:379-423`) and sanity check (`:449-493`) are
   inline near-identical methods; exploration (`:425-447`) is inline,
   divergent, and persists nothing; generation and conflict resolution
   are already extracted (`workflow_blocks.generation_dispatch` /
   `conflict_resolution_dispatch`) but as two hand-rolled copies of the
   same shape. `blocks/dispatch.py` owns the shape once: sync lane runs
   the arm's call activity, batch lane runs `batch_submit_and_wait` plus
   the arm's typed result build (the eight stats fields map identically
   in every arm — one shared helper), and the persist happens inside,
   uniformly. The two `workflow_blocks` dispatch copies are subsumed and
   deleted; `batch_submit_and_wait` itself stays in `workflow_blocks.py`
   (the same import direction T5.2 chose for `blocks/step.py` — any
   monolith reshuffle is [T5.4](T5.4-split-the-monolith.md)).
2. **Uniform persistence through one host seam.** `_persist_interaction`,
   `_call_llm_batch`, `call_generation`, and `_call_conflict_resolution`
   are duplicated verbatim across `ForgeTaskWorkflow` and
   `ForgeSubTaskWorkflow`. One shared implementation (a plain non-defn
   base class holding the per-role occurrence counters, or an equivalent
   explicit-state module function set — driver verifies the inheritance
   pattern against the sandbox with a quick test first) provides the
   persisting dispatch both classes and both blocks use. Every arm
   persists with its role: `llm`, `planner`, `sanity_check`,
   `conflict_resolution`, `exploration`.
3. **Exploration gets a call-result envelope.** `call_exploration_llm`
   returns a bare `ExplorationResponse`; token counts are measured into
   a trace span and discarded (`activities/roots.py:352-389`), so the
   sync lane has nothing to persist today. A new `ExplorationCallResult`
   carries the response, the standard stats fields, and the prompts the
   activity assembled (the sync lane builds prompts internally; the
   batch lane already has stats from `ParsedLLMResponse` and prompts
   from `assemble_exploration_context`). Activity signature changes are
   sanctioned — no live users.
4. **`blocks/gather.py` mirrors the T5.2 shape, not the 06-10 sketch.**
   The specced `run_fan_out_gather(children, fan_out, settings, *,
   commit)` predates T5.2; the reconciled shape is
   `run_fan_out_gather(spec, host)` returning a neutral `GatherOutcome`,
   with callers building `StepResult` / `SubTaskResult` (terminal
   results via the T5.1 `step_logic` builders). Two policy rows: parent
   = borrowed worktree / step-scoped commit; nested = owned worktree
   (created by the block, removed on every exit; never commits, D16).
   Child-input construction (ids, depth, propagated fields) lives in
   the block — the T1.5 fix exists once and cannot drift again.
5. **Per-child failure isolation.** Each child await is wrapped in
   `try/except Exception` → a failed `SubTaskResult` (new `step_logic`
   builder for a crashed child), while the remaining handles are still
   awaited; the existing failures check then treats it like any failed
   child. `CancelledError` (BaseException) deliberately propagates.
   Children already convert their own batch-wait failures into results
   (the T1.6b catch in their `run()`), so what reaches the parent as a
   raise is: child execution timeout, an escaping activity failure, or
   a workflow bug — exactly the shapes that today destroy the run. The
   pattern source is `ingestion_workflow.py:255-291`.
6. **ParentClosePolicy: explicit TERMINATE (recommendation — owner may
   veto at review).** Explicit TERMINATE stamps the same proto value the
   SDK defaults to today, so the committed fan-out histories replay
   unregenerated. With isolation in place the parent no longer closes on
   a child failure — TERMINATE fires only when the parent itself dies
   (execution timeout, operator terminate), where children are bounded
   by their own derived timeouts anyway. ABANDON was considered and
   rejected: abandoned children finish into a void (sub-tasks never
   commit; their results are read by nobody) at up to 25h of worker
   occupancy. The choice and rationale go in the gather module
   docstring.
7. **Nested gather exception wrap (the leak T5.2 left).**
   `_run_nested_fan_out` creates its worktree (`workflows.py:1444`) with
   no exception wrap — any raise between creation and a result-path
   removal leaks the worktree and its branch. The gather block wraps its
   owned-worktree row exactly as `blocks/step.py` wraps its fresh modes:
   cleanup on `Exception`, batch-wait shapes re-raised untouched
   (`run()`'s handler owns them). The six hand-repeated result-path
   `_remove_worktree` calls collapse into the block's exit handling
   (removal is idempotent since T5.2).
8. **Preset and cleanup dedup.** The timeout/retry presets now exist in
   three copies (`workflows.py:112-146`, `workflow_blocks.py:94-117`,
   `blocks/step.py:96-109` — the latter's comment names T5.3 as the
   retirement point). One home, imported everywhere a block or
   `workflows.py` needs it; the near-duplicate cleanup helpers
   (`blocks.step.cleanup_worktree_after_exception` /
   `workflow_blocks.cleanup_worktree_after_failure` — same body,
   different log text) fold into one.
9. **Replay discipline: preserve, don't regenerate.** `fan_out_batch`
   (+ two child histories) pins the batch planner sequence
   (`assemble_planner_context` → submit/status/fetch/parse → persist)
   and the parent gather sequence (2× start-child → await → detect →
   `write_files` → validate → commit). The consolidations must be
   command-identical on those paths; per-child try/except and explicit
   TERMINATE add no commands. Exploration and sanity checks appear in no
   committed history (`max_exploration_rounds=0` in every scenario), so
   the exploration persist is replay-safe. The nested gather stays
   pinned by workflow tests only (the same posture planned-step holds
   after T5.2); new histories are T5.5's business.

    GatherFailure`, following the `MergedFiles | MissingResolutions`
    precedent in `step_logic`. `commit_sha` exists only on success and

    failed cleanly and returned its own result — exactly the distinction
    an operator needs, because for `child_crashed` the diagnosis is not
    in the result at all but in the child's own workflow history. The
    parent-level gather failure still uses `sub_task_failed`.
