## Problem

Three observability defaults misbehave:

1. **Prompt-leak channel via the root logger.** `cli.py:489-490` sets the
   *root* logger to DEBUG whenever the file handler attaches, so every
   third-party library's DEBUG stream lands in `forge.log`/`worker.log` —
   and any SDK that logs payloads at DEBUG leaks prompts into log files,
   outside the trust boundary the 2026-06 review analyzed when it refuted
   the store-retention finding (the refutation covered the interactions
   table, not logs).
2. **Dead config knob.** `FORGE_OTEL_ENDPOINT` (`tracing.py:33`) is
   defined but never read — `init_tracing`'s `endpoint` parameter is only
   honored when passed explicitly, and the sole production caller is bare
   `init_tracing()` (`worker.py:224`). Configuring it silently does
   nothing.
3. **Span spam by default.** `resolve_exporter_type` defaults to CONSOLE
   with a synchronous `SimpleSpanProcessor` (`tracing.py:98`, `:167-170`),
   printing every span to stdout on local runs — contradicting D85's
   quiet-worker design. The EC2 units mask it with
   `FORGE_OTEL_EXPORTER=none`; local dev gets the spam.

## Background and Detailed Explanation

This task fixed three shipped defaults in forge's observability layer,
all misbehaving in ways that stayed invisible until someone looked.

**The prompt-leak channel.** Forge writes its logs to a file
(`forge.log`/`worker.log`). When that file handler attached, the code
set the *root* logger to DEBUG — which meant every third-party
library's DEBUG output landed in the file too. Any SDK that logs
request bodies at DEBUG would therefore write prompts into a log file
sitting outside the trust boundary the 2026-06 review had signed off on
(that review cleared the interactions *table*, not logs). The fix rests
on a subtlety of Python's logging: when a record propagates up from a
child logger, Python re-checks *handler* levels but not the ancestor
*logger* level. So setting the root logger to INFO and the `forge`
logger to DEBUG lets a `forge.*` DEBUG record still reach the DEBUG file
handler, while a third-party library's DEBUG record is dropped at its
own logger (effective level INFO) before it ever gets there. The two
levels coexist deliberately. **The accepted trade-off:** at `-vv` with
file logging on, third-party DEBUG no longer reaches the console either
— acceptable, since the whole point is to keep prompt-bearing
third-party DEBUG out and forge is not in production.

**The two tracing defaults.** `FORGE_OTEL_ENDPOINT` was a config knob
that nothing read — setting it did nothing — so it was a lie. It had
already been deleted by T3.6, so this task only had to confirm its
absence with `rg`. Separately, tracing defaulted to a CONSOLE exporter
with a synchronous processor, printing every *span* (one timed unit of
a trace) to stdout on local runs — contradicting D85's quiet-worker
design, which the retired EC2 units had masked with an explicit `none`.
The default is now `none`; console and OTLP output are opt-in via
`FORGE_OTEL_EXPORTER`, and a bare `forge worker` run builds a
no-processor provider that emits nothing per span.

## Scope

- Root logger at INFO; `forge.*` loggers at DEBUG.
- Wire `FORGE_OTEL_ENDPOINT` into `init_tracing` or delete the constant.
- Default exporter `none`; console/OTLP opt-in.

Coordinate note: T3.6 reworks tracing *composition* (set-once guard,

## Plan

Landed alongside T0.2 and T0.6 (shared `cli.py`).

1. **Root-logger DEBUG leak (`cli.configure_logging`).** When the file
   handler attaches, set the *root* logger to INFO and the `forge` logger to
   DEBUG instead of the root to DEBUG. Python only re-checks *handler* levels
   (not ancestor *logger* levels) on propagated records, so a `forge.*` DEBUG
   record still reaches the DEBUG file handler while a third-party (NOTSET →
   effective root INFO) DEBUG record is dropped at its own logger. Reset the
   `forge` logger to `NOTSET` on the no-file branch so the function is
   idempotent across repeated calls (tests call it many times).
2. **`FORGE_OTEL_ENDPOINT` — already gone (T3.6).** `TracingSettings` has only
   `exporter`; no endpoint field, no env read. AC satisfied on the "or gone"
   branch — documented here, no code change.
3. **Default exporter → none.** Flip `resolve_exporter_type(None)` to return
   `ExporterType.NONE`; correct the three T3.6-era docstrings that assert
   None ⇒ CONSOLE (tracing module, `resolve_exporter_type`, `init_tracing`)
   plus the `TracingSettings` docstring; update the two tracing tests that
   asserted the old default.

## Development Notes

**2026-07-18 — landed (with T0.2, T0.6).**

- *Logging.* Python only re-checks *handler* levels on records propagated up
  from a child logger, never the ancestor *logger* level — so root=INFO drops a
  NOTSET third-party logger's DEBUG at its own logger (effective INFO) while
  `forge`=DEBUG lets `forge.*` DEBUG reach the DEBUG file handler. This is why
  the two levels can coexist. On the no-file branch `forge` is reset to
  `NOTSET` so `configure_logging` is idempotent across the many test calls.
  Trade-off: at `-vv` *with* file logging, third-party DEBUG no longer reaches
  the console either (root is INFO). Acceptable — the whole point is that

  worker's `init_tracing(settings.tracing.exporter)` needed no change — a bare
