# T7.4 — Exploration budget

**Status:** NOT STARTED
**Phase:** 7 — Context engine (forge)
**Repos:** forge
**Depends on:** [T7.1](T7.1-project-descriptor.md)
**Last updated:** 2026-07-08

## Problem

The LLM-guided exploration loop is unbounded — a verified major finding
of the review: no dedup, no request caps, no token budget, quadratic
resend of accumulated results, and up to 10 sequential round-trips. In
batch mode each round is a paid batch round-trip with hours of latency,
so an unbounded loop is the context engine's largest cost and latency
liability.

## Background and Detailed Explanation

Forge lets the model pull its own context: from a menu of providers it
requests "read this file," "list these symbols," "trace these imports,"
and forge fulfills each request, looping until the model signals it is
ready to generate (D48). The review found that loop effectively
unbounded — no request deduplication, no per-round cap, no token budget,
up to ten sequential round-trips, and a *quadratic resend* where every
round re-ships all results accumulated so far, so ten rounds carry
rounds one-through-nine's payloads over and over. In batch mode this is
the expensive part: each round is a paid batch submission with hours of
latency, which makes an unbounded loop the context engine's single
largest cost-and-latency liability.

**The fix.** An `ExplorationBudget` on `ContextConfig` with a mode-aware
`max_rounds` default — 2–3 in batch mode, 10 in sync — which the review
flagged as its single highest-ROI change, since batch mode pays hours
per round. Plus a per-round request cap, deduplication keyed on
`(provider, sorted params)` answered from an already-retrieved stub
instead of a fresh fetch, a deterministic total-estimated-token cap, and
`exploration_exhausted` surfaced and logged when a cap stops the loop
(D96 amends D48/D49).

**Two adjacent fixes (2026-07-08 sweep, phase-independent — safe to
cherry-pick now):**

- **A cache-defeating counter.** `## Round {N} of {M}` renders at the
  *top* of the system prompt (`exploration.py:75`), so the cacheable
  prefix changes at roughly line 12 every single round — in the one loop
  that repeats enough to benefit most from prompt caching. Render the
  counter in the user message instead and keep the system prompt
  append-only across rounds, so each round extends the previous prompt
  as a strict prefix.
- **Truncate at the source, not at render.** `read_file`, `symbol_list`,
  and `import_graph` return unbounded content; the existing 8,000-char
  truncation runs only at prompt-render time — *after* the full payload
  has already crossed the activity boundary into Temporal workflow
  history (which has a ~2MB ceiling). Enforce a per-result output cap in
  the fulfillment activity itself.

Done means round/dedup/cap tests, the batch-mode default verified,
round N+1's system prompt proven a strict string prefix of round N's,
and `read_file` on an oversized file returning already-truncated content
from the activity.

  stub.
- Deterministic total-estimated-token cap.

  unbounded content (`providers.py:52,128,168`) and the existing
  8,000-char truncation lives only at prompt render, after the payload
  crossed the activity boundary into workflow history.
