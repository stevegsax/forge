# T9.1 — Provenance ledger (shared dedup + source provenance)

**Status:** NOT STARTED
**Phase:** 9 — Document classifier
**Repos:** forge
**Depends on:** nothing — independent of Phases 0–8
**Last updated:** 2026-07-27

## Problem

Document-classifier intake must examine an admin-curated manifest of
~110,000 absolute paths (~46,000 corpus PDFs under the SAX OneDrive
shared libraries; an estimated 10% unique content, the rest renamed or
relocated copies), and no component records dedup verdicts durably. The
nearest existing mechanism, ocr's duplicate handling, has three defects
at manifest scale: verdicts are discarded
(`execute_check_ocr_duplicate`, `apps/ocr/src/ocr/activities.py:584` —
returns `is_duplicate` plus the existing document id and records
nothing, so every re-run re-hashes and re-decides every file); the
content hash is computed twice, hours apart (at submit, then again in
fetch-and-store, `activities.py:440-442`, only if the file still
exists — which is why `ocr_results.file_hash` is nullable and a
backfill helper exists); and dedup is an advisory check-then-insert
with no uniqueness constraint (`file_hash` is indexed, not unique,
`apps/ocr/src/ocr/store.py:65`), so concurrent same-content intakes
can store content duplicates.

## Background and Detailed Explanation

The SAX document corpus has accumulated as copies: the same purchase
agreement saved to a deal folder, re-saved under a new name, attached
to an email, and downloaded again. Before any document is OCR'd,
classified, or shown to an auditor, intake has to decide which files
are the canonical instance of their content and which are copies — and
it must never repeat that work. Hashing 46,000 files is hours of I/O;
doing it once is acceptable, doing it on every re-run is not. The
owner's requirement is explicit: once a file (identified by its full
path) has been examined and marked, it is never examined again unless
the file itself changes.

The fix is a provenance ledger: one durable record per examined path,
carrying the path, the SHA-256 of the bytes, the file's size and
modification time at examination, and a verdict — canonical (first
instance of this content), duplicate (pointing at the canonical
entry), or unreadable (the file could not be hashed). A re-run skips
every settled path whose size and modification time are unchanged; a
path whose stat data drifted is re-hashed and re-decided, because the
bytes may differ. The ledger records content truth only — services
that store documents map canonical entries to their own document
records.

The ledger is deliberately a shared component, not
classifier-internal. The documents-platform intake is the first
consumer (via the classifier evaluation harness, T9.2); ocr is the
natural second, since adopting the ledger fixes all three defects
above at once (that adoption is its own task, not part of this one).
The payoff beyond dedup is provenance: when the same content was seen
at nine paths, the ledger is the record that says so — the answer to
an auditor's "where did this document come from" is every source path
that ever carried the document's bytes, each traceable to its
canonical entry.

Two hash decisions are settled and carried here from the design
record. SHA-256 over raw bytes, not CRC: at 46,000 files a 32-bit
checksum has roughly a one-in-five chance of at least one accidental
collision — a false merge of two different documents, unacceptable in
an audit product — and SHA-256 is already the convention on both
sides of the fleet. And the hash is computed exactly once, at
examination time; downstream stages carry the recorded value and
never re-derive it from the filesystem, because a file can move or
change between pipeline stages (ocr's nullable hash is the symptom of
hashing at the wrong end).

## Scope

- New `sax_platform` provenance module: a pure core (verdict logic,
  hash-format validation, stat-drift detection) plus Temporal
  activities and a batch-examination workflow; module and table
  placement (Alembic chain, task queue) decided at plan time.
- Ledger entry: `source_path`, `content_hash` (SHA-256, 64 lowercase
  hex characters, unconstructible otherwise), `verdict`
  (`canonical | duplicate | unreadable` as an enum, not strings),
  `canonical_entry_id` (required for `duplicate`, absent otherwise —
  the illegal combinations unrepresentable), `file_size`, `mtime`,
  `decided_at`.
- Rules: hash once at examination; skip settled paths with unchanged
  (size, mtime); re-decide on stat drift, retaining the prior verdict
  as history; at most one canonical entry per content hash, enforced
  by a database unique constraint, with a concurrent loser converted
  to a duplicate of the winner; canonical invalidation marks dependent
  duplicates stale for re-decision on the next run.
- Unreadable paths are recorded and re-examined on every run until
  they resolve.
- Out of scope: ocr's adoption of the ledger (follow-up task);
  near-duplicate detection beyond byte identity (the documents
  platform's content identity handles convergence of byte-different
  copies).

## Acceptance Criteria

- [ ] A manifest examination computes each file's SHA-256 exactly
  once; no downstream consumer re-derives a hash from the filesystem.
- [ ] A malformed content hash cannot be constructed (tested at the
  type/constructor level, not by downstream runtime validation).
- [ ] Re-running examination over an unchanged manifest performs zero
  hashing and zero verdict changes (test with stat-identical files).
- [ ] The one-canonical-per-hash invariant is enforced by a database
  constraint; a concurrency test shows two same-content examinations
  converging on one canonical and one duplicate.
- [ ] A duplicate verdict always references an existing canonical
  entry; an unreadable verdict carries no hash and is retried on the
  next run.
- [ ] A settled path whose size or mtime changed is re-hashed and
  re-decided; the superseded verdict remains queryable as history.
- [ ] Canonical invalidation marks dependents stale and they are
  re-decided on the next run.
- [ ] `make gates` green.
