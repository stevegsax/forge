## Problem

The application store of record (forge/ocr shared database) lives on
Supabase while Temporal persists locally (D99's split). The owner corrected
the record 2026-07-22: during a period when ongoing Supabase access was not
guaranteed, the podman stack was adopted for disposable test databases
after weighing alternatives — a history the decision record had not
captured. Standing owner requirements, stated 2026-07-22:

1. The application must not be split across two database deployments —
   one server, with application and Temporal databases kept separate on it
   (enables later migration and granular per-database permissions).
2. Which database a command targets must never be ambiguous. Launching
   against production must be an explicit act — never the result of an
   unset variable using a default. (Trigger: `ocr tracker-status` failed on
   an unset `FORGE_DB_URL` and neither owner nor session could say with
   confidence which database anything used.)

Grounding (2026-07-22, live inspection; corrected same day): the Supabase
`FORGE_DB_URL` database (Postgres 17.6, pooler) holds forge + ocr tables in
`public` **and pbook's data in its own `pbook` schema** (`pbk_`-prefixed by
design for coexistence: 60 entries, 256 tags, 82 ingested sessions) — an
initial public-schema-only query wrongly concluded no pbook data existed.
`forge.env` currently has no `PBOOK_DATABASE_URL` (pbook's settings treat
unset as store-disabled) and no pbook worker is installed, so current
writes come from interactive/historical use, not the worker. The latency
concern recorded in D99 applies to Temporal history ticks (already local),
not to the app store's low-rate business writes — re-examined and
dismissed for the app store at current scale.

## Decision (owner, 2026-07-22)

- App databases move to the existing `forge-postgres` podman instance
  (pgvector/pg16, loopback :5434 on this machine) as **separate databases**
  beside Temporal's: new `forge` (forge + ocr chains — the source `public`
  schema, migrated from Supabase) and `pbook` (the source `pbook` schema
  migrated into its own database for the first time; pgvector enabled).
  `forge_dev` remains the disposable dev database. `envs/prod.env` sets
  `PBOOK_DATABASE_URL` explicitly — ending the silent store-disabled state.
- Supabase is retired as the store of record; the final pre-cutover dump is
  retained and Supabase left frozen until the owner decommissions it.
- Offsite durability moves to a nightly `pg_dump` → S3 launchd job
  (lifecycle policy already in `deploy/s3/`).
- Explicit-environment guard, built now: `FORGE_ENV ∈ {prod, dev, test}`
  with **no default**; per-env profile files
  `$XDG_CONFIG_HOME/forge/envs/<env>.env` carrying a matching
  `FORGE_ENV_TAG`; prod additionally requires `FORGE_PROD_ACK=yes` and the
  tagged profile (never hand-assembled env). Workers declare their env in
  launchd; interactive shells must declare theirs.
