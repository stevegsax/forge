# T7.2 — Worktree-accurate graph

**Status:** NOT STARTED
**Phase:** 7 — Context engine (forge)
**Repos:** forge
**Depends on:** [T7.1](T7.1-project-descriptor.md)
**Last updated:** 2026-07-08

## Problem

The grimp import graph is built in the worker process against the
installed forge package, not the task's worktree — one of the review's
verified critical findings ("grimp analyzes the worker's installed
package, not the task worktree"). Context discovery therefore reflects
stale module structure, cannot see worktree-only changes, and cannot
work against a non-forge repo at all; graph failures fall back silently
with no signal in ContextStats. `module_to_file_path` compounds this
with CWD-relative checks that assume the worker's working directory.

## Background and Detailed Explanation

`grimp` is the library forge uses to build a project's import graph —
which module imports which — so context discovery can pull in a target
file's neighbors and the repo map can rank files by how central they are
(D31, D32). The verified-critical bug: the graph is built inside the
worker process against the *installed* forge package, not against the
checkout the task is actually editing. So discovery describes the wrong
code — it cannot see a module a worktree just added or renamed, and
against a non-forge repo it describes forge instead. When the graph
build fails outright, the fallback is silent: nothing in `ContextStats`
tells anyone that context was degraded. `module_to_file_path` makes it
worse by resolving paths relative to the worker's current directory.

**The core fix is small.** Build the graph in a subprocess with
`PYTHONPATH={worktree}/{src_root}` so grimp analyzes the task's own tree
— roughly a twenty-line change that both fixes the drift and makes
off-repo discovery work. Surface failure honestly by adding `degraded`
and `degradation_reason` fields to `ContextStats` (logged, not
swallowed), keep the repo map alive through a file-walk fallback when the
graph cannot build, and delete the CWD-relative checks.

**Three ranking corrections (2026-07-08, phase-independent — safe to
cherry-pick now).** These touch the same subsystem and fix quiet
wrongness in *what* context surfaces:

- **Nondeterministic seeding.** The planner personalizes PageRank with
  `list(graph.modules)[:5]` — a slice of a hash-ordered set, so it seeds
  the ranking around five effectively random modules that change from one
  worker process to the next, making the planner's repo map
  non-reproducible. Replace it with an explicit no-target ranking mode
  (uniform personalization already exists for the empty case) and
  deterministic iteration order.
- **Backwards rank flow.** PageRank over an importer→imported graph
  pushes importance toward *dependencies*. But the code that matters for
  a change is its reverse-dependents — everything that would break if the
  target changes — and those systematically rank last, so they are
  truncated first. Run PageRank on the reversed graph, or add weighted
  reverse edges, so the change-impact surface ranks up.
- **Symbol-parser blind spots.** `extract_symbols` misses PEP 695
  `type X = ...` aliases (the repo targets ≥3.12), and `_UPPER_CASE`
  constants unparse their whole literal into the repo map, so a 50-line
  constant can crowd real API surface out of the 2048-token map. Handle
  `ast.TypeAlias`; render constants as `NAME = ...` with long literals
  elided.

Done means a test proving the graph reflects a worktree-only change, a
degradation test, reproducible `rank_files` ordering regardless of
`PYTHONHASHSEED` with a direct importer outranking a distant transitive
one, and PEP 695 aliases visible in symbol summaries (D96 amends D31).

## Scope

- Build the grimp graph in a subprocess with

### Amendments (2026-07-08, capture sweep)

- **Deterministic planner ranking (phase-independent — safe to
  cherry-pick now).** The planner path seeds PageRank personalization
  with `list(graph.modules)[:5]` — a hash-ordered set slice that differs
  across worker processes (`planner.py:266-268`), so the planner's repo
  map is personalized around five random modules per run. Replace with an
  explicit no-target ranking mode in `rank_files` (uniform
  personalization already exists for `[]`, `graph.py:179-182`) and
  deterministic iteration order.
- **Ranking direction.** Personalized PageRank over the
  importer→imported DiGraph sends rank mass only toward dependencies;
  reverse-dependents — the change-impact surface — systematically rank
  last and are truncated first. Run PageRank on the reversed graph or add
  weighted reverse edges.
- **Symbol-parser fidelity (same subsystem).** `extract_symbols` misses
  PEP 695 `type X = ...` aliases (repo targets ≥3.12), and `_UPPER_CASE`
  constants unparse their entire literal into repo-map "signatures,"
  displacing real API surface within the 2048-token map
  (`parser.py:77-85,148-203`). Handle `ast.TypeAlias`; render constants
  as `NAME = ...` with long literals elided.
