## Problem

`determine_transition` is deterministic logic executed as a Temporal
activity (`evaluate_transition`), violating "deterministic work should be
deterministic" — it costs an activity round-trip, worker registration, and
a mock in every workflow test. Failure-summary construction is copied
across five join sites, and result builders, persist-key construction, and
merge-resolution handling live inline in workflow code where they cannot
be unit-tested without Temporal.

## Background and Detailed Explanation

T5.1 is about moving a "what happens next?" decision out of the
network and into plain code.

**The problem.** After every workflow step, forge decides what to do
next — proceed, retry, fail, escalate. That decision is pure logic:
given the step's outcome, the answer is always the same. No I/O,
nothing external. But today it's implemented as a Temporal *activity*
(`evaluate_transition`), which means the workflow sends a task over
the wire to a worker, waits, and gets the answer back — a network
round-trip to compute something a plain function could return
instantly. It's the project's own Principle 2 being violated
("deterministic work should be deterministic"): you don't dress up
arithmetic as external work. The tax shows up everywhere — every
workflow test has to mock that activity, the worker has to register
it, and the workflow history carries events for it. And it's not
alone: a handful of other pure-logic bits (error-summary assembly
copy-pasted in five places, result assembly, merge handling) live
inline inside workflow code, where they can't be unit-tested without
booting Temporal.

**The fix.** Create one plain-Python module, `forge/step_logic.py`,
with zero Temporal imports, and move all of that pure logic into it
as ordinary functions. Workflows then just *call* them inline — which
is safe precisely because they're deterministic (Temporal replay
reproduces the same answers). The `evaluate_transition` activity gets
deleted outright, along with its registration and every test mock of
it.

**The buried gem:** today, when a fan-out task finishes, the output
file *contents* get copied into the result structure three or four
times over (top-level list, per-step, per-sub-task, resolved
conflicts). A large fan-out can approach Temporal's ~2MB payload cap
at the moment of completion — meaning the workflow fails at the
finish line, *after* all the LLM spend. T5.1 fixes that: contents
live in exactly one place, everything else carries paths and digests.
This is the same payload-limit concern behind Architecture Principle
8's parked claim-check corollary — T5.1 removes the redundancy that
makes it bite early.

**How you'll know it's done:** the full decision matrix is covered by
parametrized unit tests that run in microseconds without Temporal;
the activity and its mocks no longer exist anywhere; and a synthetic
multi-hundred-KB fan-out's final result stays comfortably under the
cap.

### Design decisions (settled)

1. **`FailureKind`** — a `Literal` in `models.py` (beside the result
   models), field `failure_kind: FailureKind | None = None` on
   TaskResult, StepResult, and SubTaskResult (`None` = success). Values,
   mapped from the terminal construction sites:
   `"validation"` (terminal validation failure, incl. leaf sub-tasks),
   `"batch_wait"`, `"step_failed"` (TaskResult when a step fails),
   `"sub_task_failed"` (gather saw failed children),
   `"sanity_abort"`, `"duplicate_sub_task_ids"`,
   `"conflict_unresolved"` (D27, resolve_conflicts=False),
   `"conflict_incomplete"` (missing resolutions),
   `"merged_validation"` (merged output failed validation).
2. **LLM run totals** — a dedicated `LLMRunTotals` model in `models.py`
   (`call_count`, `input_tokens`, `output_tokens`,
   `cache_creation_input_tokens`, `cache_read_input_tokens`,
   `llm_time_ms`), NOT a reused `LLMStats` (totals span models;
   `model_name` would lie, and summed latency is total LLM time, not
   wall time — hence `llm_time_ms`). Field
   `TaskResult.llm_totals: LLMRunTotals | None`, computed once in each
   `run()` just before the `PersistRun` persist by a pure
   `step_logic.llm_totals(task_result)` walking planner_stats +
   step/sub-task/conflict stats in the finished tree — one call site
   covers success, failure, and batch-wait paths. Known limitation
   (recorded, accepted): stats of earlier *retried* attempts are not in
   the result tree, so totals count surviving calls; authoritative spend
   stays the interactions table (D97's intent is result-level
   visibility, not accounting).
3. **Slimmed representation** — explicit new field
   `output_digests: dict[str, str]` (path → sha256 hex) on StepResult
   and SubTaskResult. `output_files` stays for the child→parent wire
   transfer (gather and conflict detection consume direct children's
   contents), and the slim builders empty it into `output_digests` at
   embed time: nested nodes slim their children before returning; the
   planned driver slims each StepResult before appending to
   `step_results`. `conflict_resolution` is slimmed via
   `model_copy(update={"resolved_files": {}})` (stats retained — it
   subclasses LLMStats). `TaskResult.output_files` remains the single
   content-carrying place. One consumer updates:
   `sanity_check.build_step_digest` counts
   `output_digests or output_files`.

### Approach

1. **`src/forge/step_logic.py`** — pure module, zero `temporalio`
   imports (imports `forge.models` + stdlib `hashlib`; plain frozen
   dataclasses for its own return types):
   `determine_transition` (moved verbatim), `failure_summary`,
   `subtask_failure_summary`, terminal-result builders that set
   `failure_kind` + summary, slim builders
   (`slim_step_result`/`slim_sub_task_result`), `llm_totals`,
   `merge_resolution(conflicts, resolved, non_conflicting) ->
   MergedFiles | MissingResolutions`, `child_timeout` (moved from
   `workflows.py:_child_timeout`), `compound_sub_task_id`,
   `sub_task_workflow_id`.
2. **`models.py`** — add `FailureKind`, `LLMRunTotals`,
   `output_digests`; delete `TransitionInput`.
3. **`workflows.py`** — inline `determine_transition` at the five call
   sites (import under `imports_passed_through`); delete
   `_TRANSITION_TIMEOUT` and the `TransitionInput` import; route the

5. **Tests** — new `tests/test_step_logic.py` (parametrized decision

   `test_worker.py`'s registration list; fold
   `test_activity_transition.py`'s pure cases into the matrix and

   `make replay-histories`.
6. **Docs** — CLAUDE.md (universal-step section: drop the "do not add
   logic to evaluate_transition" standing warning, state the inline

7. **Verification** — `make gates` (lint, mypy ×4, lint-imports, four

### 2026-07-24 — /simplify pass (post-close quality review, four-angle)

A four-agent cleanup review (reuse / simplification / efficiency / altitude)
over the uncommitted T5.1 diff produced deduped fixes, applied same-day:

- **Builder set slimmed to logic-only.** The four pass-through success
  builders (`single_step_success`, `planned_success`, `step_success`,
  `sub_task_success`) added no logic over the model constructors and were
  deleted — success results are constructed inline with
  `status=TransitionSignal.SUCCESS`. `planned_step_failure` and
  `planned_sanity_abort` merged into one `planned_failure(failure_kind,
  error, ...)` matching the fan-out builders' style. Builders that compute
  (failure_kind + wording, embed-time slimming) all remain.
- **One generic slim.** `slim_step_result`/`slim_sub_task_result` (identical
  bodies) became `slim_result[R: (StepResult, SubTaskResult)]` with an
  already-slim early return — a slim subtree is returned by reference, not
  re-copied per ancestor level. The two stats walkers merged the same way.
- **Nested wire payload fixed.** `nested_fan_out_success`/`_failure` now slim
  their own `conflict_resolution` (and all four fan-out builders slim it
  uniformly) *before* the result crosses the child→parent boundary — resolved
  contents already travel in the merged `output_files`, so the unslimmed field
  was doubling them in both workflows' histories.
- **Invariant moved into the models.** `StepResult`/`SubTaskResult` gained a
  `model_validator` rejecting both-populated `output_files`+`output_digests`
  and a `file_count` property owning the either-state count
  (`sanity_check.build_step_digest` now reads the property instead of
  encoding the lifecycle); `LLMRunTotals.from_stats` owns the stats→totals
  field mapping beside the field definitions. The `output_digests` field
  description now states the real invariant (a failed step's contents are
  dropped from the result and survive only in its worktree — they are *not*
  folded into `TaskResult.output_files`).
- **Smaller cleanups:** `MissingResolutions.message` owns the
  incomplete-resolution wording; the batch-wait builders take the exception
  and own the "Batch wait failed:" prefix; the `match` arms whose only job
  was name-binding became `isinstance` narrowing; the planned driver appends
  each slimmed step once instead of per-branch; the sha256 test pins a known
  vector instead of mirroring the implementation; the `failure_kind`
  parametrize is typed `FailureKind` (ignore removed).

Deliberately skipped (recorded, not fixed): composing parent digests from
children's digests (couples slimming to merge provenance for a ms-scale win);
the scripted-transition token vocabulary and per-scenario `max_attempts`
tuning in `test_workflows.py` (T5.5 harness rebuild); the duplicate-ids /
merged-validation / D27 message duplication across the two gathers (T5.3's
single gather dissolves the second copy); folding a failed step's contents
into `TaskResult.output_files` (a behavior change — documented instead).
