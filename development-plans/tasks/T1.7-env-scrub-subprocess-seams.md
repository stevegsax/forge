## Problem

**Critical:** `validate.py` test commands and the `run_tests` exploration
provider execute model-influenced commands with the worker's full env (API
keys, DB URLs, TLS paths).

## Scope

- Explicit allowlist env dict (PATH, HOME, VIRTUAL_ENV, LANG, TMPDIR) at
  those two seams.
- **Amendment (2026-07-08):** drop root at the unit level too — the EC2
  systemd units run the worker as root with zero hardening, so the scrubbed
  env still executes model-influenced commands as root on the instance
  holding all platform secrets. Harden `deploy/systemd/forge-worker@.service`
  and `pbook-worker.service`: `User=forge`/`Group=forge`,
  `NoNewPrivileges=true`, `ProtectSystem=strict` (+ `ReadWritePaths=` for
  the app/data dirs), `ProtectHome=true`, `PrivateTmp=true`.

## Plan

Two independent defenses, both cheap:

1. **Env allowlist (pure core + two shell seams).** A pure
   `allowlist_env(environ)` returns only `PATH, HOME, VIRTUAL_ENV, LANG, TMPDIR`
   from a given mapping. The shell supplies `os.environ` at each subprocess
   runner and passes the result as `subprocess.run(..., env=...)`, which
   *replaces* the child environment rather than augmenting it — so every unlisted
   var (API keys, `FORGE_DB_URL`, `AWS_*`, TLS paths) is dropped by construction.
   Apply at both model-influenced seams T1.4 left:
   - `validate.py::_run_command` — the single runner all lint/format/test checks
     route through.
   - `providers.py` — a new shared `_run_scrubbed` that every shell-out handler
     (rg, pytest, ruff, git ×5) routes through.

2. **Systemd privilege drop.** Harden both worker units to run as an
   unprivileged `forge` user with a read-only filesystem, so the scrubbed
   commands no longer execute as root on the secret-bearing box. Bootstrap
   creates the account and hands it the paths the worker writes.

## Development Notes

- 2026-07-08 — Amended pre-implementation per
  [forge-review-2026-07-08.md](../../forge-review-2026-07-08.md) §4.5: env
  scrub without privilege drop leaves C3's subprocesses running as root;
  the systemd hardening is the same cheap-fix class as the scrub.

- 2026-07-15 — Implemented. Result: **1221 passed / 4 deselected**, coverage
  **87.93%** (gate 85%), ruff clean on all changed files (the two pre-existing
  `tests/test_worker.py` findings TC003/SIM117 are untouched — not in this
  diff). Single commit on `phase-1`.

- **Allowlist as a pure function.** New `src/forge/subprocess_env.py` holds
  `allowlist_env(environ: Mapping[str, str]) -> dict[str, str]` +
  `ALLOWED_SUBPROCESS_ENV_KEYS = (PATH, HOME, VIRTUAL_ENV, LANG, TMPDIR)`. It
  reads nothing itself; the shell hands it `os.environ`. `subprocess.run(env=...)`
  *replaces* the child env wholesale, so exclusion is by construction — secrets
  can't leak even if a new one is added to the worker env later. Absent
  allowlist keys are omitted (not blanked) so we never mask an unset var.

- **Clean seam per T1.4.** T1.4's Development Notes deliberately kept the
  `to_thread` boundary off the `subprocess.run(...)` internals precisely so this
  task had "a clean seam (env dict)". Both seams already funnel through one
  runner each: `validate.py::_run_command` (all lint/format/test checks) and —
  new here — `providers.py::_run_scrubbed`, which every shell-out handler now
  calls. So the scrub is two `env=` additions, one per runner, covering rg,
  pytest, ruff, git, and every validate check. Kept the two runners separate
  (different return shapes: `SubprocessResult` vs `CompletedProcess`) but both
  delegate env-building to the shared pure function.

- **PATH/VIRTUAL_ENV are load-bearing, not optional.** With `env=` replacing the
  whole environment, the child can only find `python`/`pytest`/`ruff`/`rg`/`git`
  via the preserved `PATH`, and pytest/ruff resolve the project venv via
  `VIRTUAL_ENV`. Verified by
  `TestValidateEnvScrub::test_real_pytest_passes_under_scrubbed_env`: a genuine
  `python -m pytest` command runs a temp test file green under the scrubbed env
  (with a sentinel `ANTHROPIC_API_KEY` set). If the allowlist were too tight
  this test would fail, not silently pass.

- **Systemd hardening — write-path analysis.** Traced every path the worker
  writes so `ProtectSystem=strict` + `ReadWritePaths` would not brick it:
  - `/data` — logs (`FORGE_LOG_DIR=/data/forge/logs`), git worktrees (repos
    cloned under `/data/repos`, worktrees at `<repo>/.forge-worktrees/…`), and
    `pbook.db` (`/data/pbook/pbook.db`).
  - `/srv/forge-app` — the app + venv, plus uv's managed Python and cache. Set
    `Environment=HOME=/srv/forge-app` (not under `/home`, so unaffected by
    `ProtectHome=true`) so uv's `$HOME/.local/share/uv` + `$HOME/.cache/uv`
    resolve to a forge-owned, writable path. **Gotcha:** the original bootstrap
    ran `uv sync` as root, which would drop the managed interpreter under
    `/root` — inaccessible to the forge user once `ProtectHome=true` is on. Fix:
    bootstrap now runs `uv sync`/`pbook migrate` with `HOME=$APP_DIR`, then
    `chown -R forge:forge $APP_DIR /data`, so the interpreter the venv points at
    is forge-owned.
  - `ReadWritePaths=/srv/forge-app /data` covers all of the above; `/etc/forge`
    stays read-only (only read for `EnvironmentFile`). Loopback Temporal
    (127.0.0.1:7233) is unaffected — none of these directives touch networking.
  - Directives added to **both** units: `User=forge`, `Group=forge`,
    `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true`,
    `PrivateTmp=true`, `ReadWritePaths=/srv/forge-app /data`,
    `Environment=HOME=/srv/forge-app`.

- **Bootstrap changes.** Creates the `forge` system group+user
  (`--home-dir $APP_DIR`, `/sbin/nologin`, idempotent via `getent`), runs the
  venv build + pbook migrate under `HOME=$APP_DIR`, and `chown -R forge:forge
  $APP_DIR /data` right before installing/starting the units (after
  `docker compose up`, so the temporal stack is untouched — root still reads the
  now forge-owned config).
