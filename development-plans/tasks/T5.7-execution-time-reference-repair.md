## Problem

A plan-authored reference to a file that does not exist yet is swallowed
on the live path: `_read_context_files`
(`src/forge/activities/context.py:584`) skips missing files with a
warning log, so a step whose context names a file only a *later* step
creates runs on silently incomplete context and degrades output quality
with no failure signal. The forward/cyclic-reference finder that would
catch this exists in `forge/plan_checks.py` (T5.6) but runs only in the
eval harness, because at plan-acceptance time "reads a file a later step
modifies" (legitimate) and "reads a file only a later step creates"
(defect) are indistinguishable without the repo file set.

## Background and Detailed Explanation

T5.7 closes the one gap T5.6's preflight gate could not: catching a plan
whose steps reference files in the wrong order, and letting the planner
repair its own plan when it happens.

**The problem.** A "forward reference" is a plan defect where step 2
wants to *read* a file that only step 4 *creates* (a cycle is the
mutual version). The preflight gate cannot detect this because it runs
as pure workflow code with no filesystem access, and without knowing
which files already exist, a forward reference is structurally
identical to the completely normal pattern of reading a file an earlier
commit put in place. So today the defect sails through the gate, and at
execution the missing file is silently skipped by context assembly —
the step's LLM call proceeds with incomplete context, and the only
trace is a warning in a log nobody watches. The failure mode is
degraded output, not a crash: the worst kind, because nothing halts.

**The fix.** Detect at the moment the ambiguity disappears. When
`assemble_step_context` runs, it is already an activity standing in the
worktree, and every file that *should* exist by that point *does*
exist — so a plan-authored context reference that is missing right then
is unambiguous, with no false positives possible. The activity reports
the fact (a structured list of missing plan-authored references on its
existing output, a backward-compatible optional field); the workflow,
which holds the whole plan, classifies the fact with the shared
`plan_checks` finders: "created by a later step" (forward reference) or
"appears nowhere in the plan" (hallucinated path). The diagnosis then
routes into the sanity/REVISE arm as revision context — the same
violation-message shape the preflight gate feeds planner retries — so
the planner gets a bounded chance to repair its own plan mid-flight.
The revision rides `MAX_PLAN_REVISIONS` and the over-cap guard T5.6
built (`splice_revision`); when the cap is exhausted or the revised
plan is still defective, the run terminates cleanly with a named
failure kind instead of degrading silently. Autonomy is the point;
the cap is what makes it safe to grant.

**What this is and is not.** This is detection at first bite, not
prevention: steps before the defective one have already run and
committed, so a defective plan is discovered mid-flight, not before
takeoff — strictly better than silent degradation, but not the
preflight AC's original letter, and this task is the deliberate
resolution of that recorded **Partial**. Two boundaries keep false
positives out: *target* files are exempt (a step's target legitimately
may not exist yet — creating it is the step's job; only the *read* set
is checked), and task-level `context_files` supplied by the user keep
today's skip-with-warning behavior (a missing user-supplied file is an
input problem, not a plan defect, and must not burn a plan revision).

**The replay constraint.** The happy path's command sequence must not
change: the check piggybacks on an activity that is already scheduled,
and the classification is pure workflow logic on that activity's
result. New behavior appears only in runs whose plans are defective —
which no committed history contains — so all committed replay
histories must pass unregenerated.

**How you'll know it's done:** a plan whose step reads a file a later
step creates triggers a named diagnosis at that step's assembly, a
capped REVISE repair with the diagnosis in the planner's context, and
either a successful resumption or a clean `plan_revision` terminal —
while a run with a healthy plan produces a byte-identical command
sequence to today's.

## Scope

- `assemble_step_context` (and the sub-task assembly path,
  `context.py:988` — both read plan-authored `context_files`): report
  missing plan-authored context references as structured data on the
  activity output — an optional field defaulting to empty, so
  previously recorded payloads still deserialize (the in-flight-run
  hazard T5.6's Development Notes flagged for `LLMResponse` must not be
  repeated here). The skip-with-warning behavior is unchanged for
  task-level (user-supplied) context files. Target-file reads are never
  flagged.
- Workflow-side classification: a pure helper in `forge/plan_checks.py`
  (reusing the existing finders) mapping the missing-file list + plan to
  named diagnoses — forward reference (names the creating step) vs
  unknown path.
- Reaction (owner-ruled 2026-07-27): route the diagnosis into the
  REVISE arm as revision context; the revision rides the existing
  `MAX_PLAN_REVISIONS` cap and `splice_revision` guard; cap exhaustion
  or a still-defective revision terminates cleanly
  (`failure_kind="plan_revision"` unless implementation finds a reason
  to distinguish — record the choice). Step-level retry is explicitly
  the wrong arm: the same file is still missing on every retry.
- Tests in the rebuilt harness (`ScenarioState`, keyed scripting,
  `sync_mode=True`): forward-reference → REVISE repair → resumption;
  cap exhaustion → clean terminal; unknown-path diagnosis; missing
  user-supplied context file still skip-with-warning; target-file
  creation not flagged. Pure classification unit-tested without
  Temporal.

## Acceptance Criteria

- [ ] A step whose plan-authored context references a file absent from
      the worktree at assembly time produces a structured missing-file
      report and a named workflow-side diagnosis (forward reference
      with the creating step named, or unknown path) — no silent skip
      for plan-authored references.
- [ ] The diagnosis routes into the REVISE arm with the violation list
      in the planner's revision context; a successful revision splices
      through `splice_revision` and execution resumes.
- [ ] Revisions triggered this way ride the existing
      `MAX_PLAN_REVISIONS` cap; cap exhaustion or a still-defective
      revision terminates cleanly with a named `failure_kind`.
- [ ] Target files and user-supplied task-level context files are
      exempt: a step creating a new file and a missing user-supplied
      context file each behave exactly as today.
- [ ] All committed replay histories pass unregenerated (the happy-path
      command sequence is unchanged).
