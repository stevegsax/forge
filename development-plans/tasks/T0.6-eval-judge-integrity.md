## Problem

- **The judge is blind.** `judge_plan` accepts and renders `repo_context`
  (`eval/judge.py:64-67,176-193`) but its only caller passes none
  (`eval/runner.py:133`), so the completeness ("covers all required
  target files") and context-quality criteria are scored without seeing
  the repo — noise dressed as measurement.
- **Criterion coverage is unvalidated.** Nothing enforces one score per
  `JudgeCriterion` (`eval/models.py:59-63`); `compare_runs` averages
  whatever arrived (`runner.py:84-85`), so a baseline averaged over six
  criteria can be compared against a candidate averaged over three.
- **The comparison math is single-sample.** One judge call per plan, an
  undocumented ±0.5 band, a 3-case corpus (`runner.py:57-109`) — judge
  noise on a 1–5 scale plausibly exceeds the band.

## Scope

- Plumb repo context derived from `case.repo_root` (file listing or
  code_intel repo map) through `evaluate_plan`/`evaluate_corpus` into
  `judge_plan` — or delete the dead parameter and the repo-dependent
  criteria claims. Wire it or remove it; no dead honesty theater.
- `JudgeVerdict` model_validator: exactly one score per criterion
  (reject duplicates; require all criteria or average only over criteria
  common to both verdicts).
- Name the ±0.5 band as a documented constant; add a
  single-sample/small-corpus caveat to `EvalComparison.summary`;
  optionally support n judge samples with score averaging. Full
  evidence-grade methodology (corpus growth, significance) stays deferred
  to the "Eval as CI release gate" backlog item — cross-reference it
  there.

## Acceptance Criteria

- [ ] Judge prompts contain repo context for cases with a `repo_root`
      (golden-prompt test), or the parameter and dependent criteria are
      gone.
- [ ] Duplicate and missing-criterion verdicts fail validation (tests).
- [ ] `EvalComparison.summary` carries the sample-size caveat.
