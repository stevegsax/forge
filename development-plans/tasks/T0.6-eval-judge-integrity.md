# T0.6 — Eval judge integrity

**Status:** DONE

**Repos:** forge
**Depends on:** —
**Last updated:** 2026-07-18

> Added by the 2026-07-08 capture sweep (findings G19/G20/G21). Minor
> individually, but together they mean `forge eval-planner` output cannot
> be trusted as evidence — and the eval framework is the tool the
> migration's own quality gates lean on.

## Problem

- **The judge is blind.** `judge_plan` accepts and renders `repo_context`
  (`eval/judge.py:64-67,176-193`) but its only caller passes none
  (`eval/runner.py:133`), so the completeness ("covers all required
  target files") and context-quality criteria are scored without seeing
  the repo — noise dressed as measurement.
- **Criterion coverage is unvalidated.** Nothing enforces one score per
  `JudgeCriterion` (`eval/models.py:59-63`); `compare_runs` averages
  whatever arrived (`runner.py:84-85`), so a baseline averaged over six
  criteria can be compared against a candidate averaged over three.
- **The comparison math is single-sample.** One judge call per plan, an
  undocumented ±0.5 band, a 3-case corpus (`runner.py:57-109`) — judge
  noise on a 1–5 scale plausibly exceeds the band.

## Scope

- Plumb repo context derived from `case.repo_root` (file listing or
  code_intel repo map) through `evaluate_plan`/`evaluate_corpus` into
  `judge_plan` — or delete the dead parameter and the repo-dependent
  criteria claims. Wire it or remove it; no dead honesty theater.
- `JudgeVerdict` model_validator: exactly one score per criterion
  (reject duplicates; require all criteria or average only over criteria
  common to both verdicts).
- Name the ±0.5 band as a documented constant; add a
  single-sample/small-corpus caveat to `EvalComparison.summary`;
  optionally support n judge samples with score averaging. Full
  evidence-grade methodology (corpus growth, significance) stays deferred
  to the "Eval as CI release gate" backlog item — cross-reference it
  there.

## Plan

Landed alongside T0.1 and T0.2 (shared `cli.py`).

1. **Wire repo context (chosen over removal).** Add a pure
   `format_repo_context(files, *, max_files=…)` to `eval/judge.py`: sorted,
   capped file listing with an "N more not shown" line when truncated (the
   size cap keeps huge repos from blowing the prompt). Both judge callers
   derive `repo_context` from the file set they already have — `_run_eval`
   from its `known_files` (`cli.py`), `evaluate_plan` from its
   `known_repo_files` (`runner.py`) — and pass it into `judge_plan`.
2. **Criterion validation.** Add a `model_validator(mode="after")` to
   `JudgeVerdict`: exactly one score per `JudgeCriterion` — duplicates
   rejected, all criteria required. `compare_runs` averaging stays honest
   (matched, complete sets guaranteed upstream). NOTE: in production the
   judge verdict is parsed via `llm.complete(output_type=JudgeVerdict)`, so a
   validator failure surfaces as `LLMSchemaMismatch` (retryable) at the
   `model_validate_json` seam — correct behavior, not a crash.
3. **Comparison math.** Name the ±0.5 band as
   `JUDGE_SCORE_SIGNIFICANCE_BAND` in `runner.py`; add a
   single-sample/small-corpus caveat to `EvalComparison.summary`. The
   n-sample averaging and judge benchmark stay deferred (operator-optional)
   to the "Eval as CI release gate" backlog item — not built here.

## Development Notes

**2026-07-18 — landed (with T0.1, T0.2).**

- *Repo-context formatter.* `format_repo_context(files, *, max_files=200)` in
  `eval/judge.py` — pure: sorts the file set, lists up to `max_files` paths,
  and appends "... and N more file(s) not shown." when truncated. The
  file-count cap (not a char budget) is the size guard — deterministic and
  trivially testable; 200 paths is a few KB. Both judge callers derive context
  from the file set they already had: `_run_eval` from its `known_files`,
  `evaluate_plan` from its `known_repo_files`. `evaluate_corpus` gets it for
  free through `evaluate_plan`.
- *Validator surfaces as `LLMSchemaMismatch` in production.* `JudgeVerdict`'s
  `model_validator(mode="after")` raises `ValueError` on a duplicate/missing
  criterion; in the runtime judge path the verdict is parsed via
  `llm.complete(output_type=JudgeVerdict)` → `output_type.model_validate_json`
  (confirmed at `libs/sax-platform/.../llm/client.py:253-255`), which catches
  `ValidationError` and re-raises the typed, retryable `LLMSchemaMismatch`. So
  a malformed judge response retries rather than corrupting a comparison — the
  intended behavior.
- *Test repair.* The new invariant means any `JudgeVerdict(...)` must be a full
  6-criterion verdict (or an explicit `pytest.raises(ValidationError)`). Fixed
  every partial construction across `test_eval_models.py`,
  `test_eval_judge.py`, `test_eval_runner.py` via small `_full_verdict`/
  `_all_criteria_scores` helpers; `_make_record` now scores all six criteria
  the same value so its average still equals the intended `avg_score`.
- *Comparison math.* Named the band `JUDGE_SCORE_SIGNIFICANCE_BAND = 0.5` and
  appended a standing single-sample/small-corpus caveat to
  `EvalComparison.summary`. Deferred (operator-optional, per scope): n-sample
  averaging + significance and the judge benchmark — cross-referenced in the
  constant's docstring to the "Eval as CI release gate" backlog item.
