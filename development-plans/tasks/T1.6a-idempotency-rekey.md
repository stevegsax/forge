# T1.6a — Idempotency rekey

**Status:** DONE
**Phase:** 1 — Stop the bleeding (current repos)
**Repos:** forge
**Depends on:** —
**Last updated:** 2026-07-15

## Problem

Workflow-ID reuse + `insert_or_ignore` silently swallows every persisted
record when the same `forge-task-{id}` is re-run (the most common
solo-operator action); `_persist_seq` makes interaction keys positional.

## Background and Detailed Explanation

Forge derives a task's Temporal workflow ID deterministically from the
task id (`forge-task-{id}`), so rerunning the same task reuses the same
workflow ID — and rerunning a task is the most common thing a
solo-operator does. Persisted records carried **idempotency keys** (a
stable key that makes a repeated write a safe no-op) built from that
workflow ID, and the write used `insert_or_ignore`. The two combined
into a silent data-loss bug: on a rerun every record regenerated the
same key and `insert_or_ignore` swallowed all of it, so the second run
left no trace. The interaction keys were also positional (`_persist_seq`),
which collided whenever a step repeated (a repeated sanity check).

The missing discriminator was Temporal's `run_id` — fresh per execution
and replay-stable via `workflow.info().run_id`. The fix rekeyed
interaction records to `{workflow_id}:{run_id}:{role}:{occurrence}`,
where `occurrence` is a **per-role** counter held in workflow state (a
`dict[str, int]` on the instance) rather than a single positional
sequence — workflow state replays identically, and per-role means a
repeated sanity check gets its own slot instead of colliding. The runs
table was rekeyed from `unique(workflow_id)` to a composite
`(workflow_id, run_id)`, and readers (`forge status`, the `past_runs`
provider) now surface the run id and show the latest run per workflow.

The Alembic migration is the part that needed care. A naive full-table
recreate would reset the Postgres SERIAL sequence and cause primary-key
collisions on the next insert, so the migration is dialect-branched:
direct ALTERs on Postgres (preserving the sequence), a copy-recreate on
SQLite. Legacy rows backfill a `"legacy"` sentinel run id, and old
three-segment interaction keys reshape to four segments by inserting that
sentinel — an injective transform, so no transient uniqueness violation
during the row-by-row update. The downgrade is honest about its limit: it
cannot restore a single-column unique over data that only became valid
because of the rekey, and it raises if reruns already exist.

## Scope

- Interaction keys become `{workflow_id}:{run_id}:{role}:{occurrence}` with
  **per-role occurrence counters held in workflow state**
  (replay-deterministic; immune to the repeated-sanity-check collision).
- Runs table rekeyed `(workflow_id, run_id)` — Alembic migration + all reader
  updates (`forge status` etc.).

## Plan

**Root cause.** `forge-task-{task_id}` is the deterministic Temporal workflow ID,
so rerunning a task reuses it. Interaction idempotency keys were
`{workflow_id}:{role}:{seq}` and the runs table was `unique(workflow_id)`; on a
rerun the same keys/workflow_id regenerate and `insert_or_ignore` silently
swallows every row. The Temporal `run_id` (fresh per execution, replay-stable
via `workflow.info().run_id`) is the missing discriminator.

**Fix, two parts.**

1. *Interaction keys* → `{workflow_id}:{run_id}:{role}:{occurrence}` where
   `occurrence` is a **per-role counter held in workflow state**
   (`dict[str, int]` on the workflow instance, replacing the single positional
   `_persist_seq`). A workflow-state counter replays identically; an
   activity-side counter would not. Per-role means a repeated sanity check gets
   its own occurrence and never collides. New pure helper
   `build_interaction_idempotency_key(...)` in `persist_models` (sandbox-safe).
2. *Runs table* rekeyed `(workflow_id, run_id)`: add `run_id` column, drop the
   standalone `workflow_id` unique, add a composite unique
   `uq_runs_workflow_id_run_id`. `PersistRun` and `save_run` carry `run_id`;
   `ForgeTaskWorkflow.run()` passes `workflow.info().run_id`.

**Migration (002).** Dialect-branched to avoid the Postgres SERIAL-sequence
reset that a full table-recreate would cause:

- common: `add_column run_id` (nullable) + backfill sentinel `"legacy"`.
- Postgres: `alter_column NOT NULL`, drop the inspected `workflow_id` unique,
  add composite unique (direct ALTERs — no recreate, sequence intact).
- SQLite: `batch_alter_table(copy_from=…, recreate="always")` omitting the old
  unique, alter `run_id` NOT NULL, add composite unique (rowid continues at
  max+1 — validated).
- interactions: reshape old `{wf}:{role}:{seq}` → `{wf}:legacy:{role}:{seq}`
  (occurrence := old positional seq; injective, so no transient uniqueness
  violation). Downgrade reverses all of the above (restoring the `workflow_id`
  unique can fail if reruns already exist — documented, inherent).

**Readers.** `get_run` returns the latest run for a workflow_id (order by
`created_at, id` desc). Display sites surface `run_id`: `forge status` list +
detail, `forge extract --dry-run`, and the `past_runs` context provider.

## Development Notes

### 2026-07-15 — Implementation

**Where the occurrence counter lives.** Per-role counters are a `dict[str, int]`
on each workflow instance (`ForgeTaskWorkflow`, `ForgeSubTaskWorkflow`),
replacing the single positional `_persist_seq`. Incremented in
`_persist_interaction`; occurrence is 0-based per role. Workflow-state → replays
identically. Key built by the pure `build_interaction_idempotency_key` in
`persist_models` (sandbox-safe, no I/O), shape
`{workflow_id}:{run_id}:{role}:{occurrence}` with `run_id = workflow.info().run_id`.

**run_id source.** `workflow.info().run_id` (Temporal execution id, fresh per
run, replay-stable). Threaded through `PersistRun.run_id` →
`persist_to_store` → `save_run(..., run_id)` → `insert_or_ignore(index_elements=
["workflow_id","run_id"])`. Only `ForgeTaskWorkflow.run()` writes a run row;
sub-tasks don't (unchanged).

**Migration 002 — backfill mapping.**

- *runs*: added `run_id` (sentinel `"legacy"` for pre-migration rows). Each old
  row was unique on `workflow_id`, so `(workflow_id, "legacy")` stays unique.
  Swapped the standalone `workflow_id` unique for composite
  `uq_runs_workflow_id_run_id`.
- *interactions*: old `{wf}:{role}:{seq}` → `{wf}:legacy:{role}:{seq}`, i.e.
  **occurrence := the old positional seq verbatim**. This is the "sensible
  occurrence backfill" the task permits: occurrences are no longer per-role
  contiguous (e.g. two `llm` rows keep seqs 1 and 3, not 0 and 1), but they stay
  unique, which is all the idempotency key needs. The transform only inserts a
  constant segment, so it is injective — distinct old keys → distinct new keys,
  and new (4-segment) keys never equal any un-rewritten (3-segment) key, so there
  is no transient uniqueness violation during the per-row UPDATE loop.

**Dialect branch (why).** A full table recreate on Postgres would reset the
`runs.id` SERIAL sequence and cause PK collisions on the next insert. So Postgres
uses direct ALTERs (inspect + drop the `workflow_id` unique, add composite, set
`run_id` NOT NULL); SQLite uses `batch_alter_table(copy_from=…, recreate="always")`
(rowid continues at max+1 — verified in a scratch run). Validated end-to-end on
SQLite: upgrade reshapes keys and records reruns; clean downgrade round-trips a
legacy-only DB; downgrade raises `IntegrityError` when reruns already recorded
multiple rows per `workflow_id` (inherent — you can't restore a single-column
unique over data that depends on the rekey; documented in the migration).

**Scope kept tight.** The bespoke `{wf}:extraction` key in
`extraction_workflow.py` is intentionally left unchanged: extraction workflow_ids
are uuid-suffixed (not reused across runs like `forge-task-{id}`), so they are
outside the rerun-collision path. The migration's reshape regex requires a
trailing numeric seg, so it never touches those keys.

**Readers updated:** `store.get_run` (now latest-wins: `order_by created_at, id
desc`), `forge status` list + `--workflow-id` detail (`cli.py`), `forge extract
--dry-run` listing (`cli.py`), and the `past_runs` context provider
(`providers.py`) all now surface `run_id`. `list_recent_runs` needed no query
change (selects `*`; the new column rides along).

**Verification:** full `uv run pytest -q`, `-m postgres --no-cov` (testcontainers),
and `ruff check .` — see CHANGELOG/return.
