## Problem

ocr's gather and store workflows are both ABANDON-children of a
fire-and-forget parent, so completion travels by signal and a failed store
child hangs the gather for 26h (verified). With forge's poller and the
signal SPI deleted in [T4.1](T4.1-forge-timer-loop-transport.md), ocr must
poll its own Mistral batches via the platform's `MistralOcr`; restructuring
the gather to parent-awaited children removes the last cross-workflow
signal platform-wide.

## Scope

ocr polls its own Mistral batches via `MistralOcr` timer-loop (same
pattern as T4.1); delete its `BATCH_RESULT_SIGNAL` handling and the SPI
wire models from contracts; **restructure gather to parent-awaited
children** (today both gather and store are ABANDON-children of a
fire-and-forget parent, so completion travels by signal and a failed store
child hangs the gather for 26h — verified); typed activity inputs (the
seven `input_json: str` activities → pydantic models through the installed
converter); `OcrJobEntry.status` enum;
`_derive_status(OcrProcessingStatus, BatchJobStatus|None)` + docstring
fixes.

### Grounding data (parked-proposal prerequisites, gathered 2026-07-19)

- **Burst shape confirmed from code:** one Mistral batch per **chunk** (not
  per document) — `OcrSubmitWorkflow` submits each chunk as its own
  single-request batch with its own store child. A 1,000-doc burst ⇒ ≥1,000
  concurrent waiters.
- **Mistral rate limits:** the docs publish no tier numbers — real RPS/TPM
  live in the workspace admin console
  (`admin.mistral.ai/plateforme/limits`); **owner to read and record**.
  Hard facts from docs: ≤100,000 requests / 512MB per batch; batch
  *processing* does not count against real-time limits; status polls
  (`jobs.get`) do.
- **Mitigation shipped here (cheapest-in-D88):** per-waiter jitter +
  adaptive backoff — 300s cadence for the first hour (mode ≈ 30min clears
  most jobs), then ×2 per poll to a 1800s cap. 25h at worst-case cadence is
  well inside the history budget. The cache-refresher stays parked; note
  for that discussion: batch **coalescing** (100k requests/batch) is a
  third option that dissolves the waiter count at the source.

### Design

1. **Parent-awaited children; `OcrGatherWorkflow` deleted.** Submit
   workflow: dup-check → read → split → per chunk (build blob → submit via
   ocr's own activity → start store child **with the real batch_id**, no
   ABANDON) → await all children → multi-chunk: `reassemble_ocr_chunks`
   inline in the parent. A failed chunk propagates immediately (AC1). The
   old start-child-before-submit ordering existed only so the poller could
   route signals; submit-then-start-child replaces it.
2. **Store child = timer loop + fetch-and-store.** Poll via a thin ocr
   `ocr_batch_status` activity (`MistralOcr.get_batch_status`); on ended,
   ONE `fetch_and_store_ocr_result` activity downloads
   (`MistralOcr.fetch_batch_results`, select entry by request_id) and
   stores in the same activity — result bytes never transit workflow
   history, so ocr needs no claim-check envelope at all. Terminal edges
   persist `PersistBatchOutcome` cross-queue (an activity call, not a
   signal) and upsert ocr status. 25h ceiling + failure symmetry as in
   forge.
3. **Shared poll loop extracted** to `sax_platform.temporal.polling`:
   `wait_batch_ended(status_fn, *, schedule)` (sleep/deadline/state
   dispatch skeleton, pure backoff+jitter schedule fn, `workflow.random()`
   for replay-safe jitter) + `BATCH_WAIT_CEILING` moves there. Forge's
   `batch_submit_and_wait` cuts over as the second consumer — **the T4.1
   replay histories are the determinism guard** (fixed-interval schedule
   must reproduce forge's exact command sequence).
4. **ocr owns submit.** New ocr activity: fetch request blob (own
   `S3Blobs`) + `MistralOcr.submit_batch`. Forge's `submit_batch_blob`,
   `execute_submit_batch_blob`, `_AnthropicBlobSubmit`,
   `_resolve_blob_submit_provider`, `BatchActivities.mistral_ocr`, and the
   forge worker's MistralOcr construction are deleted — forge's transport
   becomes anthropic-only (a non-anthropic provider raises a clear error);
   forge's `batch_fetch` mistral branches go with it.
5. **Contracts:** `PersistBatchOutcome` moves to
   `sax_platform.contracts.persist` (ocr needs it cross-queue; forge
   imports from there). Delete `BatchSubmitSpiInput`, the `BatchResult`
   envelope model + `resolve_batch_result` (forge's parse resolves via
   `blobs.get` + `parse_batch_result_payload` directly), and
   `BATCH_RESULT_SIGNAL`. Keep `dump/parse_batch_result_payload` (forge's
   claim-check) and `PersistBatchSubmission` (ledger write; `workflow_id`
   stays as audit provenance = the store child that polls).
6. **Timeout tree (T4.1 lesson applied):** store child execution timeout =
   ceiling + margin; submit parent = ceiling + margins + reassembly; set at
   the ocr CLI submission site.
7. **Scope carry-overs:** the seven `input_json: str` activities → typed
   pydantic inputs; `OcrJobEntry.status` enum;
   `_derive_status(OcrProcessingStatus, BatchJobStatus | None)` +
   docstring fixes.

**2026-07-17 — PARKED PROPOSAL (owner): batch-tracker workflow for
Mistral polling.** Documented for a full discussion later; **T4.1/T4.2
proceed as specced** — the owner's direction is "usable, valid state
first; optimize later." This note exists so the discussion starts from
the full picture.

*New operational data points (owner-provided, 2026-07-17):*

- OCR submission is extremely peaky: most of the time zero documents
  are in process, but a batch of **1,000 documents is ordinary**.
  1,000 in-process documents are no issue for Mistral; 1,000 of our
  poll requests may well hit a rate limit.
- Processing time is highly variable and uncorrelated with document
  size/content: model it as 1–1440 minutes with the mode around 30
  until better data exists.

*Why this matters:* D88's polling arithmetic was calibrated on forge's
Anthropic waiters (~30 concurrent worst case). If a 1,000-document
burst means 1,000 concurrent waiters each self-polling at the 300–600s
floor, that is 100–200 RPM of status calls against Mistral's limits —
a different regime. **Open question to resolve first:** the current
shape appears to be one batch job per document (`OcrSubmitWorkflow`
chunks a *single* file into one Mistral batch), so a 1,000-doc burst =
1,000 waiters — confirm this, and gather Mistral's actual per-tier
rate-limit numbers, before sizing anything.

*The proposal (as stated by the owner):* an event-driven **batch
tracker**. Each batch request carries a state machine that accepts
server-status messages (submit-error / acknowledged-running / finished
/ errored) and, once terminal, ignores everything — so message
ordering and replay are irrelevant by construction. Flow: (1) on
successful submit, the job registers "my message address + my batch
id" with the tracker (stored in a DB column); (2) while ≥1 batch is
active, the tracker polls the provider's **list** endpoint every ~2
minutes; (3) for each known batch (submitted within 24h) it sends the
registered address the most recent status; (4) receivers transition
their state machine; late/out-of-order messages after a terminal
state are dropped.

*Assessment recorded for the discussion (Claude, 2026-07-17):*

- **Genuinely different from the deleted D77/D78 poller** in two ways
  that matter: (a) it delivers status *hints*, not result payloads —
  if waiters fetch their own results keyed by their own batch_id on
  "done", the C1 wrong-result corruption becomes structurally
  impossible (a misrouted hint at worst triggers a harmless early
  self-fetch); (b) terminal-state absorption at the receiver makes
  duplicates and reordering harmless by design. Neither property held
  in the deleted poller.
- **What it re-introduces:** C2-shaped liveness coupling — a dead or
  stalled tracker strands every waiter. Mitigable: each waiter keeps a
  slow self-poll backstop (no update within N minutes → one direct
  status call), so the system degrades to D88 instead of failing.
- **Temporal mechanics to work out:** status-every-cycle to every
  waiter is history-expensive on both sides (up to 1,000 external
  signals per 2-minute cycle from the tracker; ~30 no-op signals/hour
  accumulating in each long-running waiter). Change-only delivery is
  the obvious refinement; tracker continue-as-new cadence needs
  design either way.
- **Variant to compare — shared status *cache*, not shared delivery:**
  the tracker refreshes the `batch_jobs` ledger from the provider's
  list endpoint (~0.5 RPM regardless of burst size); waiters keep the
  T4.1/T4.2 timer loop *unchanged*, but their `batch_status` activity
  reads the local ledger instead of Mistral, falling through to a
  direct provider call past a staleness threshold. No signals, no
  registration, no correlation anywhere; C1 impossible, C2
  self-healing; provider load identical to the tracker proposal. This
  may capture the entire benefit with a much smaller delta from the
  landed design.
- **Cheapest in-D88 mitigations** if the burst math is confirmed but
  new machinery is deferred: per-waiter jitter, and adaptive backoff
  shaped to the 1–1440min/mode≈30 distribution (poll fast early,
  back off hard after the first hour).

**2026-07-17 (later) — owner: cache-refresher variant is the
frontrunner** when this is picked back up. Owner's additional
arguments, with assessment caveats recorded alongside:

- *Local checks are ~free → waiter cadence can drop dramatically.*
  True against the provider (zero Mistral calls) and the DB (trivial
  SELECT by batch_id). Caveat: Temporal history still floors the
  waiter's loop — ~11 events/iteration means a 25h job polled at 120s
  is ~8k events (fine, ~16% of the 51.2k limit) but at 30s is ~33k
  (uncomfortable) and at 10s blows the limit. Practical floor for
  day-long jobs: **~1–2 min waiter cadence** without continue-as-new.
  Also note 1,000 concurrent waiters at 2-min cadence = ~500 activity
  executions/min against the local worker — fine for Postgres, but
  tune worker activity caps.
- *System completion latency drops to ~the refresh interval.* Broadly
  right: worst case ≈ tracker refresh (2 min) + waiter cache-poll
  interval (~2 min) ≈ 4 min, typical ~2–3 — versus the 300–600s
  self-poll floor. The refresh itself is one list call (~0.5 RPM)
  regardless of burst size, so tightening it further is cheap.
- *Dropped jobs are spotted immediately.* The strongest property: the
  cache refresher IS the reconciliation sweep, running continuously.
  Ledger-vs-remote-list diffing catches both directions — a recorded
  job absent from the remote (waiter fails fast instead of burning
  the 25h timeout) and a remote job absent from the ledger (the
  orphan case D88 deferred to a sweep; now free). Caveat: "absent"
  needs a distinguishing rule before declaring a job dropped —
  guard against (i) eventual-consistency lag right after submit,
  (ii) list windowing/pagination misses. Naive absence-means-dropped
  will false-fail freshly submitted jobs; require e.g. "absent AND
  older than one full refresh cycle AND the list fetch completed."
- Side effect to fold into the eventual decision amendment: this
  upgrades `batch_jobs` from D80's audit-only ledger to the live
  status store — deliberate, and worth recording as a D80 amendment
  when the design is adopted.
