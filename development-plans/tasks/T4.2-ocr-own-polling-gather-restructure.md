## Problem

ocr's gather and store workflows are both ABANDON-children of a
fire-and-forget parent, so completion travels by signal and a failed store
child hangs the gather for 26h (verified). With forge's poller and the
signal SPI deleted in [T4.1](T4.1-forge-timer-loop-transport.md), ocr must
poll its own Mistral batches via the platform's `MistralOcr`; restructuring
the gather to parent-awaited children removes the last cross-workflow
signal platform-wide.

## Scope

ocr polls its own Mistral batches via `MistralOcr` timer-loop (same
pattern as T4.1); delete its `BATCH_RESULT_SIGNAL` handling and the SPI
wire models from contracts; **restructure gather to parent-awaited
children** (today both gather and store are ABANDON-children of a
fire-and-forget parent, so completion travels by signal and a failed store
child hangs the gather for 26h — verified); typed activity inputs (the
seven `input_json: str` activities → pydantic models through the installed
converter); `OcrJobEntry.status` enum;
`_derive_status(OcrProcessingStatus, BatchJobStatus|None)` + docstring
fixes.

**2026-07-17 — PARKED PROPOSAL (owner): batch-tracker workflow for
Mistral polling.** Documented for a full discussion later; **T4.1/T4.2
proceed as specced** — the owner's direction is "usable, valid state
first; optimize later." This note exists so the discussion starts from
the full picture.

*New operational data points (owner-provided, 2026-07-17):*

- OCR submission is extremely peaky: most of the time zero documents
  are in process, but a batch of **1,000 documents is ordinary**.
  1,000 in-process documents are no issue for Mistral; 1,000 of our
  poll requests may well hit a rate limit.
- Processing time is highly variable and uncorrelated with document
  size/content: model it as 1–1440 minutes with the mode around 30
  until better data exists.

*Why this matters:* D88's polling arithmetic was calibrated on forge's
Anthropic waiters (~30 concurrent worst case). If a 1,000-document
burst means 1,000 concurrent waiters each self-polling at the 300–600s
floor, that is 100–200 RPM of status calls against Mistral's limits —
a different regime. **Open question to resolve first:** the current
shape appears to be one batch job per document (`OcrSubmitWorkflow`
chunks a *single* file into one Mistral batch), so a 1,000-doc burst =
1,000 waiters — confirm this, and gather Mistral's actual per-tier
rate-limit numbers, before sizing anything.

*The proposal (as stated by the owner):* an event-driven **batch
tracker**. Each batch request carries a state machine that accepts
server-status messages (submit-error / acknowledged-running / finished
/ errored) and, once terminal, ignores everything — so message
ordering and replay are irrelevant by construction. Flow: (1) on
successful submit, the job registers "my message address + my batch
id" with the tracker (stored in a DB column); (2) while ≥1 batch is
active, the tracker polls the provider's **list** endpoint every ~2
minutes; (3) for each known batch (submitted within 24h) it sends the
registered address the most recent status; (4) receivers transition
their state machine; late/out-of-order messages after a terminal
state are dropped.

*Assessment recorded for the discussion (Claude, 2026-07-17):*

- **Genuinely different from the deleted D77/D78 poller** in two ways
  that matter: (a) it delivers status *hints*, not result payloads —
  if waiters fetch their own results keyed by their own batch_id on
  "done", the C1 wrong-result corruption becomes structurally
  impossible (a misrouted hint at worst triggers a harmless early
  self-fetch); (b) terminal-state absorption at the receiver makes
  duplicates and reordering harmless by design. Neither property held
  in the deleted poller.
- **What it re-introduces:** C2-shaped liveness coupling — a dead or
  stalled tracker strands every waiter. Mitigable: each waiter keeps a
  slow self-poll backstop (no update within N minutes → one direct
  status call), so the system degrades to D88 instead of failing.
- **Temporal mechanics to work out:** status-every-cycle to every
  waiter is history-expensive on both sides (up to 1,000 external
  signals per 2-minute cycle from the tracker; ~30 no-op signals/hour
  accumulating in each long-running waiter). Change-only delivery is
  the obvious refinement; tracker continue-as-new cadence needs
  design either way.
- **Variant to compare — shared status *cache*, not shared delivery:**
  the tracker refreshes the `batch_jobs` ledger from the provider's
  list endpoint (~0.5 RPM regardless of burst size); waiters keep the
  T4.1/T4.2 timer loop *unchanged*, but their `batch_status` activity
  reads the local ledger instead of Mistral, falling through to a
  direct provider call past a staleness threshold. No signals, no
  registration, no correlation anywhere; C1 impossible, C2
  self-healing; provider load identical to the tracker proposal. This
  may capture the entire benefit with a much smaller delta from the
  landed design.
- **Cheapest in-D88 mitigations** if the burst math is confirmed but
  new machinery is deferred: per-waiter jitter, and adaptive backoff
  shaped to the 1–1440min/mode≈30 distribution (poll fast early,
  back off hard after the first hour).
