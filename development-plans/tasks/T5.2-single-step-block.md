# T5.2 — Single step block

**Status:** NOT STARTED
**Phase:** 5 — Workflow consolidation (forge)
**Repos:** forge
**Depends on:** [T5.1](T5.1-pure-step-logic.md)
**Last updated:** 2026-07-08

## Problem

The step pipeline (assemble context, call LLM, write, validate, commit) is
duplicated three times in `workflows.py` — once each for single-step,
planned-step, and sub-task execution. The copies have already diverged in
behavior (the T1.5 nested fan-out bug is divergence bred by exactly this
kind of duplication), and every pipeline change must be made three times.

## Background and Detailed Explanation

T5.2 collapses three hand-maintained copies of the same pipeline into
one, and — because the consolidated block now owns the worktree it
runs in — fixes the resource leaks and non-idempotent git seams that
turn an ordinary transient failure into a permanently stuck task.

**The problem.** Every forge step runs the same five moves: assemble
the context, call the LLM, write the result, validate it, commit.
That sequence is written out three separate times in `workflows.py` —
once for a single-step task, once for a step inside a plan, once for a
sub-task inside a fan-out. Three copies mean every pipeline change has
to be made three times, and they have already drifted: the T1.5
nested-fan-out bug (config flags silently dropped on one path but not
the others) is exactly the kind of divergence duplication breeds.
Three legal states of behavior are today spread across three code
paths where nothing forces them to stay in sync.

**The fix.** One function, `run_step_attempts(spec, settings)` in
`blocks/step.py`. A `StepSpec` carries a `mode` — one of
`single_step`, `planned_step`, `sub_task` — and a single pure table
maps that mode to the three things that actually differ between the
copies: which assemble activity to call, whether the worktree is
recreated or reset, and whether success commits at task level, step
level, or not at all. That is three legal combinations expressed as
three table rows, not twenty-seven implicit ones. The retry loop
lives here too, rebuilding the assemble input with the prior attempt's
errors (`prior_errors` via `model_copy`), and exploration runs as a
per-attempt hook *inside* the loop because it needs that attempt's own
worktree — an ordering the acceptance criteria pin with a test.

**The buried gem (the 2026-07-08 amendment).** Once the step block
owns the worktree's whole lifetime, it also has to own the cleanup
today's code skips. `workflows.py` contains *zero* try/finally: if a
step raises partway through, its git worktree and its
`forge/<task_id>` branch are left behind. That is not a cosmetic leak
— `create_worktree` always passes `-b`, so the *next* run of the same
task ID collides on the leftover branch and fails permanently. A
one-time transient (a timeout, a batch error) thus converts into a
task that can never run again until someone cleans up by hand. T5.2
wraps the worktree in try/finally so every exception path removes both
the worktree and its branch, and makes the git seams idempotent under
Temporal's activity retry: `commit_changes` must not raise "Nothing to
commit" when a retry follows a commit that actually landed, and
`create_worktree` must tolerate a leftover branch from a crashed prior
run. Consolidating the pipeline without fixing these would faithfully
preserve all three defects in the single surviving copy.

**How you'll know it's done:** one pipeline, exercised per mode
through the test harness; a mid-step exception leaves no worktree and
no branch behind; and a commit-then-retry, or a rerun after a crashed
prior run, completes instead of colliding.

## Scope

`blocks/step.py` — `run_step_attempts(spec, settings)`:

- StepSpec carries `mode: Literal["single_step","planned_step","sub_task"]`
  mapped to the (assemble activity, worktree recreate-vs-reset, commit
  task/step/never) triple by one pure table (3 legal states, not 27).
- Attempt loop rebuilds assemble input with `prior_errors` via
  `model_copy`.
- **Exploration runs as a per-attempt hook inside the loop** (it needs the
  per-attempt worktree — ordering pinned by a test).

### Amendments (2026-07-08)

The step block owns the worktree lifetime, so it also owns cleanup and git
idempotency:

- Wrap the worktree lifetime in try/finally: every exception path must
  remove the worktree *and* its `forge/<task_id>` branch. Today
  `workflows.py` contains zero try/finally; a leaked branch makes the next
  run of the same task ID fail permanently, because `create_worktree`
  always passes `-b` and `remove_worktree`'s branch delete is best-effort
  (`git.py:184`, `:210-218`).
- Make the git seams idempotent under activity retry: `commit_changes`
  raises non-retryable `CommitError("Nothing to commit")` when a retry
  follows a commit that actually landed (`git.py:255-274`); a retried
  commit must succeed. `create_worktree` must tolerate a leftover branch
  from a crashed prior run.
