# T5.2 — Single step block

**Status:** DONE
**Phase:** 5 — Workflow consolidation (forge)
**Repos:** forge
**Depends on:** [T5.1](T5.1-pure-step-logic.md)
**Last updated:** 2026-07-25

## Problem

The step pipeline (assemble context, call LLM, write, validate, commit) is
duplicated three times in `workflows.py` — once each for single-step,
planned-step, and sub-task execution. The copies have already diverged in
behavior (the T1.5 nested fan-out bug is divergence bred by exactly this
kind of duplication), and every pipeline change must be made three times.

## Background and Detailed Explanation

T5.2 collapsed three hand-maintained copies of the same pipeline into
one, and — because the consolidated block owns the worktrees it runs
in — fixed the resource leaks and non-idempotent git seams that turned
an ordinary transient failure into a permanently stuck task.

**The problem.** Every forge step runs the same five moves: assemble
the context, call the LLM, write the result, validate it, commit.
That sequence was written out three separate times in `workflows.py` —
once for a single-step task, once for a step inside a plan, once for a
sub-task inside a fan-out. Three copies meant every pipeline change
had to be made three times, and they had already drifted: the T1.5
nested-fan-out bug (config flags silently dropped on one path but not
the others) is exactly the kind of divergence duplication breeds.
Three legal states of behavior were spread across three code paths
where nothing forced them to stay in sync.

**The fix, as shipped.** One function,
`run_step_attempts(spec, host)` in `blocks/step.py` (the host is the
workflow instance's persisting LLM dispatch; exploration arrives as an
optional per-attempt hook). A `StepSpec` carries a `mode` — one of
`single_step`, `planned_step`, `sub_task` — and the pure
`MODE_POLICIES` table maps it to the three things that actually
differed between the copies: which assemble activity to call, who owns
the worktree (fresh-keep / borrowed / fresh-dispose — richer than the
planned "recreate vs reset", because single-step keeps its last
worktree for inspection while sub-tasks dispose theirs even on
success), and what an attempt commits (task-level on success *and*
terminal failure, step-scoped on success only, or never). Three legal
combinations expressed as three table rows, not twenty-seven implicit
ones — with `StepSpec.__post_init__` structurally rejecting a
mode/worktree-handle mismatch. The retry loop lives in the block,
rebuilding the assemble input with the prior attempt's errors
(`prior_errors` via `model_copy`), and exploration runs as a
per-attempt hook *inside* the loop because it needs that attempt's own
worktree — an ordering pinned by a test that asserts the full call
sequence across a retry.

**The buried gem (the 2026-07-08 amendment).** Owning the worktree
means owning the cleanup the old code skipped. `workflows.py`
contained *zero* try/finally: if a step raised partway through, its
git worktree and its `forge/<task_id>` branch were left behind — and
because `create_worktree` passed `-b`, the *next* run of the same task
ID collided on the leftover branch and failed permanently. A one-time
transient thus converted into a task that could never run again
without hand cleanup. As shipped, cleanup follows ownership: the block
wraps the attempt loop for the two fresh modes, and `_run_planned`
carries the same wrap for the borrowed worktree it creates — every
exception path removes both the worktree and its branch, except the
batch-wait shapes, which each `run()` already cleans under its T1.6b
handler (cleaning twice would also have invalidated the committed
batch-ceiling replay history). The git seams became idempotent under
Temporal's activity retry: `commit_changes` returns HEAD's SHA when a
retry follows a commit that actually landed (message-keyed),
`create_worktree` recreates over a crashed run's leftovers (prune,
force-remove of a stale registration, `worktree add -B`), and
`remove_worktree` is a no-op once the worktree is gone. Consolidating
the pipeline without these would have faithfully preserved all three
defects in the single surviving copy.

**How it was proven done:** one pipeline, exercised per mode through
the workflow-test harness; the committed replay histories passed
**unregenerated** (7/7), demonstrating each mode's activity sequence
is unchanged; mid-step-exception tests assert the worktree and branch
are removed in all three modes; and real-git tests pin that a
commit-then-retry returns the landed SHA and a rerun after a crashed
prior run recreates instead of colliding.

## Scope

`blocks/step.py` — `run_step_attempts(spec, settings)`:

- StepSpec carries `mode: Literal["single_step","planned_step","sub_task"]`
  mapped to the (assemble activity, worktree recreate-vs-reset, commit
  task/step/never) triple by one pure table (3 legal states, not 27).
- Attempt loop rebuilds assemble input with `prior_errors` via
  `model_copy`.
- **Exploration runs as a per-attempt hook inside the loop** (it needs the
  per-attempt worktree — ordering pinned by a test).

### Amendments (2026-07-08)

The step block owns the worktree lifetime, so it also owns cleanup and git
idempotency:

- Wrap the worktree lifetime in try/finally: every exception path must
  remove the worktree *and* its `forge/<task_id>` branch. Today
  `workflows.py` contains zero try/finally; a leaked branch makes the next
  run of the same task ID fail permanently, because `create_worktree`
  always passes `-b` and `remove_worktree`'s branch delete is best-effort
  (`git.py:184`, `:210-218`).
- Make the git seams idempotent under activity retry: `commit_changes`
  raises non-retryable `CommitError("Nothing to commit")` when a retry
  follows a commit that actually landed (`git.py:255-274`); a retried
  commit must succeed. `create_worktree` must tolerate a leftover branch
  from a crashed prior run.

### Design decisions (settled)

1. **Module layout** — new package `src/forge/blocks/` with `step.py`, as
   specced. Confirmed against [T5.3](T5.3-single-gather-dispatch.md), which
   adds `blocks/gather.py` to the same package. `workflow_blocks.py` stays
   where it is (any monolith reshuffle is
   [T5.4](T5.4-split-the-monolith.md)); `blocks/step.py` imports its
   dispatch helpers from it.
2. **The mode table, as reconciled.** The columns are richer than the
   06-10 sketch, but it is still exactly three rows:

   | mode | assemble activity / input model | worktree policy | commit policy |
   | --- | --- | --- | --- |
   | `single_step` | `assemble_context` / `AssembleContextInput` | fresh-keep: create per attempt; remove on retry; keep on terminal exit | success **and** terminal failure (task-level; default message) |
   | `planned_step` | `assemble_step_context` / `AssembleStepContextInput` | borrowed: reset on retry; never creates or removes | success only (step-scoped message) |
   | `sub_task` | `assemble_sub_task_context` / `AssembleSubTaskContextInput` | fresh-dispose: create per attempt; removed at end of every attempt, success included (D16) | never |

   Divergences the original spec did not name, preserved deliberately:
   single_step commits on FAILURE_TERMINAL too (`status="failure"` — the
   autopsy commit); sub_task removes its worktree even on SUCCESS; the
   original "recreate vs reset" column is really a three-value ownership
   policy (fresh-keep / borrowed / fresh-dispose).
3. **StepSpec plus a small host protocol.** `StepSpec` (frozen, lives
   only inside workflow code, never serialized): `mode`, the git/validate
   task id (task_id or compound id), `repo_root`, `base_branch`, the
   prebuilt attempt-1 assemble input, `max_attempts`, `model_name`
   (`""` = don't stamp — this normalizes sub_task's conditional stamping
   without changing behavior), the validation config, the commit-message
   override (planned mode), exploration rounds. The block also needs the
   workflow instance's persisting LLM dispatch: a host protocol with
   `call_generation` (both workflow classes already expose identical
   methods) and an optional exploration hook.
4. **Neutral outcome; mode-specific results stay with callers.**
   `run_step_attempts` returns a `StepAttemptOutcome` (signal,
   output_files, validation_results, llm_result, context_stats, worktree
   path/branch, commit_sha). Callers build TaskResult / StepResult /
   SubTaskResult from it — success constructions inline, terminal results
   via the T5.1 `step_logic` builders. No result-model change, so no
   persisted-shape drift.
5. **Attempt loop** rebuilds the assemble input each attempt with
   `model_copy(update={"prior_errors": ..., "attempt": ...,
   "worktree_path": ...})` — the three input models share those field
   names (verified). The unreachable post-loop `RuntimeError` survives
   once.
6. **Exploration is a per-attempt hook** called between assemble and
   model stamping with that attempt's worktree path. single_step passes a
   closure over `_run_exploration_loop` +
   `_format_exploration_context`; planned_step and sub_task pass none.
   Planner-time exploration in `_plan_task` is untouched.
7. **Exception cleanup follows worktree ownership.** Fresh modes
   (single_step, sub_task): the block wraps its attempt loop; on
   `Exception`, best-effort removal of the worktree **and** its branch,
   then re-raise. Borrowed mode: `_run_planned` gains the same wrap
   around planner + steps — it owns that worktree, the block does not.
   `CancelledError` is deliberately excluded (post-cancellation activity
   scheduling is its own Temporal problem; the status-quo leak on cancel
   is recorded as a limitation, with a janitor sweep as the eventual fix,
   not shielded cleanup here). The run()-level BATCH_WAIT catch keeps its
   cleanup — double removal is harmless once remove is idempotent.
8. **Git seam idempotency** (`git.py`):
   - `create_worktree` tolerates a crashed prior run: `git worktree
     prune`, force-remove a stale registration of the same path, then
     `worktree add -B` (branch reset matches "worktrees are disposable";
     two live runs of one task id are already excluded by Temporal
     workflow-id uniqueness).
   - `commit_changes` with nothing staged compares HEAD's commit message
     to the intended message: match → the commit landed on a prior
     attempt, return HEAD's SHA; no match → genuine empty commit, still
     `CommitError`.
   - `remove_worktree` becomes a no-op when the worktree is already gone
     (prune + best-effort branch delete). Not named by the amendment but
     under its umbrella: today's raise-on-nonexistent would fail a
     retried remove and breaks both cleanup paths' reliability.
9. **Replay discipline.** Happy-path activity sequences are preserved
   per mode exactly, so the committed histories should replay
   **unregenerated** — run the Replayer on them as the
   behavior-preservation proof. Regenerate only if a deliberate sequence
   change creeps in, then re-verify.
