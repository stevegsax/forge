## Problem

pbook's entry lifecycle is two booleans plus a CLI hard-delete — illegal
states are constructible and the audit trail is destroyed on delete.
Cosine-similarity thresholds stand in for idempotency, so retries after
embedding drift duplicate entries. Vectors are full-precision with the
dimension hardcoded in three places, there is no lexical search column,
and no feedback/retrieval event tables exist. One destructive migration
fixes the schema; because it is destructive, a JSON dump must come first
and the judge sweep must not apply demotions until T6.2's gates pass.

## Background and Detailed Explanation

T6.3 replaces pbook's improvised entry bookkeeping with a real schema —
a state machine, a deterministic identity key, and search
infrastructure — in a single irreversible migration.

**The problem.** An entry's lifecycle is currently two boolean columns
plus a CLI hard-delete, and that shape is broken four ways. The two
booleans make illegal states *constructible* (an entry can be flagged
in contradictory ways no valid lifecycle allows), and the hard-delete
destroys the audit trail — a deleted entry leaves no trace of why.
Idempotency is faked with cosine-similarity thresholds, so when an
embedding model drifts a retry no longer looks "similar enough" to the
original and inserts a duplicate. And the store lacks the machinery
real retrieval needs: vectors are stored at full precision with their
dimension hardcoded in three separate places, there is no
lexical-search column, and there are no tables to record retrieval or
feedback events.

**The fix.** One destructive Alembic migration replaces all of it: a
CHECK-constrained `status` enum
(`probation`/`active`/`stale`/`rejected`/`superseded`) with reason and
provenance columns in place of the booleans; an `origin_hash` UNIQUE
column (a sha256 of stable inputs) that makes idempotency
*deterministic* instead of similarity-guessed; a generated `search_tsv`
tsvector with a GIN index for lexical search; embeddings converted to
`halfvec(1536)` with the HNSW index rebuilt; new `pbk_retrieval_events`
and `pbk_feedback_events` tables; and a `knowledge.approved_entries`
view (the exact surface forge later reads through — T6.7/D92). The
migration preflights its pgvector version and refuses to run if the
database is too old to support halfvec and iterative scans.

**Why the ordering is load-bearing.** The migration is destructive and
cannot be un-run, so three things happen in a fixed sequence: a
one-time JSON dump of the current entries is taken *first*; the judge
sweep over the backfilled entries runs *report-only*; and demotions are
applied only after T6.2's calibration gates pass. An uncalibrated judge
must never be the thing that rewrites the corpus.

**The operational gotchas (2026-07-08 amendments).** A backup you have
never restored is untested by definition, so the JSON dump must be
restored into a scratch schema and verified — row counts plus spot
checks — before the destructive step runs. `CREATE INDEX CONCURRENTLY`
cannot execute inside Alembic's transaction, so the halfvec conversion
and HNSW rebuild need an explicit out-of-transaction strategy and a
stated downtime window. These safeguards were written when the store
was hosted Supabase (hence the transaction-pooler
`prepare_threshold=None` verification); T0.9/D102 has since rehomed the
store to local Postgres, so the Supabase-specific details may no longer
apply, but the discipline they encode — concurrent index builds outside
the transaction, a rehearsed restore — is store-agnostic and stands.

## Scope

Ordering is load-bearing: **pre-migration JSON dump FIRST**; the judge
sweep runs **REPORT-ONLY**; demotions are applied only after T6.2's gates
pass.

- **One-time JSON dump of pbk_entries first.**
- Single destructive Alembic migration:
  - `status ∈ {probation, active, stale, rejected, superseded}` +
    `status_reason`/`status_changed_at`/`rejected_by`/
    `superseded_by_id`/`last_validated_at` (CHECK-constrained; backfill:
    rejected wins → rejected; needs_review → probation; else active).
  - `origin_hash` UNIQUE (sha256(session_id + experience_hash +
    normalized_title), NULL for manual/legacy).
  - `search_tsv` generated tsvector + GIN.
  - Embeddings → `halfvec(1536)` + HNSW rebuilt (`halfvec_cosine_ops`) +
    `embedding_model`/`embedding_dim` columns.
  - `pbk_retrieval_events` + `pbk_feedback_events` (UNIQUE
    entry/session/polarity).
  - `knowledge.approved_entries` view (**non-vector columns +
    search_tsv**).
  - Migration preflights pgvector ≥0.7 (halfvec) and ≥0.8 (iterative
    scans) and refuses otherwise.
- Then the **report-only** judge sweep of backfilled actives; apply
  demotions (→ probation) only after T6.2 gates pass.
- First migration test.

### Amendments (2026-07-08)

Operational safeguards the original scope lacked:

- **Index-build strategy.** `CREATE INDEX CONCURRENTLY` cannot run inside
  Alembic's transaction — define how the halfvec conversion and HNSW
  rebuild execute against hosted Supabase (autocommit block or
  post-migration step) and the expected downtime window.
- **Tested restore path.** The pre-migration JSON dump must be restored
  into a scratch schema and verified (row counts + spot checks) *before*
  the destructive migration runs — an unrestored backup is untested by
  definition.
- **Pooler behavior.** Verify `prepare_threshold=None` on the engine the
  migration itself uses when connecting via the 6543 transaction pooler
  (adjudication #10 lives in DECISIONS, not here, and the podman fixture
  cannot catch pooler behavior).
