## What to know before touching anything

1. **T5.5 is committed as `66b5ec2`, with this sweep as its child
   commit.** The change-set: `tests/test_workflows.py` deleted;
   `tests/support/` and `tests/workflows/` plus seven new replay
   histories added; `pyproject.toml`, `uv.lock`,
   `tests/replay/regenerate.py`, three block-test docstrings, and the
   T5.5/TASKS/CHANGELOG records modified. Deployment is a separate,
   still-open owner decision: production runs `7002435`, so neither
   T5.4 nor T5.5 is live — `make prod-deploy REF=<ref>` (D103) when
   wanted.
2. **A discovery from T5.5 that changes how you read the old suite:**
   *every* legacy workflow scenario actually ran on the **batch** lane.
   `sync_mode` defaults to `False` and the old activity lists all
   registered the batch trio, so the sync `call_llm` mocks in those
   sections were dead code and the `"call_llm"` entries in their call
   logs were written by the *parse* handler. Migration therefore changed
   no test's lane; three assertion families were renamed to the
   batch-lane entry they actually observe (`"call_llm"` →
   `"parse_llm_response:LLMResponse"`; `"call_conflict_resolution"` →
   `"parse_llm_response:ConflictResolutionResponse"`;
   `"call_sanity_check"` → `"parse_llm_response:SanityCheckResponse"`),
   each with an inline comment. That is the only assertion-text change
   class in the whole migration. New tests use `sync_mode=True` (guide
   D6 applies to new tests only).
3. **Writing new workflow tests now means writing against the
   harness.** Construct a `ScenarioState` inside the test, hand
   `build_activities(state)` to the per-test `Worker`, and script
   outcomes **keyed by identity** — never by arrival order. Two key
   spaces, documented in the harness module docstring's table:
   transitions/validations are keyed by the *validate identity*
   (`ValidateOutputInput.task_id` — the task id, or the compound
   `parent.sub.child` id), and LLM responses by the *call identity* read
   off the assembled context. Scripts handed in are read-only
   (`MappingProxyType` tables; consumption uses an internal cursor —
   there is no `pop(`, no `.clear()`, no handler-pointer reassignment
   anywhere in the new files). Batch-lane identity is recovered from
   `request_id`, exactly as the real transport selects a waiter's line.
4. **The crash-recovery test needs `max_cached_workflows=0` on both
   workers, and the reason generalizes.** With sticky execution on,
   Temporal routes a run's later workflow tasks back to the dead
   worker's private sticky queue, which drains only after its
   schedule-to-start timeout — a delay the time-skipping server does
   **not** fast-forward, so the test sits in real time. Disabling the
   cache puts every workflow task on the shared queue. Any future
   worker-restart scenario will hit the same wall.
5. **T5.6's REVISE hazard is worse-behaved than its spec says.** The
   splice reconstructs `Plan(steps=…)` and `Plan` now carries
   `max_length=25` (T4.1), so an over-cap splice raises a pydantic
   `ValidationError` **inside workflow code** — an infinitely retrying
   workflow task (a hung workflow), not the spec's "unbounded history."
   The revision cap must therefore *catch* the over-cap case and produce
   a clean terminal result, not merely count. The spec's line references
   are also stale; the task file's 2026-07-27 amendment carries the
   current ones (`models.py:299-307`;
   `src/forge/workflows/task.py:435-443`; the batch-lane gate is
   `Plan.model_validate_json` in `blocks/dispatch.py`).
