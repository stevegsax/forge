## What landed since the last handoff

- **T5.6 — plan preflight gate (`36e1609`).** Planner output is checked
  for structural defects before any step runs. The nine eval checks
  moved into the new pure `src/forge/plan_checks.py` as *finders*
  (offending items out, empty means clean) and now **recurse into nested
  `sub_tasks`** — ids compared among siblings (identity is the compound
  `<parent>.sub.<child>` path), target overlap compared on each child's
  *effective* set (its own targets plus every descendant's, because a
  grandchild's file surfaces in its parent's merged output).
  `eval/deterministic.py` keeps its public API, result models, and
  wording; each body is now one call to a finder. The live gate is the
  five structural finders (duplicate step ids, duplicate sub-task ids,
  overlapping sub-task targets, absolute/`..` paths, output-less leaves)
  run from `blocks/dispatch.py::dispatch_planner` — the single T5.3 seam
  every planner call on both lanes passes through, so the gate and its
  retry arm exist in exactly one place and emit **zero commands on a
  clean plan**.
- **The retry arm as ruled.** A rejected plan is re-planned with the
  specific violations appended to the planner's prompt (pure string
  work — one more planner call, no extra activity),
  `MAX_PLANNER_ATTEMPTS=3` total, no backoff, thinking escalated to
  `effort="max"` on the last attempt; after the third, a clean halt with
  the new `failure_kind="plan_preflight"`. A raise was deliberately not
  used: `run()` catches `ApplicationError` as a batch-wait failure and
  would mislabel the halt, so `dispatch_planner` returns
  `PlanCallResult | PlanPreflightHalt`.
- **The REVISE splice now catches rather than counts.** With
  `Plan.steps` capped at 25 since T4.1, reconstructing an over-cap plan
  raises a pydantic `ValidationError` *inside workflow code* — a
  workflow task Temporal retries forever, i.e. a hung run, not a failed
  one. The pure `splice_revision` rejects before construction, also
  enforcing `MAX_PLAN_REVISIONS=5` and re-running the gate on the
  spliced plan (`failure_kind="plan_revision"`). `FailureKind` is now
  twelve values.

## What to know before touching anything

1. **The live gate is a subset, and T5.7 exists because of it.**
   `check_context_files_plausible` and `check_no_forward_references`
   take a `known_repo_files` set; obtaining it inside a workflow means
   scheduling an activity, which changes the command sequence of every
   planned run and invalidates the committed replay histories — the one
   thing T5.6's design avoids by staying pure inline logic. A
   repo-set-free forward-reference rule was considered and rejected:
   "step 1 reads `config.py`, step 3 rewrites `config.py`" is an
   everyday plan and is indistinguishable from a genuine forward
   reference without the file set, so the rule would false-positive
   constantly and halt real runs. T5.7 moves the check to the moment the
   ambiguity disappears (step context assembly, standing in the
   worktree), which is why it is a separate task and not a fix.
2. **Any fixture that reaches conflict resolution by *declaring* the
   same file twice is now rejected before it runs.**
   `check_sub_task_targets_non_overlapping` is the headline gate rule,
   and three test fixtures used exactly that shape. They were rewritten
   to declare distinct targets while both children still *write* the
   shared file — which is what a conflict looks like in production now,
   because conflict detection has always classified what children
   produced (`classify_file_conflicts` over `SubTaskResult.output_files`),
   never what the plan declared. Sites:
   `tests/support/block_mocks.py::five_arm_activities`,
   `tests/replay/regenerate.py::_scenario_conflict_resolution_sync`. Write
   new conflict scenarios that way; the declared-overlap shape no longer
   reaches the arm.
3. **One replay history was regenerated, and the diagnosis is the
   precedent to follow.** `conflict_resolution_sync` failed as
   `NondeterminismError: Activity machine does not handle this event:
   HistoryEvent(id: 29, StartChildWorkflowExecutionInitiated)` — the
   recorded history's planner result carries the old overlapping-target
   plan, so replaying it through the new code rejects that plan at
   preflight and schedules a *second planner call* where the history has
   a child-workflow start. No fixture edit can save a history whose
   recorded payload is the rejected artifact, so that one was
   regenerated (`uv run python -m tests.replay.regenerate
   conflict_resolution_sync`) and only that one. Diagnose before
   regenerating; the other twelve replaying untouched is the proof the
   gate emits no commands on a clean plan.
4. **The empty-response validator makes one old payload shape
   undeserializable, and that is a deploy-timing hazard, not a test
   hazard.** `LLMResponse` with `files=[]` and `edits=[]` no longer
   validates. No committed history carries one, and the shape was a
   silent no-op success, so nothing is lost — but a *recorded* payload
   of that shape in an in-flight workflow's history now fails to
   deserialize on replay. Mechanism: a production worker upgraded to
   `36e1609` while such a run is in flight would fail that run's
   workflow task. Act-now: nothing. Act-later, at deploy: check for
   in-flight planned runs (`temporal workflow list` on the `default`
   namespace) before `make prod-deploy REF=<ref>`; an idle queue makes
   this a non-event. T5.7's scope explicitly forbids repeating the
   pattern — its new activity-output field must be optional with an
   empty default so previously recorded payloads still deserialize.
5. **`derive_execution_timeout` learned about the retries.** Its
   planner term went from `max_exploration_rounds + 1` to
   `max_exploration_rounds + MAX_PLANNER_ATTEMPTS`, because on the batch
   lane each planner attempt is a full 25h-ceilinged wait. Missing it
   would have left a batch-lane planned run able to exhaust its own
   execution timeout inside the retry arm. The function is pure and
   CLI-side, so it is not replay-affecting — but any future change to
   attempt counts has to revisit it.
6. **Production is on `e0e3214`; T5.6 is not deployed.** The pinned prod
   checkout (`~/repos-sax/forge-prod`, D103) is two commits behind main
   (`36e1609`, `d7a2d1f`), and all four prod pollers report
   `prod-<role>@e0e3214` with no `-dirty`. T5.4 and T5.5 *are* live —
   they were deployed after the last handoff was written, which is why
   that handoff's "production runs `7002435`" no longer holds.
   Deploying T5.6 is a separate owner decision (`make prod-deploy
   REF=<ref>`), subject to item 4's timing check.
7. **Open adjudications: A1, A3–A8** (plan review §2–§3; A2 was ruled —

8. **Standing directives**, reproduced from [SDLC.md](SDLC.md)
   § Standing directives as it reads today (13 items, four groups; that

   *Authority and scope:* commits and merges are the owner's on explicit

   timeout/retry presets come from `forge/presets.py` only, because the

   order, with no module-level mutable containers (the pytest-xdist

   writing or reviewing Python, and require the same of any spawned
   code-writer. *Working style:* mechanism-level explanations — the
   underlying cause, act-now versus act-later versus no-action, concrete
   command sequences, and never a safety caveat compressed into a bare
   clause; challenge weak arguments and spot missing data, do not
   praise. *Tool hazards:* `rg -n`, never `rg -rn` (`-rn` parses as
   `--replace n` and fabricates output); never start a wrapped `.md`
   prose line with `+`, because the formatter hook re-parses it as a
   list marker and rewrites the list; `gsed`, not `sed`, when
   stream-editing is unavoidable — prefer Edit.

- **Two exemptions keep false positives out** and are acceptance
  criteria, not optimizations: a step's own *target* files are never
  flagged (creating them is the step's job — only the read set is
  checked), and user-supplied task-level `context_files` keep today's
  skip-with-warning behavior, because a missing user input is an input
  problem and must not burn a plan revision.
- **The replay constraint is the design constraint.** The check
  piggybacks on an activity that is already scheduled and the
  classification is pure workflow logic on its result, so all committed
  replay histories must pass **unregenerated** — new behavior may appear
  only in runs whose plans are defective, which no committed history
  contains. If a design move would add an activity to the happy path,
  it is the wrong move.
