# Workflows and Service Layer

*Describes the target architecture adopted in the June 2026 review; implementation is phased —
see [REVIEW-2026-06.md](REVIEW-2026-06.md).*

Exactly two Temporal workflows exist — `IngestWorkflow` and `CurationWorkflow`, both on
`pbook-task-queue` — because only durable multi-step jobs justify Temporal
([TEMPORAL_PATTERNS.md](TEMPORAL_PATTERNS.md)). Everything else (CRUD, retrieval, export,
feedback) is synchronous service-layer code, documented here as well. There are no cross-queue
workflows: ingestion is pbook-owned end-to-end, and forge neither calls pbook nor is called by
it (see [INTEGRATION.md](INTEGRATION.md)).

Worker conventions, per the house rules: activities are bound methods on frozen activity
classes built at the worker composition root; retry presets come from `sax_platform.temporal`
(`LLM_RETRY`, `DB_RETRY`), with auth/config errors classified non-retryable via
`classify_llm_error`; determinism is gated by replay tests with committed histories under
`tests/replay/`, regenerated by one command.

## Service layer

The CLI and library consumers call synchronous functions in `pbook/service.py`. No worker, no
Temporal connection. Dependencies arrive in a frozen `AppContext(settings, engine,
embedder | None)` built once at `__main__` entry — the composition root. There are no
module-level singletons; env vars are read only inside the `Settings` class:

| Env var | Requirement |
| --- | --- |
| `PBOOK_DATABASE_URL` | Required; missing raises `ConfigError`, which the CLI maps to the `db_disabled` JSON envelope |
| `OPENAI_API_KEY` | Optional for CLI search (absent means degraded lexical search); required for the worker |
| `ANTHROPIC_API_KEY` | Worker only |

Service functions:

| Group | Functions |
| --- | --- |
| Retrieval / read | `search`, `list_entries`, `get_entry`, `review_queue`, `check_duplicate` |
| Write / lifecycle | `add_entry`, `update_entry`, `approve_entry`, `reject_entry`, `invalidate_entry`, `purge_entry` |
| Feedback | `record_feedback` |
| Provenance / metadata | `list_sources`, `list_tags`, `list_sessions`, `session_text` |
| Export | `export_entries` |

Pure logic lives in core modules the service layer (and tests) call directly: `ranking.py`
(`score_candidates` plus a frozen `ScoringWeights`), `lifecycle.py` (`EntryStatus`,
`transition()`, `compute_staleness()` plus a frozen `StalenessConfig`), `tags.py`
(`normalize_tags`), and the packing/prompt builders. The state machine and staleness triggers
are specified in [DATA_MODEL.md](DATA_MODEL.md); CLI command mapping in [CLI.md](CLI.md).

### Retrieval pipeline (`service.search`)

The only ranking implementation is the pure `ranking.score_candidates`.

1. **Embed the query.** If there is query text and `ctx.embedder` is present, one embedding
   call (`text-embedding-3-small`).
2. **Candidate generation.** Union of three top-50 SQL rank lists, all filtered to
   `status IN ('probation', 'active')` in SQL (`hnsw.iterative_scan` enabled for the filtered
   ANN query):
   - lexical — `search_tsv` matched with `websearch_to_tsquery`, ranked by `ts_rank_cd`
   - semantic — `embedding <=>` query vector (cosine distance)
   - tag — entries sharing any query tag
3. **Pure scoring.** RRF base with `k=60` over the lexical and semantic rank lists, multiplied
   by bounded factors:
   - tag overlap (capped)
   - mode alignment (table below)
   - feedback ratio — `(helpful - harmful) / retrieval_count`, applied only when
     `retrieval_count >= 3`, bounded
   - probation factor ×0.7

   Scores clamp at ≥ 0. Zero-tag-overlap entries surface via the lexical/semantic lists by
   construction — tags are a boost, never a gate.
4. **Pack.** Ranked candidates are packed within a token budget (default 5,000). Packed
   probation entries carry `"status": "probation"` so consumers see confidence.
5. **Record.** A `pbk_retrieval_events` row plus an atomic `retrieval_count` increment for
   served entries (best-effort).

Mode alignment factors:

| Mode | Entry-type boost | Tag-overlap boost |
| --- | --- | --- |
| `CREATE` | curated entries | `lang:` / `lib:` / `domain:` |
| `FIX` | pitfall entries | `project:` / `pattern:` |

Mode reweights ranking only — it never filters.

Degraded mode: without `OPENAI_API_KEY`, search runs lexical + tag only, ordered by
`ts_rank_cd(...) DESC, tag_overlap DESC`, and the JSON envelope gains
`"degraded": "no_embedding_key"`. Search never hard-fails on a missing key. Results include
similarity and status; `--active-only` excludes probation entries (replacing the old
`approved_only`).

## IngestWorkflow

Per-session ingestion with deterministic workflow id `pbook-ingest-{session_id}`. Input is a
union: `TranscriptSource(path, session_id, project)` or `InlineExperiences(experiences,
project)` (the `pbook push` path skips transcript analysis).

```text
IngestWorkflow                id: pbook-ingest-{session_id}    queue: pbook-task-queue

Input:  TranscriptSource(path, session_id, project) | InlineExperiences(experiences, project)
Output: {entries_created, entries_rejected, failures}

begin_session                                                  [DB_RETRY]
  └─▶ write pbk_ingested_sessions row, status='running'

analyze_transcript            (TranscriptSource only)          [LLM_RETRY, heartbeat]
  └─▶ read session JSONL by path inside the activity
  └─▶ one synchronous structured-output LLM call → experiences

for each experience           (isolated try/except)
  ├─▶ extract_candidates      GENERATION tier (sonnet)         [LLM_RETRY]
  ├─▶ judge_candidates        CLASSIFICATION tier (haiku)      [LLM_RETRY]
  └─▶ embed_and_save_entries                                   [DB_RETRY]
        ├─ survivors      → status='probation'
        ├─ judge failures → status='rejected', rejected_by='validator'
        └─ INSERT ... ON CONFLICT (origin_hash) DO NOTHING

finish_session                                                 [DB_RETRY]
  └─▶ record counts, status='completed'

on workflow error ────▶ error handler records session status='error'
```

- **Session row ownership.** The workflow owns its `pbk_ingested_sessions` row: the first
  activity writes `running`, the workflow-level error handler writes `error`, and the
  curation sweep flips rows stuck `running` longer than 48 hours to `error` with reason
  `abandoned`. The CLI never seeds session rows.
- **Claim-check by path.** `analyze_transcript` reads the transcript JSONL by path inside the
  activity; transcripts never enter workflow history. The activity makes one synchronous
  structured-output LLM call with heartbeat.
- **Per-experience isolation.** Each experience runs in its own try/except; one failure never
  aborts the batch. The result reports per-item outcomes
  `{entries_created, entries_rejected, failures}`.
- **Extraction.** `extract_candidates` runs at the GENERATION tier (sonnet) with the strict
  quality-bar prompt. The static system prompt is a constant with `cache_control`;
  experiences travel in the user message, so prompt caching pays during multi-session
  ingestion runs.
- **Validation judge.** `judge_candidates` runs at the CLASSIFICATION tier (haiku), one call
  batching the experience's candidates, applying four binary checks: grounded-in-resolution,
  specific, non-generic, actionable. Failures are saved as `status='rejected'`,
  `rejected_by='validator'`, with the judge's reason in `status_reason` — auditable and
  minable as eval goldens.
- **Idempotent save.** `embed_and_save_entries` computes embeddings inside the save activity
  and inserts with `ON CONFLICT (origin_hash) DO NOTHING`
  (`origin_hash = sha256(session_id + experience_hash + normalized_title)`). The cosine
  thresholds — 0.85 entry-match, 0.92 source-dedup — remain only as cross-session
  match-or-attach policy, never retry protection. Survivors enter as `status='probation'`.
- **Message Batches** are deliberately not used at current volume; revisit above roughly 500
  sessions/month.

## CurationWorkflow

Runs as a weekly Temporal Schedule with id `pbook-curation-weekly`, created idempotently at
worker startup (already-exists ignored), and on demand via `pbook curate`.

```text
CurationWorkflow              schedule: pbook-curation-weekly  queue: pbook-task-queue

Output: {staled, consolidated, failures}

Step 1: staleness sweep
  └─▶ pure lifecycle.compute_staleness over entry metadata
  └─▶ marks triggered entries stale — never deletes

Step 2: consolidation         (per cluster, isolated try/except)
  ├─▶ consolidate_cluster_llm  GENERATION tier merge           [LLM_RETRY]
  ├─▶ judge_candidates         same four-check gate            [LLM_RETRY]
  └─▶ apply_consolidation      one DB transaction              [DB_RETRY]
        ├─ embed + insert survivor → status='probation', counters zeroed
        ├─ parents                 → status='superseded', superseded_by_id set
        └─ pbk_entry_sources       → reparented to survivor (never deleted)

Step 3: sweep_abandoned_sessions                               [DB_RETRY]
  └─▶ sessions 'running' > 48h → status='error', reason 'abandoned'
```

- **Staleness sweep.** Applies the pure `compute_staleness` (frozen `StalenessConfig`) over
  entry metadata: age (270 days for entries with any `lib:`/`project:` tag, 540 for pure
  `lang:`/`domain:`), harmful signal, and dead weight — see
  [DATA_MODEL.md](DATA_MODEL.md) for the trigger definitions. Stale entries are flagged for
  `pbook review --stale`, never deleted.
- **Consolidation.** Each cluster is isolated in its own try/except. The merged candidate
  passes through the same validation gate as extraction; a rejected merge is stored as
  `status='rejected'`, `rejected_by='curation'` (audit trail — the parent entries stay
  untouched and the cluster is left for the next run). `apply_consolidation` then commits
  one DB transaction that inserts the survivor as `probation` with zeroed counters (it
  re-earns trust), marks parents `superseded` with `superseded_by_id`, and reparents
  `pbk_entry_sources` rows. Curation never deletes provenance.
- **Abandoned-session sweep.** Flips ingestion sessions stuck `running` longer than 48 hours
  to `error` with reason `abandoned`.

## Quality bar

The extraction prompt instructs the LLM to extract **only** lessons that are both:

1. **Unexpected** — the default approach did not work; multiple retries were needed; an API
   behaved differently than documented; a standard pattern failed in a specific context
2. **Actionable** — there is specific, concrete advice that would help next time

Explicitly excluded: generic advice, standard rules, expected behavior, vague or
over-prescriptive guidance, entries without specific actionable content. The prompt
concludes: "It is better to extract NOTHING than to extract a misleading or overly generic
entry. Quality over quantity."

This bar is no longer prompt text alone — it is enforced twice. First, the validation judge
gates every extracted and consolidated candidate with the four binary checks; failures are
stored as validator rejections, not silently dropped. Second, three eval suites under
`tests/evals/` (run via `make evals`) pin the behavior: extraction goldens including
must-extract-zero negative cases gated at 100%, judge calibration gated at ≥ 85% agreement
with hand-graded cases, and retrieval goldens gated at recall@5 ≥ 0.8 and MRR ≥ 0.6. Model
pins move only on green paired-delta runs.

## Activity summary

| Activity | Workflow | LLM call | Database |
| --- | --- | --- | --- |
| `begin_session` | Ingest | No | Write (session row `running`) |
| `analyze_transcript` | Ingest | Yes (structured output, heartbeat) | No (reads JSONL by path) |

| `finish_session` | Ingest | No | Write |

| `apply_consolidation` | Curation | Embedding only | Write (one transaction) |
| `sweep_abandoned_sessions` | Curation | No | Write |
