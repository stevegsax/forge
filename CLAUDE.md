## Project Overview: Forge

Forge is a general-purpose LLM task orchestrator built around batch mode with document completion. It decomposes tasks into independent work units, executes them as single-step state machine transitions, and reconciles results. The architecture is task-agnostic: code generation, research, analysis, and other domains are all instances of the same universal workflow step with different prompts and context.

## Running the System (D99, D102, D103)

Deployment is **local-first on this desktop** — there is no cloud host and no remote access. Temporal self-hosts in the podman stack (`make stack-up`; frontend `127.0.0.1:7233`, UI `http://localhost:8233`, Postgres, MinIO), the forge/pbook/ocr workers run as launchd-supervised host processes out of a commit-pinned checkout (`~/repos-sax/forge-prod`, D103 — production is deployed only by `make prod-deploy REF=<ref>`, and a worker refuses to start on a dirty or unverifiable prod checkout, exit 78), and the application store of record now lives in that same local Postgres too (D102, 2026-07-22): the `forge` (forge + ocr) and `pbook` databases beside Temporal's, with S3 for blobs and a nightly `pg_dump` → S3 for offsite durability. Supabase is retired/frozen. Full detail: [docs/operations/DEPLOYMENT.md](docs/operations/DEPLOYMENT.md), [deploy/local-stack/README.md](deploy/local-stack/README.md), [deploy/launchd/README.md](deploy/launchd/README.md).

> **`FORGE_ENV` is required and has no default** (D102): no process reaches a database without declaring its environment, and a guard failure exits 78. A bare interactive shell carries no `FORGE_DB_URL` and no `FORGE_ENV`, so nothing is aimed at any database until you source a profile. Production is explicit: `set -a; source ~/.config/forge/envs/prod.env; set +a; export FORGE_ENV=prod FORGE_PROD_ACK=yes` (the `set -a` is load-bearing — a plain `source` does not export, and the guard rejects an unexported tag). Non-prod work uses `FORGE_ENV=dev` with the `dev` profile, or `--env dev` on any CLI command (either position). Production **ocr** CLI commands have a one-command wrapper: `deploy/prod-ocr <cmd>` embeds the ceremony and execs from the pinned prod checkout (client and workers on the same commit). On this machine the local stack's Postgres is on **port 5434** via the gitignored `deploy/local-stack/.env` override (the shared sax-datastores stacks now hold 5432 and 5442; forge moves onto them in T10.1).

**Staging lane:** dev is isolated from production by *server* (`:7236` vs `:7243`) and by namespace (`forge-dev` vs `forge-prod`). Both are derived from `FORGE_ENV` by `resolve_temporal_target` before every connect and returned as one frozen `TemporalTarget`, so they cannot disagree; `FORGE_TEMPORAL_NAMESPACE` is retired and `FORGE_TEMPORAL_ADDRESS` is an override that dev/prod reject unless it restates their own server. A dev process can never poll production's queues. **Deployed state lags the code** — production and the dev lane still run a pre-cutover commit on the legacy `:7233` server (`default`/`forge-dev`); the cutover is operational (create the namespaces, update `~/.config/forge/envs/`, drain, deploy) and deploying before the namespaces exist fails every worker closed at startup. Convention and migration ledger: `sax-temporal/docs/namespaces.md`. `make dev-worker [WORKER=ocr|forge|pbook]` starts a crash-safe detached tmux dev worker; a functional lane needs the ocr **and** forge workers (ocr's ledger writes are cross-queue). The lanes restart independently (2026-07-24): `make workers-restart` is production-only (launchd-label pid resolution — it cannot touch tmux workers), `make dev-worker-restart WORKER=<name>` restarts one dev worker, `make workers-status` shows both lanes. See [docs/operations/WORKERS.md](docs/operations/WORKERS.md#staging-lane-dev-namespace).

## Cross-Project Dependencies

Forge is the monorepo (D98, consolidation complete): the repo root is a uv workspace with one `uv.lock` and one venv, and every internal package is a workspace member — `apps/pbook`, `apps/ocr`, plus `libs/sax-platform` (born in Phase 3, not an absorbed repo) — so a bare checkout is self-contained. Members declare no `[tool.uv.sources]` of their own. ocr is the one member forge does **not** depend on (apps never import apps): setup is `uv sync --all-packages` and its CLI runs as `uv run --package ocr ocr <cmd>`. Version pinning inside the set is deliberately gone: the suites are the compatibility contract.

- **sax-platform** (`libs/sax-platform`, workspace member; **a dependency of forge, ocr, and pbook**) — the D89 platform library. `sax_platform.llm`: structured-outputs LLM client on both lanes — the sync `complete[T]` helper (`messages.parse`) and the batch request builder plus submit/status/fetch helpers (`output_config.format`, with stored-bytes classification into typed non-retryable failures at the fetch/parse seam) — typed refusal/truncation/mismatch outcomes, `max_retries=0`, required `max_tokens`, thinking selected via `ThinkingPolicy`, opt-in prompt caching. ## Build, Test, and Lint Commands

```bash
uv sync --all-packages           # Install dependencies (all workspace members)
uv run pytest                    # Run all tests (excludes e2e and postgres markers by default)
uv run pytest tests/test_foo.py  # Run a single test file
uv run pytest tests/test_foo.py::TestClass::test_name  # Run a single test
uv run pytest --no-cov           # Skip coverage (faster iteration)
uv run pytest -m postgres --no-cov  # Migration tests against real Postgres (testcontainers)
uv run ruff check .              # Lint
uv run ruff format .             # Format
uv run ruff check --fix .        # Auto-fix lint issues
```

Coverage is enforced at 85% by default (`--cov-fail-under=85` in pyproject.toml). When running a single test file, use `--no-cov` to avoid failing on aggregate coverage.

Workspace command discipline: the commands above, run from the root, cover forge only (`testpaths = ["tests"]` keeps the members out of the default run). Setup is `uv sync --all-packages` (a bare exact `uv sync` prunes ocr's packages, since forge doesn't depend on it; `uv run`'s inexact sync self-heals). Each member's suite runs from its own directory so its own config applies: `cd apps/pbook && uv run pytest` (85% gate; its conftest needs a running podman machine or `PBOOK_TEST_DATABASE_URL`), `cd apps/ocr && uv run pytest` (85% gate), `cd libs/sax-platform && uv run pytest` (85% gate). `make gates` runs the workspace gates — lint, mypy (all four packages), lint-imports, and the four test suites — mirroring `.github/workflows/ci.yml`, which additionally runs the `postgres` migration suite (`pytest -m postgres`) as its own job. Never run a member's tests from the root (e.g. `pytest apps/pbook/tests`): forge's addopts would apply and the member's conftest would run under the wrong config.

The test suite uses `asyncio_mode = "auto"` and a session-scoped Temporal time-skipping environment (`WorkflowEnvironment.start_time_skipping` in `conftest.py`). Two markers are excluded from default runs: `postgres` (Alembic migrations against a real Postgres via testcontainers) and `e2e`. The `e2e` marker is defined but currently empty in forge — `tests/test_e2e.py` is a default-run integration suite with mocked LLM calls (T8.2 renames it to `test_pipeline.py` and restores marker honesty).

## Architecture Principles

1. **Batch-first.** The system is designed to operate in batch mode, with orchestration handled by Temporal workflows. Any proposed change must be evaluated for batch compatibility. If a change requires synchronous, interactive, or low-latency LLM calls that are incompatible with batch mode, flag it early.
2. **Deterministic work should be deterministic.** Never ask the LLM to figure out something you can compute. Pre-calculate facts and include them in context.
3. **Context isolation is a feature.** Each task gets a tightly constrained definition of "done" and a customized context assembled fresh for each request.
4. **Planning is the hard part.** Invest the most expensive models and highest token budgets in planning. Everything downstream is bounded by plan quality.
5. **Halt when confused.** When the orchestrator encounters a situation it cannot classify, it stops and escalates to a human.
6. **The LLM call is the universal primitive.** Every task is an instance of: construct message, send, receive, serialize, transition.
7. **Follow Temporal best practices.** Before planning changes that touch Temporal workflows, activities, or worker configuration, check [Temporal Best Practices](https://docs.temporal.io/best-practices) and [docs/operations/WORKERS.md](docs/operations/WORKERS.md) to ensure the approach aligns with Temporal's guidance.
8. **Application access is through Temporal** (owner decision 2026-07-23). CLI and application reads/writes route through workflows/activities — no direct database connections outside the workers, unless strictly necessary. Infrastructure tooling is the sanctioned exception: diagnostics that must work when Temporal itself is down (`ocr tracker-status`), schema migrations (`ocr migrate`, `pbook migrate`), and backup tooling. Corollaries (both parked, tracked in TASKS.md — neither is implemented as of 2026-07-27): workflow-routed CLI commands should bound their first-step wait and fail with a clear "no worker is polling this queue/namespace" message rather than hanging (today no CLI bounds this wait); if an operation's result ever approaches Temporal's payload limits, the direction is a claim-check — the workflow writes to S3 and returns the link (the batch transport's inline-≤256KB-else-S3 pattern is the precedent) — parked until actually needed.

## Test Patterns

Workflow tests use the Temporal time-skipping test server with a session-scoped `env` fixture. Since T3.6 that fixture is the `temporal_env` fixture from `sax_platform.testing`, re-exported (`env = temporal_env`) in each app's own `conftest.py` — an explicit import, not a pytest11 plugin; request only one of `env`/`temporal_env` per session (the fixture cache is per-name). Activities are still mocked by name using `@activity.defn(name="activity_name")` and registered on a per-test `Worker` — the class conversion (T3.6) is invisible to workflows because bound methods keep their `__name__`, so the by-name workflow-mock files were untouched. Batch waits are tested with three by-name mock activities for the timer-loop transport (T4.1): `submit_batch_request` echoing the workflow-minted `request_id`, `batch_status` returning `ended` (or `in_progress` to exercise the poll loop — the time-skipping environment fast-forwards the sleeps), and `fetch_batch_result` returning an inline canned body; `parse_llm_response` stays mocked as before. Since T5.1 there is no `evaluate_transition` mock: transition evaluation is inlined (`step_logic.determine_transition`), so a test drives the signal through the `validate_output` mock's result — a passing result yields SUCCESS, a failing one yields RETRYABLE while attempts remain and TERMINAL at `max_attempts`. The full decision matrix is unit-tested directly in `tests/test_step_logic.py` (no Temporal). Since T5.2 the step pipeline runs through `blocks/step.py` — the by-name mock approach is unchanged (activity names and order per mode are identical; the committed histories replay unregenerated), the mode table has direct unit tests in `tests/test_step_block.py`, and new workflow tests must pass `sync_mode=True` (the batch-first default otherwise routes to an unregistered `submit_batch_request` mock). Since T5.3 the gather and dispatch run through `blocks/gather.py` / `blocks/dispatch.py`, with direct unit tests in `tests/test_gather_block.py` / `tests/test_dispatch_block.py`; a crashed fan-out child is a failed `SubTaskResult` (`child_crashed`), not an escaping `ChildWorkflowError`, and interaction-record uniformity across all five arms is pinned by `TestInteractionRecordsForEveryArm`. Replay coverage: 16 committed histories under `tests/replay/` with a Replayer test — including three failure-path histories (`preflight_retry_sync`, `preflight_halt_sync`, `plan_revision_halt_sync`, added by the T5.6 follow-up so the retry arm and both plan-halt terminals are replay-pinned); regenerate with `uv run python -m tests.replay.regenerate` (or `make replay-histories`) after deliberate workflow-logic changes, or name scenarios to regenerate a subset (`uv run python -m tests.replay.regenerate <name>…`, added in T5.5 so new histories never re-emit committed ones) — histories are not byte-stable across regenerations (ids, timestamps), only shape-stable. **Since T5.5 the workflow suite is `tests/workflows/` (eleven per-mode files) over `tests/support/workflow_harness.py`**: `tests/test_workflows.py` and its module-global scenario state are gone, along with every `global` statement and `_reset_*` function. A test constructs its own `ScenarioState` and hands `build_activities(state)` — the 26 canonical by-name mocks, closures over that state — to the per-test `Worker`; `tests/support/block_mocks.py` holds the four T5.2/T5.3 factories that assert exact call sequences. Script outcomes **keyed by identity, never by arrival order** (that race was the mechanism of the old ~1/8 flake, fixed in T5.5): transitions/validations key on the *validate identity* (`ValidateOutputInput.task_id` — the task id, or the compound `parent.sub.child` id), LLM responses on the *call identity* read off the assembled context, and batch-lane calls recover identity from `request_id`. Scripts handed in are read-only (`MappingProxyType`, internal cursor); do not reintroduce module-level mutable containers — they are the `pytest-xdist` blocker (`uv run pytest -n auto --no-cov tests/workflows/` runs the suite on 14 workers; the coverage-gated run stays serial). A worker-restart scenario needs `max_cached_workflows=0` (a dead worker's sticky queue drains only after a schedule-to-start timeout the time-skipping server does not fast-forward) — see `tests/workflows/test_crash_recovery.py`. Since T5.6 a planner fixture whose sub-tasks **declare** overlapping target files is rejected by the preflight gate before any step runs, so conflict-resolution scenarios declare distinct targets while both children still *write* the shared file (conflict detection classifies what children produced, never what the plan declared) — the shape used by `tests/support/block_mocks.py::five_arm_activities` and `tests/replay/regenerate.py::_scenario_conflict_resolution_sync`. Multi-attempt planner scenarios are scripted with `ScenarioState.plan_sequence` (keyed by planner task id, cursor-consumed, sticky); the preflight/REVISE workflow scenarios live in `tests/workflows/test_preflight.py` and the pure checks in `tests/test_plan_checks.py` (no Temporal).

CLI tests use Click's `CliRunner` and mock async submission helpers with `_async_result(value)` (a helper that returns an async function wrapping `value`, avoiding orphaned coroutine warnings from `asyncio.run`).

Activity tests construct the activity class with injected fakes and call the bound method directly as a plain async function (not through a Temporal worker): `LlmActivities(FakeLLM())` (or the directly-injected `build_mock_llm` mock still used by forge's activity-test files), `StoreActivities(engine)`, `BatchActivities(...)` in forge; `OcrStoreActivities(engine, blobs)` in ocr; `LlmActivities`/`StoreActivities`/`EmbeddingActivities` in pbook. Since T3.6 there are no module-global clients/engines/registries to monkeypatch, so the `dispose_store_engines`, output-type-registry, and mistral-cache reset fixtures are gone; `sax_platform.testing` supplies `FakeLLM` and `FakeMistralOcr`, and tests own engine lifecycle through explicit fixtures. No-dependency activities (git, validate, output, the pure context assemblers) stay free functions called directly.

Cross-queue workflow tests (e.g., ingestion) run two `Worker` instances in parallel — one on `forge-task-queue` and one on `pbook-task-queue` — with mock activities/workflows registered on each. (These are deleted with forge's ingestion side in T6.4.) The workflow sandbox restricts module-level mutable state access inside workflows, so canned results must be returned from activities rather than read from module globals.

## The Universal Workflow Step

Every operation follows: construct message, send to LLM, receive response, serialize result, evaluate transition. Temporal provides the workflow engine; the LLM call is a Temporal activity, while transition evaluation is a pure function — `forge.step_logic.determine_transition` — inlined into the workflow (T5.1, D95, amending D3). Since T5.2 the pipeline body exists **once**: `forge.blocks.step.run_step_attempts(spec, host)` runs it for all three modes, with the differences (assemble activity, worktree ownership, commit policy) expressed as the three rows of the pure `MODE_POLICIES` table — do not reintroduce inline pipeline copies in the `forge/workflows/` drivers (since T5.4, `workflows.py` is a package: `task.py` / `subtask.py`, and the former `workflow_blocks.py` is dissolved into `blocks/{transport,worktree}.py`). Since T5.3 the fan-out gather and the typed LLM dispatch exist once as well — `forge.blocks.gather.run_fan_out_gather(spec, host)` (two-row `GATHER_POLICIES`; per-child failure isolation; explicit `ParentClosePolicy.TERMINATE`) and `forge.blocks.dispatch` (the `ARMS` table; every arm persists an interaction record with token counts) — the same no-inline-copies rule applies, and every activity timeout/retry preset comes from `forge/presets.py` only (the values are ScheduleActivityTask command attributes; changing one is a replay-breaking change). Deterministic work stays deterministic: there is no `evaluate_transition` activity, and `forge.step_logic` (zero `temporalio` imports) also holds the failure-summary helpers, the terminal-result builders that stamp `failure_kind`, the merge-resolution union, the output-slimming builders (file contents travel once, in the top-level `TaskResult.output_files`; embedded Step/SubTaskResults carry `output_digests`), the `LLMRunTotals` aggregator, and the child-id/timeout helpers. Since T5.6 plan structure is deterministic in the same way: `forge.plan_checks` (zero `temporalio` imports) holds the recursive finders shared by the live preflight gate and `eval/deterministic.py`, plus `splice_revision`, and the gate runs inline at the single `blocks/dispatch.py::dispatch_planner` seam — it emits no commands on a clean plan, which is why adding a check that needs repo I/O (an activity) is a replay-breaking design change, not a detail. Every LLM call is structured as a document completion for batch API compatibility. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for details.

## Git Strategy

- Each task-level agent works in its own git worktree branched from `main`.
- Merges to `main` are always human-gated.
- Worktrees are disposable: on failure, document the problem, create a fresh worktree, start over.
- Task ordering from the plan is the primary conflict avoidance mechanism.

## Execution Modes

- **Single-step** (`plan=False`, default): Assemble context, call LLM, write, validate, commit.
- **Planned** (`plan=True`): Planner decomposes task into ordered steps; each step commits on success.
- **Fan-out** (planned steps with `sub_tasks`): Parallel child workflows per sub-task, gathered and merged by the parent.

All modes include automatic context discovery (Phase 4), LLM-guided exploration (Phase 7), diff-based output (D50), and error-aware retries (Phase 8) by default. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for details and CLI flags.

The end-to-end lifecycle — roles, the dispatch model, verification and close-out gates, records ownership, and the standing directives — is mapped in [development-plans/SDLC.md](development-plans/SDLC.md).

**Agent model split** (owner directive, 2026-07-24): planning stays in the main session; implementation work is dispatched to the `implementation-driver` agent (Opus, defined in `.claude/agents/`), which writes non-trivial code itself and delegates only obviously easy, mechanical code to `code-writer` (Sonnet), reviewing everything it accepts. The bias is explicit: if it's not obviously easy, Opus writes it. Subtle seams — Temporal workflows, the environment guard, concurrency, migrations — are never delegated to Sonnet.
